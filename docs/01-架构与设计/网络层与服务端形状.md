# 网络层与服务端形状（asio 取舍 / 单连接单对局 / 输出采样）

整理时间：2026-09-17。对应分支 `feat/netsrv`（工作区 `project/agents/netsrv`）。

本文回答三个问题，并记录已经落地的部分：

1. 网络层要不要继续用 Boost.Asio？→ **不引入，自持原生 reactor**（已落地并验证）。
2. 服务端是"单连接单对局"还是保留"单连接多对局"？→ **以对局（Room）+ 座位（Seat）建模**，
   两种形态是同一套对象的两种座位数（已定，未落地）。
3. 服务端是否只做后端、不做配置，只在几个特殊时点采样发给前端渲染？→ **方向对，
   但"只在几个特殊时点采样"要改成"全时点事件带 + 按需快照"**（已定，未落地）。

## 一、去 Asio：改动面比直觉小得多

### 1.1 先量清楚 Boost 到底被用来做什么

全仓（`include/ src/ resources/ test/ tools/`）grep `boost::` 符号，只有两类：

| 符号 | 引用数 | 用途 |
|---|---|---|
| `boost::asio::*` | 80 | `io_context` / `thread_pool` / `post` / `dispatch` / `strand` / `executor_work_guard` / `ip::tcp::socket` / `async_write` |
| `boost::system::*` | 13 | `error_code`（配合 `BOOST_ERROR_CODE_HEADER_ONLY` 头文件版） |

**没有** `boost::unordered_map`、`boost::filesystem`、`boost::shared_ptr`、`boost::format` 等。
（早期 grep 命中的 `rule_center.h`、`battleContext.h`、`battle_primitives.h` 是 `stat_boost` /
`attack_boost` 这些标识符的子串误报，不是 Boost。）

关键结论：**插件 ABI（`include/plugin/core_api.h`）不含任何 Boost 类型**，`BattleContext`
也不含 Boost 成员。所以拆掉 Boost 不触碰插件边界，也就不触碰"字段偏移一致性"这条红线。

### 1.2 用到的 asio 能力面只有极小一角

实际调用的只有四件事：`accept`、`async_read_some`、`async_write`、`thread_pool::post`。
asio 真正的价值在高阶组合（resolver、timer、strand 组合器、协程、超时组合、SSL），
这些一个都没用。用法等价于"给我一个能收发的 socket + 一个 post 队列"。

代价侧则是实打实的：`find_package(Boost REQUIRED)` 让整个项目（含每个场景测试二进制、
每个插件）都背上 Boost。所以**为了这一角能力引入整条依赖不划算**，自持一个
reactor（约 1300 行含注释）维护成本更低、可读性更好、调试时栈完全在自己手里。

需要改动的文件一共 9 个：`thread_pool/boost_thread_pool.h`、`thread_pool/io_thread_pool.h`、
`fsm/iControlBlock.h`、`fsm/iControlBlock.cpp`、`server.h`、`server/server.cpp`、
`tools/training_cli.cpp`、`fsm/battleFsm.h`（只改线程池类型）、`CMakeLists.txt`。
其中 `io_thread_pool.h` 本来就是死代码（`post_impl` 整个被注释掉了）。

### 1.3 已落地：`src/net/` 原生事件循环

| 文件 | 行数 | 职责 |
|---|---|---|
| `include/net/poller.h` | 56 | 平台 IO 多路复用原语的最小抽象（唯一有平台分支的地方） |
| `src/net/poller_platform.cpp` | 358 | kqueue（macOS/BSD）/ epoll（Linux）实现 |
| `include/net/reactor.h` + `src/net/reactor.cpp` | 899 | 事件循环、连接、非阻塞读写、写队列、定时器、跨线程投递 |
| `include/net/framing.h` | 100 | 长度前缀成帧（与既有 10 字节头协议一致） |
| `include/thread_pool/native_thread_pool.h` | 157 | 纯标准库线程池，替换 `boost::asio::thread_pool` |
| `test/test_net_reactor.cpp` | 557 | 验证程序 |

设计要点：

- **线程模型**：一个 `Reactor` 绑一个线程，poller 只在 loop 线程被碰。跨线程只开放两件事
  `Reactor::post(fn)` 与 `Connection::write()`，二者内部经唤醒管道交回 loop 线程。
  这样"战斗计算线程池算完要发数据"这条路径不需要知道 loop 在哪，也不存在并发动 poller。
- **定时器取消用迭代器索引**：`multimap` 的键（到期时刻）会重复，只存时间点定位不到具体那一枚。
  另外周期定时器**先重新排期再执行回调**，否则回调里 `cancel_timer(id)` 会被"复活"。
- **关闭路径三重保证只触发一次**：`closed_` 上的 CAS、`close_handler_fired_` 标志、
  以及 close 回调只在 loop 线程触发。
- **写队列上限约束的是积压量，不是单条消息长度**。这条是实测改出来的：最初写成
  `queued + msg > cap` 就拒绝，结果一条合法的、比上限还长的快照永远发不出去。现在只有
  积压本身超限才断开（对端不消费 / 故意灌数据），不让单个连接把服务端内存拖垮。
- **`SO_NOSIGPIPE` / `MSG_NOSIGNAL`**：macOS 上向已关闭连接 `write()` 会直接给进程发
  SIGPIPE 把服务打死，必须设；两个平台各用各的机制。

### 1.4 验证覆盖（`sim_net_test`，20 轮连跑全绿）

| 用例 | 钉住的错误 |
|---|---|
| 成帧器：逐字节喂入 / 一次 3 帧粘包 / 半包 / 超长拒绝 / 低于下限拒绝 | 分包粘包、内存放大攻击面 |
| 64 连接 × 40 帧并发回显，逐字节比对 | 并发路径、连接隔离、串包 |
| 3MB 单帧 | EAGAIN 部分写、分包读、大帧 |
| close 回调恰好一次（每连接计数，且回调次数 == 收到回调的连接数） | 重复关闭 / 漏关闭 |
| 对端不读 → 写队列超限 → 服务端断开 | 背压，内存放大 |
| 帧头声明 2GB → 拒绝并断连 | 失同步后的流处理 |
| run_after / run_every / cancel_timer | 定时器重复排期与取消复活 |
| 全部连接回收后 fd 数回到基线 | fd 泄漏 |

> 仪表坑记一笔：close 计数最初按 `Connection*` 建索引，堆地址被后续连接复用后读到上一个
> 连接的残留值，把"地址复用"误报成"重复关闭"（12 轮里偶发 2 轮）。计数器改挂在
> Session 上（每连接一份）后 20/20 通过。**验证代码自身的可观测性也要能证明是对的**，
> 否则会把仪表的 bug 记成实现的 bug。

### 1.5 Windows / IOCP：本轮**不做**，这是有意的

`Poller` 抽象覆盖的是 **readiness** 家族（epoll/kqueue）。IOCP 是 **completion** 语义，
两者不可通约：IOCP 没有"这个 fd 可读"这回事，只有"你投的那个 `OVERLAPPED` 完成了"。
把它塞进 `Poller` 接口只会得到一个假的抽象。

正确做法是替换 Reactor 的等待/投递机制（`src/net/reactor.cpp` 里的 `run_once` +
`schedule_flush` 那一层），而 `Connection` 的对外形态（`on_read` / `write` / `close`）
不变。当前 `src/net/reactor.cpp` 对非 POSIX 平台是 `#error`，宁可不给，也不留一份
"看起来能用、其实没在 Windows 上编过"的代码。

**建议**：等真有 Windows 构建机（或有玩家反馈必须在 Windows 跑）再写 IOCP 后端。
在那之前 macOS(kqueue) + Linux(epoll) 覆盖了联调与部署两端。
另注：`poller_platform.cpp` 的 epoll 分支本机（macOS）无法编译验证，
逻辑与 kqueue 分支同构但**未在 Linux 上跑过**，第一次在 Linux 构建时请优先回归 `sim_net_test`。

## 二、服务端形状：用 Room + Seat 建模，而不是"连接"或"对局"

### 2.1 结论

"单连接单对局"是对的方向，但**不要把它写成代码里的硬假设**。把对局建模成一个
**Room**，Room 里有 1~2 个 **Seat**（座位），每个 Seat 由一个连接驱动：

| 形态 | 座位数 | 用途 |
|---|---|---|
| 单人驱动（solo） | 1 | 一个连接同时喂双方操作。**验证期的主力形态**：测试者一个人就能复现问题，不需要找第二个玩家 |
| 双人对战（pvp） | 2 | 两个连接各占一个座位，服务端做撮合 |

两种形态共用同一个 Room / 状态推进 / 输出序列化代码，只是座位数不同。这样：

- 本次开放给玩家验证时，**单人形态已经能覆盖绝大多数"这个判定对不对"的验证需求**
  （现在的 `sim_training_cli` 就是这种用法），不必先做撮合、房间号、断线重连。
- 之后要双人对战，加的是**撮合层**（谁和谁进同一个 Room），不是重写对局层。

### 2.2 这条选择顺带消掉的复杂度

现有 `TrainingControlBlock` 之所以绕，是因为它是"单 socket 多 uuid 多对局"：
`waiting_uuid_`、`pending_inputs_`、`ctx->m_buffer`、`ctx->is_empty`、
"当前是否正处于等待输入状态"的判断，全是为了在一个连接里复用多个对局。

单连接单对局（一连接一座位）之后，这些结构全部消失：一个连接 = 一个座位 = 一个
`BattleContext`，消息直接落到自己的上下文，不存在按 uuid 路由。协议里的 `uuid` 字段
可以保留（对既有 CLI 兼容），但不再是路由依据。

`docs/01-架构与设计/训练模式控制块与调度演进建议.md` 里记的 `run_mutex` 阻塞问题，
在单连接单对局下也不再是问题：一个对局本来就只有一个真实执行者，不需要锁去防并发推进。

## 三、输出：服务端不做配置，但采样点不能只有"几个"

### 3.1 结论

方向是对的：**服务端是权威规则引擎，不做 UI / 配置 / 渲染**，把数据交给前端自己渲染。
但"只在几个特殊时点采样"这一条要改，否则前端渲染不出可验证的过程。

### 3.2 理由：一个回合不是一个输出，而是一串

`State` 枚举有 41 个时点，一个回合要顺序走完其中几十个（先后手各自的行动开始 / 命中前 /
命中时 / 技能效果 / 伤害结算 / 行动后 / 行动结束 / 额外行动 / 死亡结算，再加回合结束系列）。
"技能造成伤害 → 魂印回血 → 粉伤再扣"这种过程，玩家要看的是**每一步**，
而不是回合首尾两个状态。验证场景下尤其如此：测试者需要能指着"第 7 步的伤害算错了"。

所以建议输出分三条，而不是"几个采样点"：

| 输出 | 时机 | 内容 | 用途 |
|---|---|---|---|
| **事件带**（event tape） | 每次状态推进 | `{seq, state, round, actor, kind, 数值增量}` | 前端像放胶片一样播放整个回合；定位到具体某一步 |
| **快照**（snapshot） | 需要输入时 + 客户端主动请求 | 现有 `getStateJson()` / `getFullStateJson()`（**已存在，直接用**） | 渲染"现在长什么样"；权威状态 |
| **合法动作集**（legal actions） | 需要输入时 | 该玩家此刻能做什么（哪些技能可用、哪些精灵可换、药剂） | 前端只渲染合法按钮；消掉一整类客户端错 |

第三条是现在缺的、但性价比最高的一条：内核里 `skill_usable(ctx, robotId)`、
`elfPets[i].is_locked` 这些判断**已经有了**，只是从没往客户端发过。发出去之后，
前端不会给出非法输入，玩家验证时也不会把"我点了没反应"误报成 bug。

**"哪些时点算特殊"这个决定应该放在前端，不要焊死在服务端。** 服务端负责吐出有序、
完整、带序号的事件流 + 权威快照；哪些画成动画、哪些合并成一帧，是渲染层的事。
否则每加一个机制都要回来改服务端的采样点清单。

### 3.3 输入侧需要一起改的

现有 `INIT_BATTLE` 要求客户端拼一个"每只精灵 13 个 int"的二进制块
（`pet_id + 5 技能 + 6 base + common_trait_id`，见 `tools/training_cli.cpp` 的 `build_init_012_body`）。
写 CLI 可以，写 Web / Unity 前端很痛苦。建议**同时支持一份 JSON 初始化**
（每槽位 `{petId, skills[5], base[6], traitId}`），二进制旧格式保留兼容。
这不属于"配置"，是请求载荷。

## 四、落地情况（2026-09-17 完成）

上面三条结论都已落地，Boost 已从依赖中彻底移除。

| 项 | 位置 |
|---|---|
| 原生事件循环 | `include/net/` + `src/net/`（kqueue/epoll） |
| 原生线程池 | `include/thread_pool/native_thread_pool.h` |
| FSM 的 IO 契约 | `include/fsm/iControlBlock.h` —— 从 14 个方法瘦到 **3 个** |
| 线协议 | `include/server/protocol.h` |
| 对局（= IControlBlock 实现） | `include/server/room.h` + `src/server/room.cpp` |
| 连接/座位/命令派发 | `include/server/session.h` + `src/server/session.cpp` |
| 房间表/撮合/线程池 | `include/server/service.h` + `src/server/service.cpp` |
| 阵容解析（二进制 + JSON） | `include/server/battle_init.h` |
| 合法动作集 | `include/server/legal_actions.h` |
| 输出序列化 | `include/server/output_json.h` |
| 时点采样录制 | `include/effects/state_tape.h`（挂在 BattleContext 上，默认关） |

删掉的：`include/server.h`、`src/server/server.cpp`、`src/fsm/iControlBlock.cpp`
（旧的两个 asio 控制块 + 线协议混在 FSM 头里）、`include/thread_pool/{boost,io}_thread_pool.h`。

`IControlBlock` 现在只有三个方法 —— 全仓 `control_block_->` 的调用点本来就只有
`wait_for_input` / `async_write`，`on_fsm_paused` 是新增的输出时点：

```cpp
virtual void wait_for_input(BattleContext* ctx) = 0;
virtual void async_write(int player_id, const std::string& data, BattleContext*, BattleFsm*) = 0;
virtual void on_fsm_paused(BattleContext* ctx) = 0;   // 输出集中在这一个时点
```

原来接口上的 `broadcast` / `broadcast_to` / `duplicate_context` / `log_operation` /
`is_training_mode` / `get_fsm` / `set_fsm` / `register_context` / `unregister_context`
**全仓零调用**，已删除。它们只服务于"一个连接塞多个对局"的旧控制块。

### 4.1 命令一览

| 方向 | 命令 | 说明 |
|---|---|---|
| C→S | `INIT_BATTLE`(5) | 旧的二进制阵容（每只 13 个 int32），保留兼容 |
| C→S | `INIT_BATTLE_JSON`(6) | JSON 阵容。solo 给 `side1`/`side2`；pvp 给 `party`（自己那一边） |
| C→S | `SELECT_SKILL`(1) / `USE_MEDICINE`(2) / `CHOOSE_PET`(3) | payload = 3 个 int32：robot / action_type / index |
| C→S | `SYNC_STATE`(10) / `DEBUG_FULLSTATE`(23) | 权威快照 / 完整转储 |
| C→S | `DEBUG_STEP`(20) / `DEBUG_CONTINUE`(21) / `DEBUG_BREAKPOINT`(22) | 单步 / 连续 / toggle 断点 |
| C→S | `HEARTBEAT`(11) | 心跳 |
| S→C | `ROOM_INFO`(34) | match / seat / seats / mode |
| S→C | `TAPE`(30) | 本次推进的**事件带**：每时点一条采样（含 HP、等级、伤害、事件） |
| S→C | `INPUT_REQUIRED`(31) | 该谁操作 + 内嵌快照 + 合法动作集 |
| S→C | `ERROR`(33) | 错误文本 |
| S→C | `BATTLE_OVER`(35) | 胜者 + 结束原因 + 最终快照 |

帧格式不变：`[4B 大端 total][2B 大端 cmd][4B 大端 uuid][payload]`，最小 10 字节。

> ⚠️ 一个字节序陷阱（实测踩过）：`BattleContext::m_buffer` 是 FSM 用 `memcpy` 当成
> `int[4]` 读的，所以**交接口的 payload 必须是本机字节序**，不能是大端。写成大端的后果是
> 小端机上 `action_type=1` 变成 `16777216`，所有动作被判 "rejected, please resubmit"。
> 转换点在 `proto::build_fsm_input`，那里有注释。

## 五、实测发现的两个问题（都不是本轮改出来的）

### 5.1 两个场景用例本来就失败

全量回归：**71 通过 / 2 失败**，失败的是
`sim_scenario_030_aigens_finish`（断言 `ability_levels[0][kRender]=0 vs 2`，exit 134）
与 `sim_scenario_072_skill_batch6`（`b2.pet(1).hp=1000 vs 1500` 后崩溃，exit 138）。

已用 `git stash` 回到本轮起点（`8156343`）单独验证：**两者在基线上同样失败**，
所以本轮重写零回归。顺带更正：我在上一轮说"73 个场景全过"是错的 —— 那次构建其实
没成功（`BUILD_EXIT=2`），回归跑的是上一轮的旧二进制。现在这个 71/2 才是新代码的真实结果。

### 5.2 引擎缺少"一方精灵全灭 → 结算败北"的判定

自动对打到一方精灵全灭时，对局**永久卡死**：

- `State::CHOOSE_AFTER_DEATH` 的 `need_input()` 只看"场上精灵是否倒下"，不看
  "还有没有活着可换的精灵" → 返回 true；
- `handle_ChooseAfterDeath` 只接受 `CHOOSE_PET`，而全部精灵已 `fainted` → 无从输入；
- `kLinearStateOrder`（40 个状态）里**没有 `FINISHED`**，`generateState()` 是线性走表 ——
  败北结算依赖"被击败方换宠后继续推进"到 `BATTLE_ROUND_COMPLETION` → 越过表尾 → FINISHED。
  换宠这一步做不到，链条就断了。

服务端目前的处理：`on_fsm_paused` 里检测"正在等输入但该玩家**没有任何合法动作**"，
兜底发 `BATTLE_OVER`（`reason: "engine_no_legal_action"`）并打 ERROR 日志。

这是**兜底，不是修法**：它保证玩家不会被挂死（否则"开放给玩家验证"根本进行不下去），
但引擎侧的败北判定口径属于领域语义，需要先定规则再改。候选修法（供决策）：

1. `need_input()` 在该方无存活精灵时返回 false，**同时** `handle_ChooseAfterDeath`
   在没有合法换宠目标时不再要求输入、直接推进状态机；
   ⚠️ 两者必须一起改 —— 只改 `need_input()` 会让 run 循环对空 `m_buffer`
   反复调用 handler 而不推进状态，变成线程内死循环。
2. 或者新增一个显式的"败北判定"时点/handler，在全灭时直接置状态到 FINISHED。

规则上要先确认：全灭是否即时判负？是否有"最后一只不能被打死"之类的保护机制
（`BATTLE_NEW_DEFEAT_MECHANISM` / `OPERATION_PROTECTION_MECHANISM_2` 这两个时点存在，
但当前实现没有做出这个判定）。

## 六、下一步（剩余）

1. **pvp 撮合**：座位 1 的撮合路径已通（两个连接各坐一座、各自提交自己那一边阵容），
