# RuleCenter 容器选型评估

评估日期：2026-09-27（基线 commit `3a67101`，场景库 134 个用例）。

## 目的

回答一个问题：`RuleCenter` 现在是单一 `std::vector<RuleTicket> all_`，查询按
category + target 线性过滤；是否值得换成 `std::array<std::vector<RuleTicket>, N>`
按 category 分桶，让查询只扫命中桶、不再遍历全部票。

当前结论是：

- **不换。** 实测票数规模与查询量都比预想小两个数量级以上，分桶省的是纳秒级。
- 评估用的插桩与临时分支已删除，本记录保留数据与重启条件。
- 顺带横向看了事件中心等组件，真热点不在内核容器（见 §五）。

## 实测方法与数据

方法：在临时 worktree 分支上给 `rule_center.h` / `event_center.h` 加原子计数插桩
（查询循环进入数、逐票判定数、票数峰值、事件投递数等），跑全部 134 个场景二进制
（约 1199 场对局）后汇总，评完即还原。插桩对代码只增不改语义，场景全部通过。

### RuleCenter

| 指标 | 数值 |
|------|------|
| 单 center 票数峰值（全场景最大） | **7 张**（场景 091 神觉·米斯蒂克——票最密集的用例） |
| 典型对局峰值 | 1–3 张 |
| 每场对局查询循环进入次数（均值） | ~38 次 |
| 每场对局逐票判定总次数（均值） | ~8 次 |
| `sizeof(RuleTicket)` | 208 字节（3 个 `std::function` 占大头） |

峰值 7 张 × 208B ≈ 1.5KB，稳定在 L1。换成分桶后查询从扫 ~2–7 张降到 ~1–2 张，
**每次查询节省纳秒级**，整场对局合计省不到 1 微秒。最重场景（080 混沌魔君索伦森）
单次运行 CPU ~22ms（含进程启动 + DB 初始化），全量 134 场景套件秒级跑完。

### EventCenter（对照）

全场景合计 emit 8611 次，其中只有 **670 次**投递时有监听器在场（绝大多数事件
只是录进事件带供回放）；`deliver()` 里为投递中增删安全而做的 `ids` 向量拷贝合计
759 个元素。事件分发同样不构成瓶颈。

## 为什么不改（数据之外的结构理由）

1. **生命周期清扫本来就是全量遍历。** `tick_rounds` / `cleanup` / `clear_on_stage` /
   `clear_round_type` / `invalidate_stale` / `recount()` 都必须扫所有票，分桶只优化
   查询那一半——而查询恰恰是实测中便宜的那一半。
2. **这是全库语义最密的文件**（1600+ 行，每个方法挂着用户拍板的机制口径注释）。
   项目当前主矛盾是规则正确性不是吞吐（见《训练模式控制块与调度演进建议》），在
   这里做机械重构的风险收益比很差。
3. **耦合面不小。** `entries()` 被 ~15 个测试文件直接消费（含按下标断言）；
   `consume_immune` 的"只扣最外层"、池改写的"授予序折叠"、盔遮蔽的"取首张"都依赖
   **桶内授予序**。分桶能保住桶内顺序（改起来是可行的），但每处都要重新核对一遍。

## 重启条件（什么时候回头看）

满足任一条再启动，方案照本记录 §三的第 3 点执行（按 category 分桶、
`array<vector<RuleTicket>, kCategoryCount>`，桶内保持授予序）：

- 批量自博弈训练落地后 **profile 实测**指向 RuleCenter 查询（不是猜）；
- 活跃票数规模涨一个数量级（如全队 12 只精灵都挂常驻票的机制普及）。

工作量预估：机械重构 + 全场景回归，约一天。

## 横向评估：其他组件与真热点

- **内核容器整体不是瓶颈。** `event_center` 已按事件类型建索引、`timed_bucket` 已按
  (State, owner) 分桶，唯一没索引的 `RuleCenter` 实测量级见 §二。三者都不值得动。
- **时间的真实去向**：场景单次运行 wall ~131ms 但 CPU 只 ~22ms——大头是进程启动 /
  fork / dyld / DB 打开，不是内核逻辑。将来训练吞吐成为目标时，值得投入的方向是
  **进程内批量对战 API**（复用已加载的 DB 连接与已组装的精灵工厂，绕开
  fork + socket），与《训练模式控制块与调度演进建议》"高性能训练不经过 socket"
  的预判一致。
- **微观点位（记账不动）**：`EventCenter::deliver` 的 ids 拷贝可换成成员级 scratch
  buffer 复用（省 realloc 不省拷贝）；`resolve_anomaly_pool` 的去重是 O(n²)（池
  ≤8 个异常，无所谓）；`notify` 的盔遮蔽嵌套扫描 O(盔×标记)（两者都是个位数）。

## 附录：`grant_immune` 不调 `recount()` 的口径

`grant_immune` 是全 RuleCenter **唯一**授予后不调 `recount()` 的方法（含句柄复用、
覆盖键刷新、新增三条路径）。今天安全，原因是：IMMUNE 属
`is_undeletable_category`，**永远不进 `round_count_`**（`has_round_type` 的"有无可断
物"门只统计非免断的回合类票），故免疫票的授予/刷新对回合类计数恒为零贡献，漏调
无副作用。这个不变量没有局部说明，容易在演进中踩坏——已在 `rule_center.h` 的
`grant_immune` 处补注释；将来若新增"回合类且可被断"的 IMMUNE 细分、或 `recount`
统计口径变化，必须补上 `recount()` 调用。
