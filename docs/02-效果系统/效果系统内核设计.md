# 效果系统内核设计：事件通道与免疫系统

整理时间：2026-08-08

定位：
- 本文聚焦"效果系统有哪几个固定内核、机制如何作为数据住进内核"。
- 决策框架见 `docs/04-训练与AI/AI决策框架与训练思路.md`，时点定义见 `include/fsm/battleContext.h` 的 `State` 枚举。
- 核心结论先行：**机制是数据，不是 struct；内核是少数几个固定的注册表；FSM 永远不因新机制而加代码。**

---

## 一、为什么必须有"内核"概念：防屎山测试题

官方代码变屎山的根源不是 struct 多，而是**每个机制把自己的钩子硬编码进 FSM**（N 机制 × M 时点 = N×M 段散落的调用）。防屎山的保证只有一条：

> **FSM 只访问一个固定的、很小的内核集合；机制一律是内核里的数据；FSM 永远不因为新机制而加代码。**

区分"这个新东西是内核还是数据"的测试题：

> **这个机制会不会被多个不相关的原语反复查询？**
> - 会 → 它是**内核**（共享查询，值得一个注册表）。
> - 不会，只被单一入口调用 → 它是**数据**（一段程序）。

实例：
- 免疫：断回合、控场、伤害减免、属性弱化……全都问 `is_immune` → 内核。
- 断回合补偿："被断时XXX"，未来所有"当X事件发生时"的机制都要同一件事 → **事件通道**（内核）。
- 护盾本身：多个原语要查"有没有盾" → 内核；但"破盾后造成固定伤害"只是**数据**（程序）。

## 二、内核总览（当前盘点的固定集合）

| 内核 | 现状 | 职责 |
| --- | --- | --- |
| 1. 时点效果桶 | ✅ 已有 | `skills_effects` / `soul_mark_effects` / `updater_effects`，按 State 执行程序 |
| 2. 回合效果 + 断回合 | ✅ 已有 | `ContinuousEffect` + `valid_id` 版本号，负责"持续 N 回合、可在时点行动、可被断"这一轴 |
| 3. **事件通道** | 🆕 新增 | `on_round_broken` 泛化，统一"当X事件发生时"的所有补偿/反应 |
| 4. **免疫内核** | 🆕 新增 | 免断/魂免/免伤/免弱等，统一"在时点 T 对威胁 X 免疫"的查询 |
| 5. 异常状态 | ✅ 已有 | 36 状态 + 生命周期 + 抗性 |
| 6. 伤害管线 | ✅ 已有 | FSM 中的伤害结算链 |

新增机制进入流程：**先写成程序（数据）塞进现有内核 → 内核缺一维就扩展其数据模型（加枚举值/条件目录项，小改可审）→ 只有出现"未来多个机制共享的新不变量"才建新内核（一个注册表，不是按机制建）。**

## 三、事件通道内核（EventCenter）

### 3.1 概念与动机

"断回合补偿"根本不是普通回合效果，而是**独立监控性质的响应**。把它往上推一层：所有"当X事件发生时触发补偿/反应"的机制共享同一个不变量——**需要一条从发生点到响应点的通道**。这就是事件通道。

旧实现 `on_round_broken` 只服务断回合一个事件，是一条专用管道。泛化后成为唯一的通用管道：

```
原语成功路径末尾 → emit(EVENT_X) → EventCenter → 匹配 watcher → 同步执行
                                                          └ 或注册效果到未来时点 → FSM 推进自然执行
```

### 3.2 事件与 watcher 数据模型

```cpp
enum class EventType {                     // 枚举值增长 = 数据扩展，不是新 struct
    EVENT_BREAK,             // 断回合成功
    EVENT_DEATH,             // 精灵死亡
    EVENT_CONTROLLED,        // 控场异常施加成功
    EVENT_ANOMALY_APPLIED,   // 任意异常施加成功
    EVENT_HIT,               // 攻击命中
    EVENT_TAKE_DAMAGE,       // 受到伤害结算后
    EVENT_ENTER_STAGE,       // 上场
    EVENT_SWAP,              // 换宠
    EVENT_OPPONENT_DEFEATED, // 击败对手
};

struct BattleEvent {         // 事件载荷：类型 + 双方 + 可选泛化 payload
    EventType type;
    int actor;               // 发起方
    int target;              // 承受方
    // payload 先最小化，随需要作为数据扩展
};

struct EventWatcher {
    EventType type;
    int owner;                                      // 谁注册的（决定回调里的 self 视角）
    int register_round;
    int duration_rounds;                            // 0 = 永久; >0 = 窗口（对齐被保护效果）
    bool once;                                      // 触发一次后自动移除
    std::function<void(BattleContext*, const BattleEvent&)> fn;
};

class EventCenter {
    std::unordered_map<EventType, std::vector<EventWatcher>> watchers_;
    std::vector<BattleEvent> pending_;              // 重入防护队列
    bool delivering_ = false;
public:
    void register_watcher(EventType, EventWatcher);
    void emit(const BattleEvent&);
    void drain_pending();                           // 状态迁移末尾调用
    void cleanup(int roundCount);                   // round-reduction 统一清理过期 watcher
    int  watch_count(EventType) const;
};
```

### 3.3 投递策略：emit 只入队，FSM 在固定 drain 点投递（已定）

- **emit 是纯入队**：原语成功路径末尾只把事件塞进队列，**绝不内联执行 watcher**。这从根上消除重入——emit 不跑任何代码，也就不会"同步执行中再次 emit"，不需要重入防护队列。
- **投递点固定**：FSM 在"每个 State 的效果桶跑完后、推进到下一个 State 之前"统一 drain 事件队列，投递给匹配的 watcher。投递时机对状态机相对位置恒定，消除"未知时序"。
- **桶迭代安全**：drain 在桶执行完之后，效果桶此刻稳定，watcher 改动 context 不会破坏正在迭代的结构。
- **watcher 的两种反应**：
  1. 直接改 context（即时补偿，如"被断时反伤"）——drain 点改值安全。
  2. 注册效果到未来时点，等 FSM 自然推进（延迟补偿）——更常见。
- **同 State 注册不被同一轮拾取**：drain 在桶之后，watcher 注册到"当前 State"的效果要下一轮才执行——这是刻意的确定性选择；即时补偿直接用改值表达。
- **已知边界**：一次 drain 内 watcher 又 emit 的事件进入下一轮 drain；极端互发用深度预算兜底（防御性，理论不触发）。

### 3.4 watcher 的两种响应模式（优雅统一的钥匙）

EventCenter 不关心 watcher 做什么，但两种模式是设计目标：

1. **同步执行**：`fn` 直接改 context。适合"即时反伤""即时回血"。
2. **注册未来效果**：`fn` 调用 `context->registerEffect(未来State, ...)` 把效果注册到未来时点，等 FSM 自然推进执行。适合"被断后下回合速度+1""受控后 N 回合内锁伤"。

两种都只是"fn 里写什么"。**补偿逻辑全部住在 watcher 里，原语不实现任何补偿。**

### 3.5 断回合补偿迁移

| 旧（on_round_broken） | 新（EventCenter） |
| --- | --- |
| `register_break_callback(owner, duration, fn)` | `register_watcher(EVENT_BREAK, {owner, duration, fn})` |
| `remove_all_round_effects` 里 `if(had_effects)` 遍历触发 | 断回合原语成功路径末尾 `emit(EVENT_BREAK, actor, target)` |
| `cleanup_expired_effects` 里单独清 `on_round_broken` | `EventCenter::cleanup(roundCount)` 统一清理 |

语义保持：断回合**成功**（有可断效果且未免疫）才 emit，与"成功分支下结束时 emit"一致。

### 3.6 首批事件挂接点

| 事件 | 由哪个原语在成功路径末尾 emit |
| --- | --- |
| `EVENT_BREAK` | 断回合原语 |
| `EVENT_CONTROLLED` / `EVENT_ANOMALY_APPLIED` | 异常施加原语 `apply_anomaly` |
| `EVENT_DEATH` | 死亡结算 |
| `EVENT_HIT` / `EVENT_TAKE_DAMAGE` | 伤害管线命中/结算后 |
| `EVENT_ENTER_STAGE` / `EVENT_SWAP` | 登场/换宠状态 |

## 四、免疫内核（ImmunityCenter）

### 4.1 数据模型

```cpp
enum class ImmunityType {            // 枚举值增长 = 数据扩展
    BREAK,      // 免断
    DAMAGE,     // 免伤
    STAT_DROP,  // 免弱（属性弱化免疫）
    ANOMALY,    // 异常免疫（按 mask 细分，见下）
};

struct ImmunityProvider {
    int owner;
    ImmunityType type;
    int register_round;
    int duration_rounds;    // 0 = 永久
    uint64_t coverage;      // 时点 bitset（State 归一化: bit = (int)state + 1），ALL = 闭环
    uint64_t anomaly_mask;  // ANOMALY 类型专用：免疫哪些异常（36 位）；0 = 全免
    bool active;
    int  condition_id;      // -1 = 无条件; 否则查条件目录（受限枚举，不是每机制一个 struct）
    int  source_id;         // 谁授予的（revoke / 堆叠用）
};

class ImmunityCenter {
    std::unordered_map<int, std::vector<ImmunityProvider>> providers_;  // key = owner
public:
    int  grant(int owner, ImmunityType, uint64_t coverage,
               uint64_t anomaly_mask = 0, int duration = 0, int condition_id = -1);
    void revoke(int owner, int source_id);
    bool is_immune(int owner, ImmunityType, State timing, int status_id = 0) const;
    void cleanup(int roundCount);
};
```

### 4.2 查询语义

```cpp
bool ImmunityCenter::is_immune(int owner, ImmunityType t, State timing, int status_id) const {
    for (const auto& p : providers_.at(owner)) {
        if (!p.active || p.type != t || !covers(p.coverage, timing)) continue;
        if (t == ImmunityType::ANOMALY && p.anomaly_mask != 0
            && !((p.anomaly_mask >> status_id) & 1u)) continue;   // 该异常不在免疫列表
        if (p.condition_id >= 0 && !condition_passes(p.condition_id, this, owner)) continue;
        return true;
    }
    return false;
}
```

- **高低级 = 覆盖集数据**：`coverage` 全置位 = 闭环免断/魂免（任何时点不可能被断/被控）；只含部分时点 = 低级。不需要"等级"字段。
- **未保护时点可被断/被控**：那个时点 `is_immune` 返回 false，原语照常执行。天然正确，无需特殊处理。
- **按异常免疫（天生免疫xxx）用 `anomaly_mask` bitmap**：36 个异常状态（id 0~35）正好一个 `uint64_t`。魂免/全免/按具体异常免疫统一成 ANOMALY + 不同 mask：

  | 场景 | anomaly_mask |
  | --- | --- |
  | 全异常免疫 | `0`（全 36 位） |
  | 魂免（免控场） | `kControlAnomalyMask`（从异常 category 枚举派生控制类位集合） |
  | 天生免疫xxx | 对应具体 `status_id` 的位 |

  位运算 O(1)；`coverage`（41 位）+ `anomaly_mask`（36 位）共 72 位，空间可忽略。

### 4.3 两种条件语义

| 语义 | 实现 | 示例 |
| --- | --- | --- |
| **回合开始快照** | 条件写在**程序**里：`[BATTLE_ROUND_START] if hp>max/2: grant(ANOMALY, kControlAnomalyMask, coverage, 本回合)`。grant 写记录，中途查询只读记录，不重判。下回合程序重跑 → re-grant 或让旧记录过期。**无手动 cancel。** | "回合开始时体力>1/2则本回合免控" |
| **Live 实时** | provider 带 `condition_id` 指向条件目录（`hp_gt_ratio` / `has_shield` / `has_mark` / `has_anomaly`…），`is_immune` 时计算 | "有护盾时免控"（护盾中途才上） |

关键点：**"激活条件"与"覆盖范围"分开**。条件决定何时生效，覆盖决定生效期间保护哪些时点。混为一谈就会退化成"每时点重算瞬态标记"的老路（漏 cancel 就泄漏、双份真相漂移）。

### 4.4 快照的钩子 = 已有的时点 + grant 原语

用户疑虑"回合开始判定、中途才查询，要不要专门钩子"——**不需要新钩子机制**：

- BATTLE_ROUND_START 是 FSM 已有的时点，条件程序在那里跑。
- `grant_immunity` 是免疫原语，往注册表写记录。
- 中途任何时点 `is_immune` 只读记录，快照语义成立。
- 引擎没有为免断/魂免新增任何状态机钩子，它们就是普通程序。

### 4.5 集成：原语只查不问（增量委托，不重构 apply_anomaly）

```
断回合原语 break_round_effects(ctx, target) -> BreakResult:
    if is_immune(target, BREAK, currentState): return IMMUNE;
    if !has_round_effects(target): return NO_EFFECTS;      // 清除失败
    ctx->invalidate_all_round_effects(target);             // 机械无效化（内核操作）
    emit(EVENT_BREAK, actor, target);                      // 成功路径末尾
    return SUCCESS;

异常施加原语 apply_anomaly(ctx, target, status) -> ApplyAnomalyResult:
    [Step 3] if is_immune(target, ANOMALY, currentState, status_id): return TARGET_IMMUNE;
    ... 施加成功后 emit(EVENT_CONTROLLED / EVENT_ANOMALY_APPLIED)
```

职责边界（原语层位于 `include/primitives/battle_primitives.h`）：
- `is_immune()` **只回答"免疫吗"**；异常**施加逻辑**（7 步检查链、状态生命周期）作为原语集中实现。
- 免疫检查步**委托** `is_immune`；Mark ID 0 先映射成一个 Provider（永久+全时点+mask 全免），跑通后再逐个接入条件魂免、按异常免疫。
- **抗性系统（概率百分比）是另一个内核，不并入**：免疫是"能不能"，抗性是"概率多少"，语义不同。
- **原语返回结果枚举**（`BreakResult` / `ApplyAnomalyResult`），技能据此分支后续行为；谓词（is_immune/has_round_effects）保持 bool；发射即忘（emit/grant）为 void。

### 4.6 mark.h 魂免迁移

现 `Mark(0, "异常免疫")` 有两种归宿，建议先保留后统一：
- 视为"永久 + 全时点 + 无条件 + ANOMALY/mask 全免"的 Provider（等价的默认记录）。
- 或把"有无 Mark(0)"做成条件目录的一个检查项（`has_mark`），Provider 只负责时点/窗口。

按异常免疫（天生免疫xxx）直接 grant 一条 `ANOMALY + 具体 status_id 位` 的 Provider，不再需要 mark 记录。

## 五、原语与程序的关系（本设计的骨架）

```
FSM(State 循环)
  └─ 时点效果桶（程序 = 数据: [trigger, 条件, 原语序列]）
        └─ 原语 = 纯动作 + 成功路径末尾 emit
              └─ EventCenter / ImmunityCenter / 异常系统 / 伤害管线   ← 内核，被查询或被更新
```

- **原语是闭集**：扣血、治疗、能力增减、护盾获取、异常施加、断回合、加免疫、注册 watcher……增长慢、**每个值得审**。
- **程序是开集**：每条 effect_info → 一段程序（数据），增长快、**不需要逐条审**，用 schema 校验 + 黄金集兜底。
- 事件与免疫让原语保持**纯净**：原语不写补偿逻辑、不查自己是不是被免疫——发事件、查免疫都是原子动作。
- 时点覆盖（`coverage`）、激活条件、回合窗口全部是效果程序的数据字段，AI 批量生成时只需产出数据。

   - **伤害前分层（DamagePhase）**：伤害修正不是单次折叠，而是有序节点序列——伤害值在 workspace 流经各 phase，每个效果声明自己挂哪个 phase（数据），管线按序 `walk`。增伤能否击穿锁伤、锁伤能否免疫增伤，**纯粹由节点先后决定**，零两两硬编码。**已实现（2026-08-09）**：`include/effects/damage_pipeline.h` + `src/effects/damage_pipeline.cpp`——`DamagePhase{GUARD_DETECT,AMP,AMP_EXTRA,REDUCE_FLAT,REDUCE_PCT,FLOOR,CAP,BLOCK,DETECT,FINAL_CORRECT}`（2026-09-14 重排，见下） + `DamageEffectCategory{AMP,MITIGATE,BLOCK,DETECT}` + 每阶段每方桶 + `run()` 按序 walk（先攻击方后防御方）。`ElfPet::damage_suppress_mask` 按类别抑制（沧岚"挡伤失效"=置对方 mask BLOCK|DETECT，被抑制效果直接跳过）。萨瑞卡式"受高伤归零/回满"= **GUARD_DETECT** 阶段读 `resolvedDamage.final`（链首，故之后发生的增伤/保底会"穿过"它）。FSM 攻击伤害 handler 在 apply 前跑 `damage_pipeline_.run()`。
   - **减伤已迁入 REDUCE（2026-08-09）**：`applyDamageReduction` 从 `stage_simple_attack_damage` 内联移出，由 `BattleContext::install_default_damage_reduction()` 注册为 REDUCE 阶段 MITIGATE 效果（init_battle/clearAllEffects 后安装）。`stage_simple_attack_damage` 只算 base，`final=base`，减伤在管线 walk 时施加——天然可被 suppress_mask 抑制。测试覆盖：阶段序/类别抑制/归零/抑制后增伤生效/REDUCE 减伤/抑制后不减伤。
   - **减伤 vs 挡伤分家（2026-09-13，场景 031）**：`MITIGATE`(减伤/保底/锁伤) 与 `BLOCK`(挡伤归零) **必须分开**——官方口径下"使对手挡伤失效"（蚀砚之泪≥4滴）只废**归零类**（免伤/抵挡/弹伤/受高伤转化），**减伤不可被无视**（"减伤100%、点数减伤全都是不能被无视的效果"）。故新增 `DamagePhase::BLOCK`（插在 CAP 与 DETECT 之间，挡伤归零后 DETECT 的"受高伤"判定因 `final<=0` 自然不成立）+ `DamageEffectCategory::BLOCK`；4泪掩码 = `BLOCK|DETECT`。
   - **条件盔（2026-09-14，场景 050）**：`RuleTicket::condition` 让一条拦截条目自带判据，
     `RuleCenter::notify` **逐条求值——条件不满足就跳过、不消耗次数**。代表：`854`
     「令对手下1次使用的**威力高于{0}的攻击技能**无效」（天叶领域/余温之辰）——威力不够的技能、
     属性技能、以及"对手本回合没出手"都不会白白吃掉这次数。条件签名带 **`power`（面板威力
     `Skills::power`）** 与 `is_attribute_skill`；概率封属（`chance_pct<100`）复用同一字段
     （每次响应时掷，不是授予时掷一次）。
   - **次数型免伤接进管线（2026-09-13，场景 031）**：`install_default_damage_block()`（BLOCK 阶段/BLOCK 类别，双方各一条）把 RuleCenter 的 `ImmunityType::DAMAGE` 次数型免疫（"免疫下N次攻击伤害"）接进伤害结算——命中 → 整段快照归零 + `consume_immune` 扣一次。**必须走管线而非 inline 判断**：免伤属挡伤一族，须吃同一道抑制门，被压制时既不触发也不扣次数（场景 031 Q4 验证）。对应地，`apply_anomaly` 的 [3]次免/[5]魂免两个门在挡下时也调 `consume_immune`——`consume_immune` 的扫描条件与顺序与 `is_immune` 完全一致，命中窗口条时不消费、也不越过去扣后面那条次数型（否则会"窗口条挡下、次数条被扣"）。
   - **阶段序按官方口径校准（2026-09-14，场景 045）**：原 7 阶段重排为 10 阶段——
     `DamagePhase{GUARD_DETECT, AMP, AMP_EXTRA, REDUCE_FLAT, REDUCE_PCT, FLOOR, CAP, BLOCK, DETECT, FINAL_CORRECT}`。
     依据两条官方口径：时点链「**犀牛魂印—通用增伤—693增伤—保底伤害—护盾**」（从先到后），
     以及减伤区固定顺序「**点数减伤——百分比减伤——伤害锁定——伤害免疫**（不再相互穿插）」。
     - `kOrder` 是**一个可改常量**——**顺序即机制**，改一行就是改机制，不用动任何回调。
     - `GUARD_DETECT` 放链首：受高伤检测（萨瑞卡式）必须看到**未增伤**的值，之后才发生的
       增伤/保底才能"穿过"它——这就是"693 增伤乱穿犀牛"的结构成因。
     - `AMP`（通用增伤·**加法**：`damage_add_pct` 求和后一次性施加）与 `AMP_EXTRA`
       （非通用增伤·**乘法**：`damage_add_extra_mul` 逐槽连乘）分家，判据是技能文本里的"**额外**"。
     - `REDUCE_FLAT`（点数减伤：`damage_reduce_flat` 求和后从伤害里扣）与 `REDUCE_PCT`
       （百分比：加算槽求和钳 ±100 + 乘算槽连乘）分家——`(base-30)×0.5 ≠ base×0.5-30`，顺序可观测。
     - `FLOOR`（保底）在减伤**之后**、`CAP`（锁伤）**之前**：锁伤最后再拦一次。
     - **伤害抗性三种（暴击/固定/百分比）形状统一：都是乘"整段"伤害**。暴击抗性是在
       `stage_simple_attack_damage` 里 **先乘暴击系数、再乘抗性**（100 伤 → 暴击 200 → 35% 抗性
       → **130**，不是只削加成部分的 165；100% 抗性 → 0）。减伤在 `applyDamageReduction` 里
       **钳在 100%**（加算求和钳 ±100、乘算逐槽钳、结果 ≥0），超出部分不算、不会溢出或出负数。
     - `GUARD_DETECT` 有 core 的**默认回调**（`install_default_damage_guard_detect`）：把该阶段
       （链首、增伤之前）的伤害值记进 `ws.guard_detect_damage[defender]`，供「受高伤/受低伤」一族
       魂印读取（不灭地威·萨瑞卡 1217「受到超过350红伤恢复自身所有体力 / 小于350反弹50%固伤」）。
       **为什么必须由管线写**：攻击伤害时点的桶只跑当回合 mover 一侧，防守方魂印在自己不是 mover
       时根本不执行；管线每阶段双方都走。DETECT 类别 → 吃"挡伤失效"掩码。
     - ⚠️ `FLOOR`/`CAP` 目前**零注册**（保底/锁伤的具体效果待做）。实现**锁伤时必须查
       `ws.attack_credential[attacker].ignore_damage_limit`（官方 697「无视伤害限制」）**——
       该凭证写入完备却零消费，目前是死凭证。
     - ⚠️ **红伤**的护盾/护罩仍在 `deal_damage`（管线**之后**）。官方两处说法不一致（"体验服规划：
       点数减伤—百分比减伤—护盾/护罩" vs 某个算例暗示护盾在 693 增伤之前）→ **待实测后再定**。
     - 打盔（技能无效）时管线整段不跑 → 次数型减伤/免伤**天然不被消耗**（官方："打盔是不会
       消耗点数减伤，既然不消耗那自然也不会触发"）。

   - **粉伤通道（PinkDamagePipeline，2026-09-15）**：粉伤（固定/百分比）**不走红伤管线**——
     它没有攻击方/技能/克制/暴击那一套输入，也不吃红伤的点数减伤/百分比减伤/锁伤。
     共有的只有"值在一个有序阶段表里流经节点"这个形状，所以另起一条**更短的**独立管线：
     `include/effects/pink_damage_pipeline.h` + `src/effects/pink_damage_pipeline.cpp`——
     `PinkDamagePhase{RESIST, IMMUNE, REDUCE_EXTRA, AMP, PINK_TO_HOOD, PINK_TO_TRUE_IMMUNE,
     CAP, HOOD, PINK_TO_TRUE_UNHARMED, FINAL}`（抗性免减 → 免疫粉伤 → 百分比免减 →
     **粉伤提升 n%** → **粉转护罩·检测点** → **粉转真·免疫粉伤·检测点** → 上限/锁伤 →
     **护罩免减** → **粉转真·未受到粉伤·检测点** → 本次最终受到的粉伤）。
     值在 `ctx->resolvedPink`（`PinkDamageResolved`）里流经各节点。阶段序**逐格照抄**
     《赛学必修8—免疫粉伤》的流程图，与官方乘算链
     `固定/百分比伤害 ×(1−抗性免减)×(1−技能特效免减)×(1−魂印特效免减) − 护罩值` 一致
     —— 抗性在前、其他免减**乘法**连乘、**护罩最后**，
     ★ **增粉排在所有免减之后**（不是链首，位置可观测）。
     - ★ **两个粉转真是分支、不是先后**，且各自有独立阶段——「粉转真·免疫粉伤」挂在
       **护罩之前**（被免减削到 0，根本没走到护罩 → 转真后**不消耗护罩**）；
       「粉转真·未受到粉伤」挂在**护罩之后**（护罩吃完了才谈得上"没受到"），
       是给免粉补偿一族挂的检测点（读 `resolvedPink.final` / `absorbed` 判类1/类2/类3）。
     - **免粉与「挡伤」走同一条路**：`ImmunityType::PINK_DAMAGE` 的 RuleCenter 票据，
       同一个 `grant_immunity` / `is_immune` / `consume_immune`。因此**次数型免粉只挡一段**
       ——多段粉是 N 次独立结算，只消费掉票据的 1 次，其余各段照常落到本体
       （窗口型/永久型 counts=0 则每段都免）。
     - 另有「星皇之怒无视区间」横跨 免疫/免减/增粉/护罩但**不含抗性**——需要一条粉伤侧

     - **多段粉 = 一次 `deal_pink_damage` 调用 = 一段**，逐段独立结算（各自取整 / 各自扣护罩 /
       各自检测）。官方算例 `300×0.65` 是**逐段取整后相加**，而不是 `(300×4)×0.65`。
       引擎端因此没有"段计数"这种状态："调 N 次"就是"N 段"。
     - **免疫 / 抗性 100% / 效果减粉 不区分**：对"免粉补偿"一类检测而言三者等价——检测就是
       即时算一段粉、当场应用、再看**体力有没有下降**。
     - **`EVENT_TAKE_PINK_DAMAGE`**：只在**经过护罩抵消后仍有剩余结算到本体**（体力真的降了）
       时才发，`amount` = 实际扣血量。要看护罩吃掉多少（"检测体力**和护罩**是否变化"那一类）
       在 `DETECT` 阶段读 `resolvedPink.absorbed`。
     - 已落地的两个真实子句：**怒涛·沧岚 2343**「此护盾存在时自身受到的固定伤害、百分比伤害
       不超过此护盾的数值」= `CAP` 阶段——登场盾以 `ShieldBank::kSoulShieldPriority`
       （最高优先级，与别的盾叠加时**优先被消耗**）+ `source_id = 魂印 id` 登记，
       条款用 `quantity_of(source_id)` **只认自己那一笔**（读 `total()` 会让别的来源抬高上限），
       且回调**实时**读、不缓存（护盾会刷新、蚀砚之泪≥3滴会让护盾失效）；
       **箫澈 2099**「每次自身受到≥300的固定伤害、百分比伤害」= 首个 `EVENT_TAKE_PINK_DAMAGE`
       消费者，阈值天然**逐段**判定。
     - ⚠️ `AMP`/`CAP`/`DETECT` 目前零注册（增粉一族 / 锁粉一族 / 免粉补偿一族的具体效果待做）；
       **粉伤管线暂不消费 `damage_suppress_mask`**——官方"挡伤失效"枚举里**没有护罩**，
       粉伤侧的抑制口径是空白，宁可留空也不要照搬红伤语义凭空发明机制。

## 七、开放决策点

1. ~~事件投递~~ ✅ 已定：emit 只入队，FSM 在 State 桶后 drain 投递。
2. **事件载荷**：`BattleEvent` 的 payload 先最小化（actor/target + 小 payload），随需要以数据扩展，不预先设计大而全的结构。
