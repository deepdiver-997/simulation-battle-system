# 命令行客户端使用说明

本文说明如何用命令行客户端 `sim_training_cli` 联调与验证机制。

> 2026-09-17 起客户端与服务端都改成原生 socket（不再依赖 Boost.Asio），
> 协议从"单连接多对局（带 uuid 路由）"改成**单连接单对局**。
> 命令不再需要 `uuid` 参数；新增 `auto` 自动对打与事件带叙事输出。

## 1. 编译

在仓库根目录执行：

```bash
cmake -S . -B build && cmake --build build -j8
```

## 2. 启动服务端

```bash
./build/sim_server                 # 默认 127.0.0.1:4399，solo 模式
./build/sim_server --port 4599     # 换端口
./build/sim_server --host 0.0.0.0  # 对局域网开放（给玩家接入时要加）
./build/sim_server --mode pvp      # 两连接一局（撮合）
./build/sim_server --help          # 全部选项
```

⚠️ 服务端必须在**仓库根目录**运行：它按相对路径加载
`scripts/data/processed/seer_unity.sqlite` 与 `resources/<lib>/liblib_1.dylib`。

想让 FSM 打详细时点轨迹：`BATTLE_FSM_VERBOSE=1 ./build/sim_server`。

## 3. 启动客户端

```bash
./build/sim_training_cli                    # 默认连 127.0.0.1:4399
./build/sim_training_cli 127.0.0.1 4599     # 指定地址与端口
```

## 4. 命令

### 开局

| 命令 | 说明 |
|------|------|
| `init012` | 用文档预设阵容开局（双方都是 12 号精灵、不同技能组） |
| `lineup <petId> <s1..s5> [petId2 <t1..t5>]` | 自定义阵容（solo）。只给一只则双方相同 |
| `party <petId> <s1..s5>` | 提交自己这一边的阵容（pvp）。服务端落到自己座位对应的边 |
| `trait <traitId>` | 下一次 `lineup`/`party` 携带的通用特性 id |

阵容用 JSON 发给服务端（`INIT_BATTLE_JSON`），不必再手拼二进制块。
solo 用 `lineup`（一次给双方）；pvp 用 `party`（两边各提交自己那一边）。

### 跑一局 pvp

```bash
./build/sim_server --mode pvp --port 4699
# 两个终端各起一个客户端：
./build/sim_training_cli 127.0.0.1 4699     # 座位 0
./build/sim_training_cli 127.0.0.1 4699     # 座位 1
# 各自 party <petId> <s1..s5>，两边都提交后自动开局；
# 每个客户端只会被提示自己那一方（座位 0 管玩家 0，座位 1 管玩家 1）。
```

### 操作

| 命令 | 说明 |
|------|------|
| `turn <a0> <i0> <a1> <i1>` | 一次提交双方动作。`a` 取 `skill`/`pet`/`medicine` |
| `skill <robot> <idx>` | 提交单个技能操作（`idx` 0~4） |
| `pet <robot> <slot>` | 提交换宠（`slot` 0~5） |
| `medicine <robot> <idx>` | 提交药剂 |
| `auto [on\|off]` | 自动应答"等待输入"。**机制验证的主力用法** |

### 查看

| 命令 | 说明 |
|------|------|
| `sync` / `status` | 请求权威快照 |
| `full` | 完整状态转储（含效果表） |
| `step` / `run` | 单步 / 连续（单步下每推进一个时点就停一次） |
| `break <stateId>` | toggle 断点 |
| `heartbeat` | 心跳 |
| `help` / `quit` | |

## 5. 怎么读输出

### 事件带（每推进一段就打印一次）

服务端每推进一段就把这段的**每个时点**发过来，客户端逐行叙事：

```
── 事件带 seq 4→28（25 个时点）
  #11 r0 先手方技能命中时(8) hp[85/85 vs 85/85]  [EVENT_HIT a0→t1 量=0]
  #13 r0 先手方攻击伤害结算(10) hp[57/85 vs 0/85] 伤害(pending=114,resolved=114)  [EVENT_TAKE_DAMAGE a0→t1 量=85]
  #18 r0 先手方死亡结算(15) hp[57/85 vs 0/85]  [EVENT_DEATH a0→t1 量=0 槽=0]
```

一行 = 一个时点，带上双方体力、非零的能力等级、伤害管线数值，以及该时点投递的事件。
**这是验证机制的主要依据**：可以直接指着某一行说"这一步的伤害/时点不对"，
而不是只看回合首尾两张快照。

### 等待输入

```
>>> 等待输入：玩家 1（choose_pet_after_death，回合 0，时点 死后选择）
    换宠: [0]波克尔(0/85)(不可用)(在场) [1]波克尔(85/85) [2]波克尔(85/85) ...
```

服务端同时给出**合法动作集**（哪些技能能用、为什么不能用、哪些精灵可换），
所以不会出现"点了没反应却不知道原因"的情况。

`reason` 字段取值：`choose_action`（选技能/药剂/换宠）或 `choose_pet_after_death`
（必须换宠——该状态下服务端会把技能标成不可用，因为 FSM 只接受换宠）。

### 战斗结束

```
═══ 战斗结束：winner=0（回合 5，存活 [2,0]）
```

若同时看到服务端 ERROR 日志 `引擎卡死：…没有合法动作…`，说明本局是服务端**兜底**结束的、
而不是引擎自己走到结束 —— 见 `docs/01-架构与设计/网络层与服务端形状.md` 第 5.2 节。

## 6. 推荐验证流程

### 快速跑一局看整体表现

```
init012
auto on
```

观察事件带叙事是否符合预期；`auto` 会一直打到结束。

### 逐步验证某个机制

```
lineup 12 10038 10057 10001 10008 10009
auto off
turn skill 0 skill 0        # 提交一个回合
                            # 逐行看事件带，确认每个时点的判定
break 10                    # 在"攻击伤害结算"打断点
step                        # 单步推进
full                        # 该时点看完整状态
```

### 死后换宠

看到合法动作集里 `mustChoosePet: true` 时用 `pet <robot> <slot>`。
注意**被提示的那一方才是需要换宠的一方**（服务端按"谁的场上精灵倒了"判定，
不是按轮次）。

## 7. 日志格式

客户端：

- `[INFO]` 一般信息，`[SEND]` 发了什么，`[ERROR]`/`[WARN]` 参数或网络异常
- `>>>` 等待输入，`──` 事件带，`═══` 战斗结束
- `[auto]` 自动应答做了什么

服务端（`stdout`）：

- `[LEVEL] [service] …` 连接接入 / 房间分配 / 回收
- `[LEVEL] [match N] …` 某局的推进：座位、开局、**等待玩家 X 操作**、引擎卡死告警
- `[LEVEL] [session N] …` 某条连接的收发与错误
- `[LEVEL] [battle] …` 战斗逻辑明细（回合选择、伤害数字）

过滤某一局：`./build/sim_server … | grep "\[match 2\]"`。
