# 配置选择与 BP 建模（元博弈层）

整理时间：2026-09-18

说明：

- 本文补 `AI决策框架与训练思路.md` 与 `Ai训练思路2.0.md` 缺失的一层：**对战开始之前的那一层决策**（配置选择、BP、开局信息推断）。
- 前两份文档把"己方配置"当成已知常量处理。这在"对战内决策"这一层是对的，但漏掉了配置本身也是决策变量、且在对手视角下是私有信息这件事。
- 核心结论：整局对战不是单智能体 MDP，而是**双人零和不完全信息扩展式博弈**，形状接近扑克而非 Atari。配置选择必须与对战决策**分层**处理，接口是胜率。

---

## 一、问题定位：己方配置不是常量

三类信息的性质完全不同，不能用同一个框架处理：

| 信息 | 谁不知道 | 性质 | 框架 |
| --- | --- | --- | --- |
| 对手数值 / 配招 / 道具 / 特性 | 我不知道 | 隐藏信息 | POMDP / 贝叶斯信念（已有文档已覆盖） |
| **己方配置（精灵 / 配招 / 道具 / 特性 / 数值）** | **对手不知道** | **私有信息** | **不完全信息博弈（本文）** |
| BP 顺序 | 双方依次决策 | 顺序博弈 | 子博弈求解（本文） |

第二行是本文的起点。己方配置的"不确定性"不来自我不知道，而来自**对手不知道**——跟扑克底牌同构。所以它不是信念问题，是元博弈问题。

### 1.1 推论：不存在"最优配置"

在零和博弈里，"最强队"这个静态概念**不存在**，只有"给定对手配置分布下的最佳应对"。对手会针对你的配置调整，所以你最终要的不是一套配置，而是一组配置的**混合策略**（这套队打 40%、那套打 35%……）。

由此可得一条重要判断：**"不同阵容里同一个精灵配置不同（因为承担的职责不一样）"不是建模难点，正是混合策略在队伍层面的正常表现。** 不要试图把它"消除"掉，它是特征不是 bug。

---

## 二、分层架构：唯一务实的解法

### 2.1 为什么不能端到端

把"选配置"和"打对战"塞进一个网络端到端训，会卡在信用分配上：配置层的反馈信号只有"这局赢了"这一个比特，而且中间隔了几十个对战决策步，梯度根本传不到配置选择。所以必须分层，中间用**胜率**（标量，非梯度）对接。

### 2.2 三层结构

| 层 | 动作空间 | 时间尺度 | 推荐算法 |
| --- | --- | --- | --- |
| **元层**（BP + 配置选择） | 小（约 10²~10⁴ 量级序列） | 每局一次 | 离线模仿 → CFR / PSRO |
| **对战层** | 每回合 4~10 个合法操作 | 每回合 | AlphaZero / MCTS（见 `Ai训练思路2.0.md`） |
| **接口** | — | — | `winrate(我方配置, 对方配置)` |

分层的额外好处：两层可以**独立开发和验证**。对战层不需要知道 BP 的存在，元层不需要知道战斗细节，只需要一个能算胜率的黑盒。

## 三、配置泛化：两条线要分开

"测试时配置和训练时不一样"这句话里混了两种情况，处理方式完全不同，混着想会卡住。

### 3.1 己方要用新配置（泛化到未见过的自身配置）

解法是**训练时就把配置当输入，而不是当常量**：

- 策略网络条件化在全队上：`π(a | state, own_team)`，己方队伍编码为 embedding 一起喂进网络；
- 训练时**随机化己方队伍**（从配置库里采样），**绝对不要在固定几套队上训练**——那样学到的是"这套队怎么打"，不是"对战怎么打"。

这条改动成本极低（只是多一个输入分支），收益却是全局的，**建议提前做，不要等对战 RL 调好再补**。

### 3.2 对手用新配置

这才是已有文档覆盖的信念 + 泛化问题，靠 domain randomization + 对手池 / League 解决。

### 3.3 表示坑：禁止 one-hot 配置 ID

配置必须用**结构化特征**表示（属性、技能效果、数值、角色标签的组合），**不能给每个配置一个 one-hot ID**。

原因：one-hot 下未见过的配置对网络是**零信息**，泛化无从谈起，而"测试时配置和训练时不一样"恰恰是常态。

补充：如果要给 CFR 做冷启动先验，"role"（打手 / 盾 / 拦截……）这类人工标签作为**特征输入**是有用的，但不要硬编码成规则。

## 四、BP 建模

### 4.1 形状：有序序列，不是集合选择

机制事实：双方互相禁止对手 3 只 → 在剩余 9 只中选 6 只；且**选择顺序会影响部分魂印**。

因此 BP 的动作空间是**有序序列**（`ban1, ban2, ban3, pick1 … pick6`），**不能建模成"从集合里挑 6 个"**，否则那部分顺序敏感的信息直接丢失。

组合数量级：
- 若忽略顺序：`C(9,6) = 84`；
- 若完全按顺序：`P(9,6) = 60480`。

这就是为什么 BP 不能暴力枚举，必须用下面这套近似。

### 4.2 为什么 BP 用 CFR 而不是 RL

- BP 恰好是 CFR（反事实遗憾最小化）最擅长的形状：**有限深度、信息集小、本质是顺序博弈**；
- 而整局对战用 CFR 是不现实的（状态空间太大）；
- 所以天然分工：**BP 走 CFR，对战走 RL**。

CFR 需要叶子节点的效用，也就是"给定双方配置的胜率"。这个由对战层提供。训练早期可以先用一个**便宜的价值网络**近似（输入双方 12 只精灵的表示，输出胜率标量），不必真的打完整局。

### 4.3 冷启动：先离线模仿

建议先做**离线模仿**：从平台 BP 日志学一个先验策略，再拿它作为 CFR 的初始策略。比从零开始自对弈快得多。

## 五、开局信息推断（BP 界面 / 开局图标 / 场上观测）

本节针对一个具体问题：实际游戏中，可以通过**开局 buff 图标的显示情况**确定对手至少携带了哪些精灵。例如对手身上有"星皇之佑"的图标，说明对手一定带了星皇；反过来，如果**自己带了星皇却没有显示图标**，说明对手带了抑制场下 buff 的精灵。再结合 BP 界面看到的内容，可以进一步缩小范围。

**结论先说：这类推断必须内置在引擎侧，做成共用的确定性模块，不能让网络自己学。** 理由有三条（见 5.3）。

### 5.1 三类信息源

| 来源 | 时点 | 揭示内容 | 可靠性 |
| --- | --- | --- | --- |
| **BP 界面** | 开局前 | ban 名单 / pick 名单 / 顺序 | 硬证据，完全可靠 |
| **开局图标 / buff** | 首回合 | 某些精灵"必然在队"、某些"必然不在" | 正观测=硬；负观测=需谨慎（见 5.5） |
| **场上观测** | 对局中 | 属性 / 配招 / 道具 / 特性、换人时机 | 有噪声，贝叶斯更新（`Ai训练思路2.0.md` §4） |

三者是**互补约束**，要合起来用，不能各做一套。

### 5.2 前提：引擎目前缺"可见性投影层"

⚠️ **现状（已核实）**：

- 机制**已实现**：`test/scenario/scenario_021_offstage_suppression.cpp` 就是本节例子——薇尔诗 2513 抑制场下源、瀚宇星皇 903 位于背包时提供星皇之赐/之佑。相关内部真值：`ctx.block_offstage_to_onstage`、`find_pet_with_soulmark`、ROSTER 魂印语义（下场不清）、死亡监控清场域。
- 但引擎**没有观测 / 可见性层**：上述状态，以及免疫状态、boost、hp 等，全是**双方共享的内部真值**，系统没有区分"内部真值 s"与"玩家 i 的观测 o_i"。`DamageSnapshot` 是伤害计算的中间量，不是观测。
- `effect_icon` **不是**运行时图标通道：它是数据库表（`include/db/official_data_repository.h:106`），存 `pet_id / effect_id / tips / kind / args`，是魂印的**定义与展示数据源**，不是"当前显示了哪些图标"的运行时接口。

**这意味着顺序问题**：推断的前提是**存在信息缺口**，而缺口必须由观测层显式制造出来。如果训练时把内部真值直接喂给网络（哪怕只是"顺带"喂了对手背包），网络会发现"偷看对手队伍"这条捷径，学到作弊策略，上线必然崩。

所以**在实现 BP / 图标推断之前，先要补引擎的可见性投影层**（内部真值 s → 玩家 i 的观测 o_i）。这一层的产物应该是**可观测事件流**，与 FSM 结算逻辑解耦（不要把投影塞进结算路径里）。

### 5.3 为什么不能"让网络自己猜"

1. **它是逻辑蕴含，不是统计规律。** "图标在 → 一定带了"是零噪声的确定性规则。用数据拟合离散逻辑规则是浪费样本，而且会学出偶尔漏、偶尔错的近似。
2. **它是对信念支撑集的硬约束。** 若交给网络近似，网络可能给"逻辑上不可能的队伍"分配非零概率 → MCTS 会去 rollout 不可能的对手队伍 → 既浪费算力又污染价值估计。这与既有原则一致：**硬约束用过滤，不用权重**（`AI决策框架与训练思路.md:63`）。
3. **负观测是反事实推断，网络极难学。** "我带了星皇但没图标"需要推理"如果对面没有抑制源，这个图标本该出现"——要求模型对**未发生的事**建模，监督信号几乎不存在。确定性代码天然处理这类排除推理。
4. **它是开局唯一的算力杠杆。** 若 BP 未完全揭示队伍，9 选 6 有 84 种组合；推断把候选集砍到几种，MCTS 采样对手队伍的**方差骤降**。这直接缓解"开局信念太宽 → 搜索又浅又不稳、算力白费"的问题（`Ai训练思路2.0.md` §9.3）。等于**在第一回合就换来了搜索深度**。

### 5.4 分层：机制 / 投影 / 推断是三件事

| 层 | 放哪 | 职责 | 不该做什么 |
| --- | --- | --- | --- |
| 机制层 | 引擎（**已有**） | 图标该不该显示、被谁抑制、在哪个时点显示 | 不做推断 |
| 投影层 | 引擎（**待加**） | 内部真值 → 各玩家观测（制造信息缺口） | 不掺任何策略 |
| 推断层 | **不塞进引擎**：独立确定性模块，引擎侧与 agent 侧**共用同一份代码** | 观测 → 候选集 / 假设集 | 不写进 FSM 结算路径 |

推断层不放进引擎的原因：它是 **agent 的知识**，不是游戏规则。放进引擎会污染"引擎 = 规则真值"的边界，也不好单独替换和测试。但它**必须两侧共用同一份代码**，否则会出现"训练时用的推断规则 ≠ 线上推断规则"这类经典事故。

### 5.5 硬约束 vs 假设：两类推断不能一刀切

**类型 1：正观测 → 一定带了**（"看到星皇之佑图标 → 对手一定有星皇"）
- 逻辑蕴含，无噪声、无替代解释 → **硬 mask**，直接从候选队伍集里剔除不含该精灵的项。

**类型 2：负观测 → 推断存在抑制源**（"我带了星皇却没图标 → 对手带了抑制精灵"）
- 这是反事实推断，**依赖"该图标本该显示"这个前提**，而这个前提可能被别的原因破坏。**本引擎里真实存在的替代解释**（对照 `scenario_021`）：
  - 我的星皇**不在出战阵容**（源不在背包）→ 不是被抑制；
  - 抑制者**已被击杀**（U4：死亡监控清场域 → 效果恢复）→ 抑制是**动态**的，不是整局静态；
  - 我的星皇**自己首发**（源在场上 → 天然放行，U3）；
  - "印记还在但效果被抑制"（U2 注释）→ 要区分**图标可见**与**效果生效**是不是同一个可见信号。
- → 因此类型 2 应作为**假设 / 高权重软约束**加入信念，**不要直接 mask**。mask 错了就是永久性错误（对应 `Ai训练思路2.0.md` 陷阱 2"信念状态坍缩"）。

**判据一句话：能确定是逻辑蕴含的才 mask；存在其它解释的一律建假设。**

### 5.6 可测试性

推断规则特别适合写成 scenario 测试（`test/scenario/`）。建议新增一类场景：给定（BP 信息 + 开局图标 + 己方配置）→ 断言候选集 / 假设集。这样规则成为**可回归的资产**，而不是埋在网络里的一团玄学。

## 六、落地顺序

按依赖排列，每步都能独立验证：

1. 固定队伍 + 已知对手，跑通对战 RL（验证 pipeline）；
2. **己方队伍随机化 + 队伍条件输入**（验证配置泛化）——成本最低、收益最大，**建议提前**；
3. 对手队伍随机化 + 隐式信念（公开历史编码）；
4. 显式队伍预测辅助头（auxiliary loss）；
5. BP 单独建模（离线模仿 → CFR），接口是胜率；
6. 元层与对战层接通，self-play 微调。

关键依赖：
- **第 5 步依赖第 2 步**：BP 层要评估"给定双方配置的胜率"，如果对战层只会打一套固定队，这个接口是空的；
- **图标推断依赖引擎的可见性投影层**（§5.2），不是可以直接开工的独立任务。

## 七、待确认 spec 清单

以下几条决定后续所有模块的形状，建议优先确认并写死：

1. **BP 界面到底展示什么？** 若已展示对手最终的 6 只 → "猜对手带了哪些精灵"退化为"猜配置（配招/道具/特性）"；若只展示 ban 名单 → 队伍推断才是主要任务。**这一条影响最大。**
2. **BP 顺序如何影响魂印？** 需要具体机制清单（哪些魂印顺序敏感、以什么方式影响），否则 §4.1 的有序序列建模无从验证。
3. **图标的可见性规则**：哪些效果会显示图标？"图标可见"与"效果生效"是否解耦（U2 提示可能解耦）？抑制关系是否递归（抑制者本身被其他效果抑制）？
4. **观测粒度**：观测层输出给 AI 的是"图标列表"还是"结构化效果事件"？前者贴近真实 UI，后者对模型更好用，需要定。
5. **BP 是不是引擎职责？** 目前引擎**完全未实现** BP（已核实：无 ban / draft / 选人逻辑）。是放进引擎，还是由平台侧实现、只把结果交给训练侧，需要定。
