# 场景化对战测试说明（test/scenario）

场景化对战测试是**引擎功能验证**的第一道防线：手动构造精灵/数值/魂印，走真实
`BattleFsm`，用断言逐时点核对效果是否符合预期。每个场景一个独立二进制，互不耦合，
新增一个场景只是放一个 `.cpp` 文件 —— **不需要改 CMake**。

---

## 1. 运行

从**项目根目录**运行（`PetFactory::initialize_runtime_data()` 用相对路径初始化 DB）：

```bash
cmake -B build && cmake --build build -j8
./build/sim_scenario_001_conditional_first_move    # 单场景
./build/sim_scenario_022_skill_replace_pre_selected
```

所有场景可批量跑（每个退出码 0 = 通过）：

```bash
for b in build/sim_scenario_*; do [[ "$b" != *smoke* ]] && { "$b" >/dev/null 2>&1 && echo "PASS $b" || echo "FAIL $b"; }; done
```

> 插件（`moves_lib` / `soul_lib`）改动后需**确保重建**——增量构建可能漏掉插件。

---

## 2. 测试框架：`scenario_harness.h`

header-only，供每个场景复用。核心组件：

| 组件 | 作用 |
|------|------|
| `make_pet(id, name, {5技能id}, speed, atk, hp, soul_mark)` | 手动构造精灵；元素类型**必须用 0**（类型 1 相互克制=0 会打出 0 伤害） |
| `make_party(pet)` | 6 格占位队伍（同宠重复） |
| `ScenarioBattle({party0},{party1})` | 持有 `BattleContext` + `BattleFsm` + 最小控制块 |
| `start()` | 驱动到 `CHOOSE` 等输入 |
| `submit_operation(player, ActionType, index)` | 提交操作（走 `m_buffer` 路径触发 `on_selected` 注册先制） |
| `drive()` | 跑完整个回合到下一输入 / FINISHED |
| `step()` / `step_until(State)` / `step_past(State)` | 单步、定位时点（`debug_step_mode`） |
| `ctx()` / `pet()` / `dump()` | 取上下文 / 宠物 / 全量 JSON（`getFullStateJson`） |

技能只按 `Skills(id)` 从 DB 加载**静态数据**（唯一 DB 触点）；技能效果本体靠
`effect_unit_parser` 组合语法或插件。因此场景既验证引擎执行链，也验证解析/插件接线。

### ⚠️ 默认关闭暴击（`make_pet` 里清零 `critical_strike_rate`）

引擎已按官方口径接入暴击：`moves.crit_rate` = **分母 16 的分子**，**`0` = 0/16 = 永不必暴**
（不是"基础 1/16"）。DB 里仍有约 200 条 `crit_rate>0` 的技能（如苍炎坠 8/16 = 50%），
它们会打出 2 倍伤害，而 `std::rand()` 未播种（序列会被每次调用移位）
——既有的精确值/紧区间伤害断言会因此随机失败。

所以 `make_pet` **默认把所有技能的暴击率清零**。注意暴击率为 0 时判定**短路、不消耗 `rand()`**，
默认档与"未接入暴击"时代**字节级一致**（这也是加暴击时既有场景不受扰的原因）。

要验暴击的场景显式打开：

```cpp
scenario::set_crit_sixteenths(battle.ctx().getPet(0), 16);   // 16/16 = 必定暴击（8 = 50%）
```

同理，**测精确伤害时不要用自带附加效果的技能**（如 37218 烬灭神咒剑带 1287 吸取强化，
会把被测的能力等级搬走）——挑 `side_effect` 为空的干净技能（场景 040 的 C3 踩过）。

### ⚠️ 回合中停泊不可达（`step_past(State::X)` 停不住，k-prod-3 2026-10-07）

"submit 后对局不结束"的对局里，`submit_operation` 内部 run 会**一次跑完整回合**；
改用 `debug_step` 单步时 `StubControlBlock::wait_for_input` 为空，need_input 忙转
会让 while 永转（K171 场景初版死循环 5 分钟 CPU）。**回合中途停泊在场景 harness
抽象下不可达**，别跟 step_past 死磕。正确姿势（2880/221 同款）：

- enter 节点的票在 `b.start()` 停泊点已挂——start 后直铺断言即可；
- 跨回合推进用 `both_act`/`drive()`；
- ROUND_START 节点的票若要在 R1 断言，实现侧补一个 enter 节点首挂（行为等价，
  K171 即此形态），不要试图"停在一回合中间"。

## 4. 命名约定与新增场景

### 命名：`scenario_<三位序号>_<特性后缀>.cpp`

- **序号**：三位十进制、递增（`001`…`999`），保证唯一与稳定排序。
- **后缀**：小写 + 下划线的英文特性名，自文档化（如 `selfdestruct_legacy`）。
- **二进制**：`sim_<文件名>`（如 `sim_scenario_023_selfdestruct_legacy`）。

序号为历史编年（谁先写谁靠前），**不是**主题分区；新场景取当前最大序号 +1。
如需让同类场景相邻，用文档归类而非重排文件。

### CMake 自动发现（无需改 CMakeLists）

```cmake
file(GLOB SCENARIO_SOURCES CONFIGURE_DEPENDS
    ${CMAKE_CURRENT_SOURCE_DIR}/test/scenario/scenario_*.cpp)
list(SORT SCENARIO_SOURCES)
foreach(scenario_src IN LISTS SCENARIO_SOURCES)
    get_filename_component(scenario_name "${scenario_src}" NAME_WE)
    add_executable(sim_${scenario_name} "${scenario_src}")
    target_include_directories(sim_${scenario_name} PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/include)
    target_link_libraries(sim_${scenario_name} PRIVATE sim_core)
endforeach()
```

`CONFIGURE_DEPENDS` 会在目录内容变化时自动重跑 configure，新增文件无需手动触发。

### 新增一个场景的清单

1. 命名：`test/scenario/scenario_024_<特性>.cpp`。
2. 顶部注释写清：**被测效果 / 对照组设计 / 断言点**（参照现有场景风格）。
3. 复用 `scenario_harness.h` 构造精灵并驱动 FSM，`main()` 内 `assert` + 打印 PASS。
4. 在本表（第 3 节）登记一行，并在第 4 节末的"覆盖能力域"补归类。
5. 从项目根重新 `cmake --build build -j8`（GLOB 自动发现），构建并运行确认 `EXIT 0`。
