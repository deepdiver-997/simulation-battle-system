> 状态：**试点期**（S6，2026-11-03）。已写 01/02 两章样章；铺量与否待试点结论裁决。
> 本文是全书唯一规范源：写新章前先读完本文，写的每一条断言都要能回答
> 「源在哪」。

## 一、这套百科是写给谁的

两类读者，一视同仁：

1. **社区新人 PVP 上手**。讲「为什么 693 增伤能打穿犀牛」，不讲「犀牛很强需要注意」。
   每个结论给出可复现的数字链条，读者拿同样的面板能算出同样的数。
2. **AI 讲解员（RAG 语料）**。语言模型讲解员对战模型有可解释性优势——对战模型会玩但
   讲不出为什么。讲解员的每句话都要能挂上出处，否则幻觉没法审计。**引注密度就是
   这份语料的公信力本身。**

定位纪律：本百科是**引注式重组**，不是从零生成。库内已有的一手语料
（引擎源码长注释、场景断言、官方原文抓取、K 系文件头记档、协议文档）是素材；
百科做的是把这些素材按「读者问题」重新组织并**逐句挂源**。

## 二、引注铁律

### 2.1 四类合法源

每个**机制断言句**必须行内挂以下四类之一的源标记：

| 类别 | 格式 | 用途 |
|---|---|---|
| 引擎源码 | 〔源: include/effects/damage_pipeline.h:44〕 | 实现口径（引擎"是什么样"） |
| 场景断言 | 〔源: 场景049 R2 断言〕 | 实测口径（引擎"被证明是这样"） |
| 官方原文 | 〔源: 官方原文 L345〕 | 官方口径（官方"说它应该是什么样"）；L 编号 = `reference/scrape/out/all_posts_final.jsonl` 行号〔源: docs_local/docs/05-任务清单/待做-变威力与增减伤时点.md 头注〕 |
| 库内文档 | 〔源: 速查§五〕〔源: 协议文档§22.1〕〔源: K1 文件头〕 | 二手但已审计的库内结论 |

- L 编号溯源工具：`reference/scrape/out/all_posts_final.jsonl`（每行一个 B 站 opus 专栏，
  含「赛学必修 1–16 全 16 篇 + 机制解析全目录 152 条」）〔源: docs_local/docs/05-任务清单/待做-变威力与增减伤时点.md 头注〕。
- 引擎源码引用**必须带行号**，行号以写作当时的工作区为准（文件头若有日期更佳）。
- 库内文档引用到节（§）级；K 系记档引用到「文件头第 N 条」级。

### 2.2 密度要求

- **同类断言至少一处源**：一句话一个机制结论，句尾必须有色。
- **关键争议口径多处源**：官方与引擎可能不一致的地方（如护盾在管线内还是管线外），
  至少两处独立源并列，并按 §五 勘误流程记录裁决状态。
- **允许的例外**：纯粹的行文衔接（「接下来看第二个阶段」）不需要源。
  判据：删掉源标记后这句话是否变成「无法审计的主张」——是则必须有源。

### 2.3 数值禁止凭记忆

**所有数值**（阈值/百分比/码表/阶段序/回合数/概率）写前必须现查，三件套：

1. **sqlite3 查 DB**（effect_des / effect_icon / moves / monster 表——官方文本与参数）；
2. **读场景断言源码**（`test/scenario/scenario_*.cpp`——引擎实测值）；
3. **读 registry.json**（`build/registry.json` 的 anomalies/moves/soul 码表——dump 权威）。

查不到的不写。宁可留行内待验证标记（格式见 §2.4 示例块），也不写一个凭印象的数。
（实证教训：S5 调研已记档「DB 行数会漂移——106/110/133 三宏 K15 时有行、现库 0 行，
引用旧调研数字前必须重 dump」〔源: 夜跑晨报-2026-10-29-a02-orch §三〕。）

### 2.4 无源推论

允许写，但必须：

1. 行内标待验证标记——字面量 = ⚠ + 「待验证」四字连写，写在断言句尾
   （机校按此字面量计数，故本规范行文拆写；S27 注）；
2. 汇总到**章末「待验证清单」**，每条给：主张、缺什么证据、建议的验证路径
   （场景断言 / 实盘对拍 / 官方文本补查）。

待验证清单是纠偏的抓手：审读者只需扫清单，不用通读全文。
试点期的核心指标就是「每章待验证条数 / 总断言数」——见 §七。

## 三、机校清单（章末固定节）

每章末尾列「本章哪些断言可被脚本自动校验」，三类已知的校验通道：

| 断言类别 | 校验方式 | 现状 |
|---|---|---|
| 效果 id 存在性 | sqlite3 查 effect_des/effect_icon，或 grep registry.json | 可立即自动化 |
| 场景号是否真绿 | 读 gate 历史 / 跑 `sh build.sh`（回归循环） | 可自动化（注意 60s 单场景超时〔源: 速查§五〕） |
| anomalies 码对齐 | registry.json anomalies vs abnormal-types.h 枚举逐条 diff | 可立即自动化 |
| 行号引用有效性 | 解析「〔源: 路径:行〕」标记 → 检查文件该行是否含关键词 | 可自动化（行号漂移告警，不阻断） |
| 官方原文 L 号存在性 | 检查 all_posts_final.jsonl 该行非空 | 可立即自动化 |

机校清单的意义：铺量之前先有校验，铺量之后引注才不会烂掉。
每章的机校清单要写到「脚本作者不需要读正文就能实现」的精度（列出：标记类型、
被校验对象、期望值来源）。

## 四、写作范式（两章样章已实证）

- **每阶段/每机制四件套**：谁注册（引擎落点）→ 读到什么值（数据流）→
  实战案例（场景断言的真实数值演算）→ 源引注。
- **贯穿案例**：一章至少一个跨小节的完整案例（如「693 乱穿犀牛」贯穿 GUARD_DETECT
  与 AMP_EXTRA 两阶段），用场景断言里的真实数字演算，不编造面板。
- **对照表**：官方口径 vs 引擎现状两列并排，差距显式写，不用「基本一致」糊弄
  （范式出处：待做-变威力 §3.7 的差距表〔源: docs_local/docs/05-任务清单/待做-变威力与增减伤时点.md §3.7〕）。
- 篇幅：**每章 150–300 行为宜**。试点重质不重量；两章样章实测 338/319 行
  （贯穿案例的数值演算与机校清单不删减——若铺量时普遍超 300，拆章而非压缩引注）。

## 五、勘误流程（沿用晨报文化）

1. **正文不写死「永远正确」**：口径冲突处并列记录双方 + 标注裁决来源（谁、何时、依据什么拍的板）。
   范式：协议文档对「2504 九维」旧结论直接写「待办作废」并给新解〔源: 协议文档§22.1〕。
2. **勘误追加不抹改**：错的内容可以划掉（~~删除线~~）或标注「作废」，但不删除——
   证据链要能回放。范式：晨报 10-30 的「勘误（2026-10-31，用户指认后全链重查）」整节
   追加在文末，保留原错误表述并逐条指认〔源: 夜跑晨报-2026-10-30-a03-orch 勘误节〕。
3. **口径勘误即时落板**：发现旧记录过时（如「soul=335 是旧基线」），当天在后续文档
   标注勘误，不留双口径并存而不注〔源: 夜跑晨报-2026-10-29-a02-orch §二〕。
4. 百科章内勘误：在对应断言后追加「（勘误 2026-XX-XX：…）」，并同步到章末待验证清单
   的「已裁决」段；重大口径变更在本文 §六 目录表登记。
