# 开工：额外行动（+ 空元之诗线）

> 建档 2026-09-18。**给新会话的自包含开工文档**——读完本文 + 下面"阅读清单"即可动手。
> 所属机制线：空元行者 4586（消逝线/`agents/vanish` worktree 的自然延续；见 `docs_local/agents/README.md`）。

## 一、目标

把**额外行动**做成通用机制，并用它落地空元行者的「空元之诗」线（之铭①~④ 的时点口径顺带拍板）。

## 二、官方口径（数据库原文，别再考古）

### 2.1 额外行动的定义（`effect_des` 331）

> 「精灵的行动结束之后，可以根据效果，进行一次追加的行动，**追加的行动在未声明的场合下不为技能，
> 故而没有威力、类型等技能属性**」

要点：
- 时点 = **行动结束之后**（本引擎 `BATTLE_*_AFTER_ACTION_END` 之后 → `BATTLE_*_EXTRA_ACTION`，见 §三）。
- 默认**不是技能**：没有威力/类型/PP，不跑命中与伤害管线，除非效果**声明**了内容。

### 2.2 与"战斗阶段结束"的关系（`effect_des` 317）

> 「一回合内，当双方的**行动、额外行动均结束之后**，战斗阶段结束，根据双方的行动顺序依次触发
> 战斗阶段结束时的效果；若先手方行动结束之后存在任意一方死亡，则计为战斗阶段中断，
> 不会触发战斗阶段结束效果」

→ 额外行动必须排在"战斗阶段结束"（本引擎 = `BATTLE_ROUND_END`，见 §三）**之前**。

### 2.3 空元之诗（空元行者 4586，`effect_icon` 1791 + `effect_des` 240）

> 空元之诗：空元行者技能中的空元之诗效果**不因原本的行动而触发**，每次行动结束后，
> 若本回合所选技能的空元之诗效果生效且条件满足，空元行者会**抹除一篇空妄诗章**，
> 抹除成功后进行**一次额外行动触发空元之诗效果**

> 空妄诗章（`effect_des` 240）：…会抹除一篇空妄诗章以进行一次额外行动执行空元之诗效果，
> **最多累计 12 篇，下场保留**

之诗子效果 = `effect_info` **2086~2090**（渍/镀/柱/烙/均），已挂在 4586 各技能的
`side_effect` 里（例：阅世 36998 = `[1808, 872, 2086]`）。

空元之渎（同一 `effect_icon`）："…之后触发空元之诗效果**不再抹除空妄诗章且不受其限制**、
每回合结束后减少 200 点体力上限"（之渎本体已落地，见交接文档"消逝批 1"）。

### 2.4 同族证据（说明这是通用机制，不是空元专属）

| 来源 | 原文关键句 |
|---|---|
| 星皇之怒（`effect_info` 1094~1098） | "技能结束后对手体力值高于 0，则 50% **进行一次额外行动以触发星皇之怒**" |
| 武心婵 2115 | "若其他技能均已崩溃且对手存活则**额外进行一次行动以发起最终指令**：自身消耗全部体力并消逝…" |
| `effect_info` 2154 / `effect_des` 267（德莱赫默） | "令德莱赫默进行一次额外行动"；"克雷弗德在场时…会自动于克雷弗德选择技能且无法行动时进行额外行动" |
| `effect_info` 2284 | "…每有 1 种异常状态未触发自身下{0}次行动结束后进行额外行动以触发咒骸魂契：附加{1}点所剥夺系别的伤害" |

⚠️ 星皇之怒本体**用户已明确往后推**（"要先建立其它效果才方便比对插入位置"，见交接文档待做项 5）——
本会话**不要**顺手做它，只要保证机制形状能容纳它（额外行动可以携带"一次攻击"这类声明内容）。

## 四、要拍板的设计问题（建议按这个顺序定）

1. **payload 形态**：额外行动"声明的内容"怎么表达？
   候选：(a) `ctx->extra_action_payload[owner]` 存 `{effect_id, args}` 列表；
   (b) 复用效果桶（在 `*_EXTRA_ACTION` 状态注册效果 → 就是"声明内容"），
   并由 `ws.extra_action_pending[owner]` 控制"这次要不要走额外行动"。
   **倾向 (b)**：与既有"时点桶 = 效果"的模型一致，插件写法统一，且星皇之怒那种
   "额外行动里打一次攻击"也能靠注册更多节点表达。
2. **是否重跑技能的命中/伤害**：§2.1 说默认不是技能 → **不重跑**。
   之诗的额外行动只"执行空元之诗效果"（= 跑那几个单元），不重新命中/不重新打伤害。
   需要攻击时必须由**声明方**显式注册攻击类节点（星皇之怒将来走这条）。
3. **额外行动的"子时点"要不要细分**（如额外行动开始/结束）？先只用一个状态 +
   桶内顺序；若同族需要"额外行动结束时"，再加状态（枚举是数据扩展，但会动
   `kLinearStateOrder` 与 FSM 映射，属于结构性改动，谨慎）。
4. **之铭①~④ 是否也只在额外行动生效** → **否（2026-09-18 定）**。之铭照各自时点，
   之诗（2086~2090）才进额外行动。依据两条：
   - 官方 `effect_icon` 1791 的 tips 是**两条独立 bullet**：【空元之铭】列 5 铭文
     （仐/叵/乂/卌/卪，**1~5 号位各一条**），【空元之诗】单独说"空元行者技能中的
     **空元之诗效果**不因原本的行动而触发"——作用域写明是"空元之诗效果"，不含铭文。
   - 机制上不可能：仐是"先制+1"（先手权结算期）、乂是"回合开始时"、叵是"命中时"、
     卌是"使用后"、卪是"击败后"；额外行动**没有技能**（effect_des 331），也就没有
     命中/使用/先制可言。卪 现在按击败时点结算（场景 074）是对的，不用动。
   → **机制只需服务之诗**，之铭另做。
5. **诗章存哪** → **`pet.soulmark_storage`（2026-09-18 更正；原建议写反了）**。
   代码里早已成文这条规矩（`battleContext.h` 的 `plugin_storage` 注释）：
   > `plugin_storage` = 给插件放"跨效果/跨时点的**战斗内标志**"（接线是否已安装、掷点结果）；
   > **pet 级状态请用 `ElfPet::soulmark_storage`（下场保留）/ `on_stage_storage`（本场上场）**。

   诗章 = pet 私有 + 下场保留 → 按规矩进 `soulmark_storage`；接线旗标（`armed_flag`、
   ±10% 管线条目只装一次）留在 `plugin_storage`（它们确实是战斗级共享标志）。
   - 原建议的**理由也是错的**："同一批 pet 打第二局会把进度带过去"那件事的根因是
     **进度被写进 `Skills`**（core 对象被插件改写），见交接文档 445/477 行——与
     `soulmark_storage` 无关。
   - ⚠️ **曾误判为"前置阻塞"，已查证为非阻塞**：顾虑是"唯一清它的 `clearAllEffects()`
     生产从未调用 → pet 级状态跨局泄漏"。**实际不成立**——生产路径**每局都新建
     `SeerRobot` + `BattleContext`**（`src/server/room.cpp:129-137` 的
     `SeerRobotFactory::create_robot` 建队后 `fresh.reset(new BattleContext(...))`），且 `seerRobot` 是
     **值成员**（pet 被拷进 ctx）→ 写全落在 ctx 的副本上，源 party 永不被改，
     pet 存储天然"不跨战斗"。**所以"诗章落 pet"安全，无需前置改造。**
   - 残留（**不在本线**）：复用**同一个 context** 的那些路径（测试；`battleContext.h`
     自记训练模式 `pet.levels` 同族问题）下 `clearAllEffects()` 是唯一重置点而 `src/`
     里无人调用，且它不清 `pet.levels`。要治的是"context 复用/重开局"这个更大的口子，
     单开一条，别混进之诗线。
   - 实现落点：`KongYuanState` 挂**魂印宿主 pet** 的 `soulmark_storage[2175]`；
     死亡拦截器里宿主 hp 已 <=0（`find_pet_with_soulmark` 的 hp>0 过滤挡掉）→ 用
     `kongyuan_state_at(owner, slot)` 按槽取。
6. **之渎交互**：之渎触发后 "不再抹除诗章且不受其限制" → 额外行动照常进行但**不消耗**诗章，

   属性伤害是**技能伤害**（不是追加伤害），**有系别**（固定/百分比/真实都"不存在系别概念"），
   数值 = **声明点数 × 克制倍数**（不涉及攻防值）；用户 2026-09-18 口径：
   **"只吃克制关系，最后以红伤形式结算"**。
   落地：新原语 `deal_attribute_damage(ctx, target, points, element[2], actor)`
   （`primitives/battle_primitives.h` + CoreApi 同名槽**追加在末尾**）。
   **吃哪些修正**（用户 2026-09-18 两轮口径）：
   ① "只吃**克制关系**" + "会受到**锁伤**修正的影响，但是**常规挡伤**不会触发，只有像岚那种
      **非本系抵挡**的挡伤才可以"；
   ② "**不会被护盾/护罩抵挡**" + "如果属性技能带有**穿透限伤**的凭证也是可以无视的"。
   → 落成：
     · 只跑伤害管线的**子集** `CAP`(锁伤) + `BLOCK`(挡伤阶段)（`DamagePipeline::run` 为此加了
       `phase_mask`；增伤/非通用增伤/各类减伤/保底/DETECT 全部排除）；
     · 锁伤生效，**带 697 穿透限伤凭证时连锁伤一起无视**（把 CAP 也踢出子集）；

     · **系别条件性抵挡**（岚"免疫非本系技能伤害"）将来作为**插件自己的 BLOCK 条目**照常被走到，
       按 `DamageSnapshot::attribute_element`（本笔声明的系别）自行判；
     · 落血用新增的 **`DamageKind::ATTRIBUTE`** → **护盾不吸收**（护罩在粉伤管线，红伤本不经过）；
       快照**保存/恢复**（属性伤害可能打断一次在途攻击）。
   **穿透凭证的适用面 → 改由 RuleCenter 的"两个门"承载**（用户 2026-09-18 口径，同一轮）：

## 四bis、之铭的建模口径（用户 2026-09-18）

> 原话大意：五条铭文都可以看作**单独的技能效果**，只不过要在**游戏开始时依次绑定到
> 五个技能槽的技能内部相应时点**（如"先制+1"追加到先手权期间）。这种**动态效果绑定**
> 很常见——**宝石效果就是这么绑的**（设计技能时不可能知道要绑什么宝石）。

- **认同**"按槽绑定时点"这个模型，且它已经是本引擎的idiom：
  `Skills::selection_effects_`（选择期效果统一注册到 MOVE_RIGHT 桶）+
  `roundChoice[owner][1]` 槽位门 + `ignore_pp[owner]` 这类**外层信号**。
- **但不需要新建"往 `Skills` 里追加绑定"的机制**：五条铭文各自落在语义正确的既有扩展点上，
  用"本回合所选槽位 == N"做门（**卪 的现成模式**，见 `kongyuan_used_bound_slot`）：
  | 铭文 | 槽 | 落点 |
  |---|---|---|
  | 仐 | 1 | MOVE_RIGHT 加 `ws.preemptive_level`（`effect_apply_base_priority` 同款）+ 攻击凭证（无视能力提升/下降） |
  | 叵 | 2 | `ignore_pp[owner]`（2260 已这么用，在 `query_usage` 里消费）+ ON_SKILL_HIT 的 `pp_reduce` |
  | 乂 | 3 | ROUND_START 节点清自身异常 |
  | 卌 | 4 | AFTER_ACTION 吸体 + 管线条目（减对手下次攻击伤害） |
  | 卪 | 5 | ✅ 已实现（击败时点，场景 074） |
  关键在于：**引擎已为"技能内部判定需要外层信号"这件事提供过槽**（`ignore_pp` 被
  `Skills::query_usage` 消费；`preemptive_level` 在选择期累加）——所以"绑进技能"的
  观察效果已经拿得到，不必真的改写技能对象。
- ⚠️ **真要改写 `Skills` 时的两条红线**：
  ① 加成员会引出 072 的**依赖布局 UB**（历史实测）；往**已有的** vector 成员里追加
     （如 `add_effect_node`）不改 `sizeof(Skills)`，不受此限；
  ② 魂印每登场/每回合会重注册 → 追加型绑定**必须有"已绑过"守卫**，否则重复追加。
  所以只在"某条铭文必须坐在**技能自身分支解析内部**"时才考虑追加路线；现在 5 条都不需要。
- **宝石那种"任意效果绑到任意技能任意时点"若要通用化**：正确落点是
  **按槽索引的绑定表（存 pet，随槽位走）**，不是 `Skills` 成员——槽位本就是全引擎的
  全局身份（见 `battleContext.h` 关于"为什么不压缩数组"的注释）。**单开一条，别混进之诗线。**

## 六、顺带议题（用户 2026-09-18 提的"管线黑箱"教训）

> 原话大意：管线以前对外是黑箱，但很多效果要读各阶段的数值，**这种"导出显示视图"很重要**。

- 已有先例：`ws.raw_attack_damage`（裸伤台账，唯一写入点 = 变威力重算之后、管线之前）；
  `ws.guard_detect_damage`（犀牛链首快照）；`ws.last_heal_amount`。
- 议题：是否把"各阶段的值"系统化成一组**具名只读视图**（而不是让效果各自注册探针）？
  倾向：**具名 + 唯一写入点 + 场景锁定**，一次加一个（像 raw_attack_damage 那样），
  不要暴露整个可变 `resolvedDamage`（谁都能改 = 时序灾难）。
- **结论（2026-09-18）：做，但按需增量做，不一次性铺开；且这件事一半已经做完了。**
  `battleWorkspace.h` 里已有一整套**视图层**，只是没被系统化命名：`battle_attrs`、
  `view_levels`、`eff_*_resist_pct`、`skill_power_view`、`combo_view`、
  `skill_element_view`、`skill_type_view`、`restraint_view`、`no_weakness`、
  `skill_element_grant`，加上三个台账。`getFullStateJson` 也**已经在 dump**
  `resolved`(final/isCrit/isTrueDamage)/`pending`/时点桶。→ 缺的不是新机制，是**读契约**。
  按性价比排：
  1. **先立规矩不加字段**：把 `raw_attack_damage` 那套注释体裁定成规范
     （具名 + 唯一写入点 + 场景锁定，"挪动写入点 = 改机制定义"），一次加一个。
  2. **绝不做**：把可变 `resolvedDamage` 暴露给效果随便改。
  3. **便宜的高价值一步**：把具名视图加进 `getFullStateJson` 的 debug 段——痛点
     "读不到"而 dump 通道已在，不用新 API、也不给效果开写权限。**单开一条小任务。**
  4. **本会话没做**：额外行动**不需要**读管线中间量（不重跑伤害），故按"只做必需的那个"
     一个都没加。唯一的新读取需求在第 4 步（2089"此技能每剩余1点PP"/2090"吸取对手
     第五技能剩余PP"）——读**本回合所选技能**的 PP，属既有能力，同样不需要新视图。
