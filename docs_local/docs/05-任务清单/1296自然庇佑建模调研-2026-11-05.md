### 1.5 “进入自然庇佑”到底做什么：证据分级

**A级——当前官方库直接证明**：N 回合窗口、受到攻击触发、P% 概率、boss 有效；不包含延迟到下回合、模式转换、计数触发或回血数值。Q1 只能证明这部分。

**B级——原作者的数据提取说明，尚非对战实测**：摸鱼的橙汁在 2021-03-14 的[《赛尔号特殊技能效果整合》](https://www.bilibili.com/read/cv10275188/)明确把“自然庇护”对应到 1296、两个参数，并说明触发后按 50%/30%/20% 三档恢复 200/300/400 体力，死亡后不恢复；作者同时声明资料来自图鉴数据提取，可能与实战不同。2026-11-05 检索返回了对应正文；直接打开页面无可读正文，故记录此访问限制，不伪称获得官方战斗录像或完整网页快照。

**研究推论**：优先把该名称理解为受击后的随机回血动作标签；目前没有证据证明它是可被异常免疫、净化、转移的独立状态，也没有依据添加下回合 pending。三档数据可作为实现候选契约，进入正式验收前仍须保留出处等级并完成下表边界裁定。

## 四、建模方案：按百科七模式与 Q0—Q7 决策

### 4.1 先定问题，再走树

推荐的候选契约是 **“N 回合受击资格窗 → 每次合格事件先判 P% → 成功后选三档治疗 → 当次消费完毕”**。这是已有回合窗中的事件响应；不把“窗口跨回合”混同于“结果推迟到下回合”。七模式的分类依据见百科原表。〔源: docs_local/docs/10-游戏百科/10-台账字段与执行结果.md:286-296〕

下表把运行逻辑和审计两个子问题分别走树；Q1 已可落点，后续问题用于检查是否真有额外存储需求，不是假装所有 Q 都必须回答“是”。

| 决策点 | 本单回答 | 落点 / 约束 |
|---|---|---|
| Q0 一笔伤害内部的值？ | 否；候选治疗量不依赖伤害大小 | 不抄 raw/final/guard_detect 当治疗量；伤害是否发生由事件判 |
| Q1 与事件同时发生？ | 候选为是；受击后恢复 | 模式 3：事件 `target/actor/damage_kind/amount/state`；若实测延迟再转模式 5 |
| Q2 本回合全局口径？ | 治疗实际值是；窗与概率不是全局槽 | 复用原语写的 `ws.last_heal_amount`；不新增 `ws.nature_blessing` |
| Q3 跨回合私有账？ | 窗要跨回合，但生命周期已有注册通道；审计/订阅句柄是私有账 | 窗交 EventCenter/ContinuousEffect；私有审计用 plugin_storage，禁止另造脱离注册表的永久 end 账本 |
| Q4 跨换宠？ | 官方模板未说明；须裁定 | 默认候选绑施放宠、ON_STAGE；若证实绑定己方改 TEAM。宠级数据只按实际保留需求选双槽，不凭“状态”一词永久保存 |
| Q5 为场景观察而写？ | 是 | 模式 2：掷前申报外层 P、内层分布；执行后记录所选量、实际量、次数与拒绝原因 |
| Q6 需要上回合状态？ | 否 | 不建 prev_round / pending_next；事件结束无待兑现债务 |
| Q7 表和事件皆无且是通用判据？ | 当前未满足 | 不申请新 ws 字段/异常枚举；只有实测要求且现有检测面确实不可表达才开内核单 |

### 4.3 推荐方案的实现契约草图（供立单，不是本次实现）

**A. 注册与生命周期。** 新增单一 moves 插件 `j_nature_blessing.cpp`，布局 `[owner,target,N,P]`，注册技能效果 1296。两参来自 DB，不写死 N=3/P=100；显式 0% 表示关闭。N<=0 不建立有效窗，参数越界按现有解包纪律报错。

起点 `start=round_effect_start_round(owner,N,InRounds)`，有效区间 `[start,start+N)`；注册期保留宿主身份/epoch。在所选的“刷新不叠加”候选契约下，重用技能须注销旧 watcher 并更新 N/P，不能只更新到期戳却继续捕获旧 P。EventCenter 有注册句柄与 `remove_watcher`，不需新增公共 API。〔源: include/fsm/battleContext.h:929-947〕〔源: include/effects/event_center.h:275-310〕

**不能原封照抄 406/190。** 旧实现只记 end、TEAM 永久 watcher，而且 406 的 `chance/amount` 被首次 lambda 捕获；190 的头注还明确不区分红粉。这些是先例的既有取舍，不是 1296 官方证据。〔源: resources/moves_lib/batch_c_skills.cpp:1390-1427〕〔源: resources/moves_lib/batch_c_skills.cpp:1429-1468〕

若裁定为可消除的回合类效果，必须有**正式 ContinuousEffect 窗口节点**纳入桶的回合计数，并由它维护受击订阅；callback 同时校验该来源的 `round_effect_valid_id`，下场则检查 watcher epoch/宿主。仅挂 watcher 再写一个 epoch 条件不够：`break_round_effects` 在没有可清对象时直接 NO_EFFECTS，不会 bump epoch，裸 watcher 永远不被断。桶的注册去重/计数、原语的判断和两个 epoch 的不同职责已有实现。〔源: include/effects/timed_bucket.h:38-81〕〔源: src/primitives/battle_primitives.cpp:899-934〕〔源: include/fsm/battleContext.h:75-84〕

落地时的小探针必须证明：只有 1296 时 `has_round_effects` 为真；消除返回 SUCCESS、后续受击不再治疗；重复刷新不增加有效窗数。窗口、订阅不得各有一份不同步的到期真相；若现有组合做不到这些，升级内核授权，而非用永久 TEAM watcher 凑覆盖率。若官方证实不可消回合，则不用为了让它可断而伪造桶节点。

EventCenter 投递只挡“已过期”，没有自动挡“尚未到 start”；后手顺延时 callback 仍须检查下界，且 watcher 自身寿命也必须从相同 start 起算，避免外层先过期吞掉末回合。〔源: include/effects/event_center.h:431-444〕

**B. 事件过滤与动作。** 基于“实际受到攻击伤害”候选，过滤 `target==owner`、合法对手 actor、NORMAL、amount>0，并读 `ev.state`，不能读已推进的 `ctx->currentState` 反推伤害发生时点。护盾全吸收在发 TAKE_DAMAGE 之前 return，因此这个事件不覆盖“命中但零落血”；这正是前置实测必须决定的分岔。〔源: include/effects/event_center.h:173-204〕〔源: src/primitives/battle_primitives.cpp:1062-1086〕〔源: src/primitives/battle_primitives.cpp:1126-1132〕

确定过滤后写审计，再走 P% 入口概率；成功后进行**一次**三档选择，`r∈[0,49]→200`、`[50,79]→300`、`[80,99]→400`，不要把三个概率写成独立 roll 或均匀取 200..400。复用项目 `sbs_rand`/`roll_percent` 体系，不复活 parser，不调用异常概率原语；0/100 门的早退已有助手。〔源: resources/moves_lib/common.h:102-106〕〔源: include/utils/sbs_rand.h:4-23〕

治疗前须显式检查宿主 `hp>0` 与死亡身份，再调用 `g_core->heal_amount`；该原语回传 `HealResult` 枚举而不是体力数，应记录当次 HP 差/立即读取 last_heal_amount。不能只靠“已登记死亡时治疗 no-op”：HP 耗尽到登记之间还有时序，B 级证据要求此时也不奶活；后续免死是否允许回需按实验裁定。〔源: include/plugin/core_api.h:69-70〕〔源: src/primitives/battle_primitives.cpp:1432-1492〕

**C. 审计数据契约。** 候选键段 `1,012,960,000 + owner×16 + slot`（10^9+1296×10^4），只是建议，不代表已预留；开工须跑撞键检查，未来同号 soul 若也使用该段要明确空间所有权。运行身份/句柄与观测值分开记录；0 是缺值时，回合戳采用 `roundCount+1`。〔源: docs_local/docs/10-游戏百科/10-台账字段与执行结果.md:377-387〕

建议 16 槽中的最小集合：入口 P、三个条件权重、当次档位、名义治疗量、实际治疗量、合格事件数、入门成功数、实际治疗数、拒绝原因、事件回合+1，以及生命周期使用的 watcher 句柄/epoch；slot 明确编号后再实现，不在本调研分配资源。拒绝事件的本次量置 0，不能遗留上一击值。实际回血可能被后续事件改写全局 last_heal_amount，私有审计应在调用返回后立即存本次值。

## 六、结论（三句话）

1296 的官方模板、9 个载体与9次普通技能引用均证实，现行引擎会跳过该子效果，但“必须等待异常系统补录”的挂账归因没有成立。
原作者的数据提取资料支持受击后的三档概率回血，推荐以现有事件、注册回合窗、治疗原语和审计槽实现，pending/快照/模式切换仅在新增实测证据要求时采用。
先立限定范围的 J 单裁定边界并实现，同时单列 R 单修复 boss 预填的 moves/soul 同号混用，当前不立新增异常或全局状态字段的内核单。
