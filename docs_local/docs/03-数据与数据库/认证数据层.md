# 认证数据层（custom_* 表）—— 引擎对官方数据的"解释/差异"层

> 本文是 `custom_effect_programs` / `custom_effect_overrides` 两张表的**权威 schema 来源**。
> ⚠️ **`scripts/` 目录被 `.gitignore`**（数据管线是本地工具），所以 import 脚本内的 SCHEMA 不入库；
> **改表结构以本文为准**，并同步改 `scripts/import_seer_unity_sqlite.py` 的 SCHEMA 字符串。

## 1. 它解决什么

官方数据库只提供**事实**（这招有什么 effect 文本、这些 id/参数），**不含我们引擎的解释**。而引擎读数据时需要两类官方没有/不可靠的信息：

1. **组合语法 / 效果程序**：`无相谛` 那种"6 个 effect 构成一个可逐条取消条件、累加威力的组合程序"，官方没有对应概念或字段。
2. **与官方的差异 / 官方 bug**：官方某些列是死列（`monsters.soul_mark_id` 全 0）、`effect_info.param_type` 过时、措辞变化会造成运行时文本解析器失效（脆弱层）。

与其在**运行时再加启发式解析**（脆弱、官方改词就挂），不如把这层解释**离线编码成数据**，引擎直接读。

## 2. 数据分层

```
官方 raw crawl (fetch/decode 产物, 只读、脚本再生成)
      │ import
      ▼
seer_unity.sqlite 官方事实层(18 官方表)   ← 引擎读的官方快照(清理版)
      │ ＋ custom_* 表(本层, 非官方字段, 不被 import 重刷)
      ▼
引擎 loadSkills 读取顺序:
   官方事实 → custom_effect_overrides(官差纠偏) → custom_effect_programs(离线程序)
            → 未命中则: 注册函数 → 运行时 parser(组合语法, 过渡期兜底)
```

## 3. 表结构

两张表都是 `CREATE TABLE IF NOT EXISTS`，且 **不**进 import 脚本的
`IMPORTERS` 列表 → 官方表重刷时本表数据**跨 import 存活**。

```sql
-- 离线编码的效果程序(组合语法/模板)。unit_json = 有序 EffectUnit 序列(JSON)，
-- 模型离线编码、引擎直接加载, 替代"运行时解析官方文本"这条脆弱层。
-- 锚定二选一: effect_id(单效果) 或 skill_id(整招组合, 如无相谛 37460)。
CREATE TABLE IF NOT EXISTS custom_effect_programs (
    id INTEGER PRIMARY KEY,
    effect_id INTEGER,                          -- 锚定单效果(可空: 组合型用 skill_id)
    skill_id  INTEGER,                          -- 锚定整招组合(可空: 单效果型用 effect_id)
    kind      TEXT NOT NULL DEFAULT 'program',  -- 'combo' | 'template' | 'program'
    name_zh   TEXT,                             -- 人读名(如 无相谛-威力模板)
    unit_json TEXT NOT NULL,                    -- [{"condition":{...},"action":{...}}, ...]
    memo      TEXT,                             -- 出处/设计说明
    UNIQUE(effect_id, skill_id, kind)
);
-- 官差纠偏: 存"故意不一致"的决策, 免得下个会话误当 bug 重查。
-- 覆盖已知官方问题: monsters.soul_mark_id 死列、param_type 过时、措辞变化等。
CREATE TABLE IF NOT EXISTS custom_effect_overrides (
    id INTEGER PRIMARY KEY,
    effect_id     INTEGER NOT NULL,
    override_type TEXT NOT NULL,                -- interpret_as_program | map_to | ignore | dead_column | window
    map_value     TEXT,                         -- override_type 的载荷(目标effect_id / 模板 / 空)
    source_scope  TEXT,                         -- 出处作用域(moves|effect_icon|hide_moves|...)
    rationale     TEXT,                         -- 为什么与官方不同(存决策, 很重要)
    UNIQUE(effect_id, override_type)
);
```

### 3.1 `override_type='window'` —— 回合数窗口家族声明（2026-09-13 新增）

**背景**：官方"回合数"效果有两族，**语义不同**（用户 2026-09-13 定）：

| `map_value` | 家族 | 生效区间 |
|---|---|---|
| `in_rounds`（**默认**，未声明即此） | 「{N}**回合内**」（约 495 条模板） | 先出手 → `R..R+N-1`；**后出手 → `R+1..R+N`**（顺延一回合，N≥2 时） |
| `next_rounds` | 「**下**{N}回合」（约 287 条，如"下2回合必定先手"） | **先/后出手都** `R+1..R+N`（本回合本就不算；后出手**不再**额外顺延） |

- 用途：`EffectMetaCatalog::build()` 把声明读进 `EffectMeta::window`；注册**持续 N 回合**的效果时用
  `BattleContext::round_effect_start_round(owner, duration, window)` 折算窗口起点（core 的 `register_branch`
  已接线；插件侧经 `CoreApi::effect_window_kind(effect_id)` 查后自行折算）。
- 为什么用显式声明而不是按文本自动判族：`effect_info.info` 的措辞官方随时会改（运行时文本解析是既定的**脆弱层**）。
- 已声明（渐进认证，用到哪个认哪个）：`58`（下N回合必定致命）、`81`（下N回合必定命中）、`83`（下两回合必定先手/致命）。
  其余"下N回合"模板**默认仍按 in_rounds** → 需要时按同一格式补行，`rationale` 务必写清依据原文。

```sql
INSERT OR REPLACE INTO custom_effect_overrides (effect_id, override_type, map_value, source_scope, rationale)
VALUES (58, 'window', 'next_rounds', 'effect_info', '原文「下{0}回合」= 本回合不算');
```

## 5. 开发循环（精灵效果逐步落地）

> 用户主导方向：**逐步实现精灵效果 → 遇到缺内核机制就反过来更新内核 → 新效果程序编码进本层**。

1. 实现一个精灵效果，发现内核缺某能力 → 在内核补（FSM 永不因新机制加代码，机制是内核数据）。
2. 效果的"解释"能离线编码 → 写进 `custom_effect_programs.unit_json`（或覆盖 `custom_override`）。
3. 引擎 loadSkills 命中即加载，不再靠运行时文本解析。

## 5.5 效果程序 JSON 格式（unit_json）

`unit_json` 是一棵**根 EffectUnit 节点树**（对应官方文本模板解析出的一整棵树）。字段：

```json
{
  "tag": "PowerBoost",            // PrimitiveTag 名（Anomaly|StatChange|Heal|FixedDamage|PpReduce|RemoveRoundEffects|DrainHp|Kill|PowerBoost），或数字下标
  "actor": 0, "target": 1,        // 相对发起方/目标（默认 0/1）
  "param0": 170,                  // 原语参数；数字=字面量，{"arg": n}=skill_args[n]（同文本模板 {n}）
  "param1": 0,
  "chance_arg": -1, "chance_value": -1,
  "condition": "SameElement",     // UnitCondition 名（None|SameElement|FirstMove|SecondMove|TargetNoAnomaly|TargetHasAnomaly|TargetHpBelow），或数字下标
  "condition_param": 0,
  "on_success": {…}, "on_immune": {…}, "on_blocked": {…}, "on_other": {…}   // 可选嵌套子单元（递归）
}
```

加载器 `load_effect_unit_from_json`（`include/effects/effect_unit_loader.h`）：解析后**扁平化**进
`std::vector<EffectUnit>`（同一份做指针链接、零 realloc 保证分支指针稳定），与 `parse_effect_unit` 输出完全同构 → 复用同一执行器。用 **nlohmann/json**（header-only，`find_path` 接 Homebrew；sim_core PRIVATE include）。

## 5.7 数据 vs 代码的实现归属 —— 为什么首选数据组装

**首选数据组装的**决定性**原因不是"代码更少"，而是可审计性：**
回合制对战里**每个 game mechanic 都必须能被静态查询、核对、做平衡性检查**（哪些招、以多大概率、改变了什么）。
普通代码封装的黑盒 effect 无法被非执行态审计——运行时只能调用，看不见内部。

> 例：魂印"抑制施展异常概率 <50% 的效果"。数据组装下，效果是结构化 `EffectUnit`（`chance_value`/`primary_tag`/
> `condition` 都是显式字段），魂印效果直接遍历对手 `Skills::parsed_units_`，筛 `Anomaly && chance<50` 的单元改/删 →
> **纯数据结构操作，零内核改动**。若改成黑盒函数封装，就看不见 chance，只能给内核加一套"异常前咨询抑制器"的
> 监听机制 —— 复杂度泄进引擎。

**两个实现方式（效果上等价，可审计性不等价）：**

| | 数据组装（DB: effect_id + 参数） | 代码封装（DB: 只存一个新 id，内部写死调原语） |
|---|---|---|
| 实现效果 | 等价 | 等价 |
| 复用 | ✓ | ✓ |
| **可被其他效果/魂印查询、定向修改**（内省性） | ✓ 结构化可读 | ✗ 不透明，需加内核监听 |
| 通用参数（换参数覆盖多招） | ✓ | ✗ 每招一个函数 |
| 非执行态审计/平衡检查 | ✓ 数据可得 | ✗ 只能靠读代码 |

**归属判定（四问，倾向数据）：**
1. **可被数据参数化**？同模板换参数覆盖多招（如 `effect 5` `{n}%改变某属性n级`）。
2. **被多个技能复用**？
3. **能拆成那几个稳定原语的组合**（CoreApi 断回合/改属性/异常/回血…）？
4. **会被其他效果/魂印 target、查询、定向修改**？（如上述"抑制 chance<50 异常"——能被外部看见/改内部）

→ 任一成立，就往数据靠；**四个全不成立才代码**（如无为觉者 2260 第五技：不参数化、不复用、强依赖魂印运行时协调、无人需要 target 它内部）。

**实现方式不冲突**：`moves.side_effect` 存的是"该招用了哪个 effect_id"；每个 effect_id 落到**两种实现之一**
（数据模板 `custom_effect_programs` / 代码函数 moves_lib·soul_lib）。DB 存「引用」不是「内容」——专属协调逻辑
留在代码、通用逻辑留数据，DB 不会为专属效果膨胀。
