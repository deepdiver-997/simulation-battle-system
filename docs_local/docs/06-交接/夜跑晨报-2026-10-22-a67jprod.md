## 勘误记档

1. **同 worktree 双会话并发（本轮最大坑）**：监督器 13:09–13:10 补起 `a68-jprod`
   ——**同一 worktree、同一分支**。对方立了 J309/J310、领了 J309；期间我的 J307 被
   以 `worker=zhr@pid89528`（**未带 agent id**）领走并**退回**，我 13:18 重新 claim
   夺回。教训：`claim.sh` 的"worktree 在用 → 退回"闸只护 **claim.sh** 路径，
   **taskctl 直连**（或 worker 未带 agent id）可绕过属主校验 → 夜跑里
   `TASKCTL_WORKER` **必须**等于 agent id，且同 worktree 并发会话应靠
   busy + 行文属主双闸。建议监督器补起前检查"该 worktree 是否已有活会话"。
2. **同秒 mtime 陷阱（新踩，重要）**：变异测试用 `cp` 复原源文件后紧接着
   `cmake --build`，若**源与 .o 落在同一秒**，make 判定 .o 仍是最新 → **不重编** →
   **变异代码留在 dylib 里** → 自己的场景假红（本轮第一遍 gate 就因此挂了
   6390/6410 两个场景，根因是 M2/M9 的变异码留在 dylib）。处置：复原后
   `touch` 源文件 + `sleep 1` 再编（或删 .o）。与 CMakeLists 里"POST_BUILD 只在
   重链接时才跑"那条警告同源，**变异测试脚本必须自带 touch**。
3. **提交信息里的 registry 数字被并发会话污染**：`feat(J306/J307/J308)` 三条提交
   里写的 moves 1384/1386/1388 是**混算**（把并发会话的 +2 记到本单）。准确口径：
   基线 1379 + 本族 5 = **1384**，板面合计 1386（含并发 J309 的 +2）。**看板状态列
   已按准确口径写**；提交信息未回改（避免在并发会话之上做历史重写）。
4. **`.agent-env` 未注入 `SBS_AGENT_ID` / `SBS_AGENTS_DIR`**（内容仍是通用邮件模板），
   本轮以 `$PWD/.agent-env` 相对路径 source 且手工 claim（同 a25/a45/a48/a62–a65）。
5. **`finish.sh` 打 hub 旧看板**（同 a48）：`finish.sh` → `lib.sh` 的
   `taskctl()` 走 `$HUB/tools/taskctl.py` → 改的是 hub(main-local)那份看板，
   看不到本分支新立的行。本轮改用 **worktree 内** `python3 tools/taskctl.py done`
   （同 a48 处置），并手工 `agent_id.py idle` 清 busy。
6. **DB 被重建（只读记档）**：`scripts/data/processed/seer_unity.sqlite`（软链到
   hub）的 mtime 在 12:55 变过；核对 `types_relation` / `skill_types` 内容**未变**
   （水→火 2.0、水→水 0.5；1草 2水 3火），本轮无影响。
7. **立单口径与 spawn 级"不自行立项"冲突（本轮按任务书 author 协议走，与
   a62–a65 的"从 spawn 级"处置相反）**：理由 = ①a64/a65 已连续四轮只做复核、
   **零产出**，且监督器每 5 分钟按"并发 0"补起 → 形成"复核 → 退出 → 再补起"的
   空转循环（a64 报告已把"需编排侧立新单或解除立项限制"挂了两轮，无人应答）；
   ②任务书正文对 author 协议有完整步骤与护栏（全局制定权锁、一次探索 ≤3 单、
   动工前置三查、**必调** `author_done.sh` 释放）；③看板空且未收到停止信号时
