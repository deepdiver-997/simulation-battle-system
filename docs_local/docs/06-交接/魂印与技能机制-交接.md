### ★ 效果 584 与特性瞬杀的叠加（本线的架构决策，回应"ws 特性物化"提案）

584 = 「{0}回合内自己的所有攻击技能都附有{1}%的秒杀概率」（29047 带 3 回合 15%）。
问题：瞬杀特性是**单掷点**（`trait_instant_kill_zero_hook` 里 `effective_common_trait` 取
本体槽 → `trait_proc_roll` 一次），技能效果给的概率与特性概率**应可叠加**，现有体系表达不了。

- **采用形态（2026-09-26 二稿，用户拍板"一次攻击判两次秒杀太怪"）**：ws 新槽
  `instant_kill_permille_bonus[2]`（千分点）。584 走标准回合窗口（注册 MOVE_RIGHT 桶——
  该桶 execute(0)+execute(1) 双侧都跑，一个注册点覆盖先/后手；先手当回合**立即写一次**
  补 InRounds 起点），每回合把概率重写进 ws；**判定仍只有一次**——钩位里特性份额与
  技能份额**加法合并成同一个掷点**，命中走一次 `force_hp_to_zero`：
  · 特性份额走 `trait_proc_permille`（含 proc_override 抬满）；
  · **亮节降零只零特性份额**（0<特性概率≤500‰ 被降零 → 特性份额记 0；技能份额不是
    特性掷点，不受降零）；
  · **proc_forced 必发优先于概率判定**（老 `trait_proc_roll` 里 forced 在 permille 判定
    之前返回 true，0% 概率的必发特性照发——场景 055 K10 守护点，合并时曾踩回归）；
  · 合计 ≥1000‰ 必发不消耗 rand；合计 0 且非必发直接返回不消耗 rand——既有场景
    （无 584）的随机序列零移位。
- **为什么不进 trait_state_（对"往 ws 加 array<array<TraitKind,range>,2> + 回合开始物化"
  提案的评估）**：方向对（回合作用域状态放 ws、走"reset→回合效果重写"套路），但整表
  物化三个问题：
  ① `TraitKind` 只有身份没有参数——584 的"15%"没地方放，得升级成 `EffectiveTrait` 表；
  ② **快照过期**：特性槽随换宠变（sync_on_stage_trait）、复制/抑制条目有自己的中途
     生命周期（epoch+登场槽惰性判活），只在回合开始物化一次必然在换宠/断回合后失真，
     要补齐就得维护一串同步点——现有惰性读就是为免掉这组同步点（同 effective_size
     "不做常驻缓存"的理由）；
  ③ **门控语义按源而分**：584 是技能效果不是特性——不吃特性抑制（扎克斯式抑制的是
     "瞬杀特性"）、不吃 proc_forced/proc_override、不吃亮节降零；混进同一张表这些门
     要么误伤要么漏。⇒ 结论：**特性身份留在 trait_state_（权威+惰性判活），
     技能给的特性式数值加成放 ws 类型化槽位、由行为钩位合并消费**。
     将来若出现大量"技能授予特性类行为"，再考虑给 TraitState 加 source 锚的 granted
     覆盖层（复用 TraitOverlay 机制），仍然不做回合快照。
- **已知边缘（合并掷点的代价）**：抑制的是"瞬杀特性"，合并后无法区分份额来源——持有
  被抑制瞬杀特性+584 的攻击者，其 584 份额也会被原语一并短路。现实里需要抑制生产者
  才可达（见下节：目前零生产者），迁移到 RuleCenter 条目时按来源分开即可根治。

### ★ TraitState.suppressions 是什么 + RuleCenter 迁移提案（2026-09-26 评估）

`TraitSuppression` 条目 = "side X 的某类特性 K 被抑制"（挂在**被抑制方**的 TraitState 上，
带 source_owner/source_slot/source_valid_id 三件套生命周期锚，查询时惰性判活）。消费方
六处：`force_hp_to_zero` 原语（瞬杀短路——**被抑制 ≠ 不触发**：照常掷点、原语不归零、
事件 blocked=true，咤咒怨照样 +1）、被动属性降/升钩、顽强/回神钩、接触毒钩、
`effective_common_trait` 查询过滤。**生产者目前为零**——只有场景 054/055/119 手工造条目
当测试桩；它是为"咤克斯式抑制对手瞬杀"预留的扩展点，还没有任何魂印接。

用户提案（2026-09-26）：**拦截不该住在 TraitState 里**——应该是魂印在战斗开始（注册函数）
向 RuleCenter 注册一条抑制项（关联到具体哪边，镜像战一边死/被消逝只撤自己的条目），
原语只查 RuleCenter；命中抑制就不归零、直接返回并发事件告知"触发了"，咤的监听器收事件
计层。**评估：同意，这是更干净的归一化**——RuleCenter 已有覆盖键/生命周期锚/ON_STAGE-
TEAM 作用域/断回合作废/条件函数（`grant_immunity` 的 condition 形参）全套机器，
TraitState.suppressions 是一套平行的迷你实现。迁移面：`is_trait_suppressed` 的六个消费点
换成 RuleCenter 查询（新 RuleCategory，如 TRAIT_SUPPRESS + kind 细分），原语里
"blocked 事件照发"的口径不变；054/055/119 三个测试的造条目方式跟着换。**待排期**，
当前无生产者、风险低。

同款思路对**亮节降零**的推广（用户提案，2026-09-26 追问落地形态后定案）：现在
`proc_zeroed_le50` 只盖**特性掷点**（`trait_proc_roll` 独家消费；圣武 ROUND_START 同步
写入 own 槽）——**技能施加的附加异常概率（"命中后X%令异常"族）不在覆盖面**，与官方
"≤50% 的附加异常全部降为 0%"有差距。Rule 化形态：圣武战斗开始注册条件票，异常施加前
查询——票内条件判"发起者是否持亮节 + 本次施加概率"，≤50% → 阻挡。
**落地形态（用户问"改原语签名还是只改概率包装"）→ 只改概率包装，不动现有原语签名**：
① 现有 `apply_anomaly/_ancient/_raw` 三槽保持不变——100% 施加没有可供亮节判定的概率，
   改签名是全插件 ABI 翻新，零行为收益；
② 新增**带概率的包装入口**（如 CoreApi 新槽 `apply_anomaly_chanced(ctx, target, id,
   duration, actor, chance_pct)`，或效果侧 inline helper）：内部先查亮节 rule
   （发起者持亮节且 chance≤50 → 直接返回"未触发"、不消耗 rand），否则就地掷点再委托
   旧原语。概率掷点从调用方挪进包装，调用方少一行且不可能绕过；
   ⚠️ 新入口只给**迁移的调用方**用——既有调用方不迁就不消耗 rand，随机序列零移位；
③ 迁移面收敛在两个漏斗：effect_unit 的 Anomaly 单元执行路径（"X%令异常"族的集中地）
   + 插件侧家族 wrapper（`apply_ancient_hit_status` 等）——逐个迁，不必一次到位；
④ 消逝撤销：圣武自己挂 EVENT_VANISH watcher 注销票（原语无关）。
**待排期**（圣武线归属另一工作区，本线不动）。

## 零前、2026-09-22 深夜：免断线——神之宣告 n-1 特判 + 断回合次数票 + ROUND_START 房主序

**回归基线：全部场景 111/111 + smoke 全绿（场景 112 增 H 组）。** 同工作区 `agents/qiling`。
口径来源：语料 **《机制解析—免断》**（opus 864257164964790278）+ **作者顶置评论**
（"元神和其他免断不一样，特殊处理为 n-1 回合，因此元神最准确的描述是**1回合免断➕下1次
免断**，而不是描述上的 2 回合免断……和圣雷 2 回合免断比起来会少 1 回合"）。

- **神之宣告（27021）的免断有实现但原样不对**：DB side_effect 走 effect 821（"n回合内
  自身的回合类效果无法被消除"），帝君线已有全局实现（平窗 n 回合 + "后出手时回合数+1"
  骑缝）。语料钉死两件事：① 821 本身就是"变相次数免断"——真尾巴是"n回合之后于对手下1次
  技能出手流程结束才结束"；② 元神被官方**额外**特殊处理为 n-1。⇒ 特判形态 =
  **窗口(n-1) + 次数票(下1次)**，对 n=2 正是"1回合免断➕下1次免断"（旧"后手+1"骑缝是
  早期近似，真尾巴按次数票表达、不再叠加）。
- **落点**：821 有 25+ 技能共享（含轮回之狱）→ 全局实现不动，`skills.cpp` loadSkills 按
  **(技能 27021, effect 821) 特判路由**到内部变体 **270210**（=技能id×10，刻意避开 DB
  effect id 空间；该段 DB 现为空），qiling 插件注册实现：窗口票 duration=n-1 + 次数票
  counts=1（无时限；两张票各占显式 source_effect_id 才并存）。

### ★ "解异常"的两个时点判定（场景 105）

引擎里"能不能出招"的判定点 = **受害者自己的行动开始**（`should_skip_action_flow` →
`has_blocking_control_status`，battleFsm.cpp 的 `handle_Battle*ActionStart`）。所以
"解异常"落在哪个时点，决定它**能不能救回本回合**：

| 档 | 时点 | 对手先手"击杀 + 附加控制"后 | 例子 |
|---|---|---|---|
| **高级**（能救回本回合） | **死亡拦截时点**（死亡漏斗里，仍在对手的行动期内） | 保留 1 体力 + **当场清掉刚被附加的控制** → 轮到自己的行动期时身上已无控制 → **当回合照常出招** | 空元之渎（`DeathInterceptor`，场景 105 C 组）、光螳螂/战螳螂等"范围即时检测"族（语料 idx=319） |
| **低级**（救不回本回合） | **回合结束**（`BATTLE_ROUND_END`） | 死亡被拦下、但当回合行动期判定时控制**还在身上** → 本回合**不能行动**，只能等回合结束才清 | 光之惩戒·英卡洛斯（回合结束解除异常）——场景 105 C' 组用"只保命、不解异常"的测试拦截器锁住这一档 |

**另一条正交判定：回合开始解异常（之铭·乂）**（场景 105 A/B 组）：

- 乂 落在 **ROUND_START**，早于双方的行动期 → 它清的是**当时**身上的异常，**不免疫后续**；
- 所以"对手先手在**本回合行动期**又附加控制"时：**旧异常确实被清了，但当回合依然不能行动**
  （A 组：诅咒被清 + 新的害怕留下 + 技能主流程被跳过）；
- 对手**上一回合**留下的控制 → 本回合回合开始被清 → 当回合正常行动（B 组）。
- 乂 的门读选择期 `roundChoice[owner][1] == 2`（面板槽位）→ **被控跳过主流程也照样在回合开始生效**
  （"回合开始时"本来就早于"能不能出招"）。

### ★ 本场踩过的坑（都已在代码里留注释）

1. **`cmake --build build --target sim_scenario_0NN_xxx` 不会重新部署插件 dylib**

   `source_id`（`kongyuan_skills.cpp` 的 `kPriorityWindowTailSource`）。
4. **魂印节点不做 SECOND 镜像**：凡是要覆盖"**后手方**出手"的节点必须 FIRST/SECOND

**二、args 编码约定（踩过才知道，务必按族取值）**：
- **概率的存放位置逐族不同**：毒/吸收在 `args[0]`；被动属性升降在 `args[1]`（args[0] 是能力码）；
  单属性增伤 args[1] 是增伤点数（**不是概率**）。→ `trait_proc_permille` 按 kind 分支取。
- **单位也逐族不同**：小概率族（瞬杀/顽强/回神/虚无/会心/免爆）args 是**千分点**；
  别的族（毒/单属性/精准/回避/吸收/被动属性/精神）args 是**百分点** → ×10 转千分点。

**三、★ 官方能力码 ≠ 引擎 stat 索引（静默错位，最难查）**：
`new_se.intro` 是权威证词：
- **Eid 34/35 族**：`0攻击 / 1防御 / 2特攻 / 3特防 / 4速度`；引擎是 `0攻/1特攻/2防/3特防/4速`
  → `trait_stat_index_from_code` 重映射（透传会把**防御与特攻互换**，场景 060 A5 钉死）。
- **Eid 26 族（数值提升，stat=2）是第三套**：`1防御/2特防/3攻击/4特攻/5速度`——用前各自核对 intro。

**四、必修6 给出的机制修正（推翻了望文生义的理解）**：
- **免爆 = 当回合免疫受到的暴击伤害（对暴击的**挡伤**），不是降低暴击概率**；
- **虚无 = 有概率闪避对手攻击技能**（不是挡伤）；
- **会心**：0 星是 6.25%（1/16）**与技能初始暴击率加法**；1-5 星是**独立二次结算**
  （"只要有一个触发则必定暴击"）；
- **精准/回避**：与技能初始命中率**乘法**、可作用于属性技能；**回避本质是降低对手命中率，
  不是概率效果**（故不被"概率提升"类效果推到 100%）；
- **被动属性提升**："在技能**命中时之前**赋予"（先赋予后挨打，对方才能消强）+ **属性技能也触发**；
- **强攻/强念**（追加伤害）：与红伤一并结算，但**攻击技能 miss 了也扣血**；
- **顽强/回神**：**仅战斗阶段触发**（回合结束后的致死伤害直接击杀，不触发）；
- **单属性增伤**：时点过于靠前，**会被变威力效果覆盖重写**（经典威严王之哈莫）。

### ★ 架构备查（2026-09-16 调研结论，用户提问后查实；下次别再重推）

**问 1：要不要把项目内的能力码布局改成"和官方一致"，省掉映射？→ 不要。**
因为**"官方"自己就有至少三套互不相同的码序**（都已实证）：
| 来源 | 码序 | 证据 |
|---|---|---|
| **技能数据（moves/effect_info）** | **0攻 1特攻 2防 3特防 4速** | effect 5「{1}%改变对手{0}等级{2}」——moves_lib 的 `effect_5_change_opp_stat` 把 `args[2]` **直接**当引擎下标用、**零转换**就正确工作（几百个技能在用）→ **引擎现有顺序就是主数据源的顺序** |
| new_se 特性 Eid 34/35 | 0攻 1**防** 2**特攻** 3特防 4速 | `new_se.intro`：`34\|1 5\|反驳\|…使对方**防御**降低1个等级` |
| new_se 特性 Eid 26（数值提升） | 1防 2特防 3攻 4特攻 5速 | `new_se.intro`：`1001\|1 20\|增加精灵**防御**20`、`1003\|3 20\|增加精灵**攻击**20` |
→ 结论：引擎顺序**不是乱来的**，它是覆盖绝大部分数据的**主流官方顺序**；少数派是特性表的另两套。
"改成和官方一致"只会把转换从 new_se 挪到 moves，并把 42 处 `levels[` 访问点全动一遍，净收益为负。
**防"忘记映射"的正确手段**：(a) 每个码序边界一个具名转换函数 + 证据注释（已做
`trait_stat_index_from_code`）；(b) 一个测试把映射钉死（已做场景 060 A5"防御 -1 而特攻未动"）；
(c) 可选加固：让转换函数返回**强类型**（如 `struct StatIndex{int v;}`），直接透传官方码会编译不过。

**问 2：要不要把 6 个能力槽包成 struct + 枚举访问？→ 建议只做"轻"的那半。**
`levels[` 现有 **42 处**访问点（battle_primitives 25 / battleContext 7 / 插件 6 / 头 4）。
数组本身没问题，**问题是裸字面量** → 引入具名枚举下标（`levels[Ability::Defense]`）或内联访问器
（`pet.ability(Ability::Defense)`）即可拿到绝大部分收益，改动是机械的、可分批做。
**暂不**把 `std::array<int,6>` 换成新结构体：收益边际，且 `ElfPet` 有**手写拷贝/移动清单 4 处**
（加字段漏改就静默丢数据，历史上踩过）——下次因别的理由动 `ElfPet` 时，
**先解决那个 4 处维护隐患**（集中化/默认拷贝）比换容器更值。

**问 3：能力等级是否该从 pet 搬到 context？→ 不建议。**
`pet.levels` 在**切宠时不清**（已核 `battleContext.cpp` 无任何 levels 重置路径）——这正是
"切走再切回保留强化"的实现基础。搬进 context 要么丢这条语义，要么得在 context 里按
`(side, slot)` 存一份**等价于 pet 的存储**（结构上只是搬家）。且 levels 与 `hp` 同类
（都是精灵**本体**状态，`hp` 就在 pet 上），单飞会造成"本体状态一半在 pet 一半在 context"的分裂；
而 `ws.view_levels` 已经是"回合内视图"（公式读它）——本体/视图分离是**有意设计**。
若真实动机是"消除 `ElfPet` 手写拷贝 4 处的维护隐患"，那正确解法是给 `ElfPet` 做集中化拷贝，
不是把字段搬走。

### ★ 决策（用户 2026-09-16 拍板）：确定性概率 / RNG 接口 —— **先不做，等下一批特性**

**背景事实（调研过，别再查）**：全仓 **28 个 `rand()` 调用点、13 个文件**，用途 9 类——
命中/闪避（skills.cpp:521）、暴击（skills.cpp:547）、连击数（skills.h:209）、
伤害浮动（calculation.h:40）、异常抗性（resistance-system.h:118/129）、概率类技能效果
（effect.cpp:269 / effect_unit.cpp:27 / battle_primitives.cpp:473 / moves_lib:20,689 /
soul_lib:34 / curse_stack:187,209）、特性掷点（trait_state.h:151）、
先手权随机（battleFsm.cpp:1144,1198）、随机选取（moves_lib:1304 / soul_lib:1527）。

**⚠️ 隐性契约（本仓库一直依赖，改动前必读）**：几处代码**靠"短路时不消耗 rand()"保序列稳定**——
`skills.h:203`（连击区间退化 min==max 不消耗）、`battleFsm.cpp:230`（无连击模板同）、
暴击率 0 短路不消耗（harness 注释）。**2026-09-16 的 4 场景回归事故**就是把这条踩了
（见上条"最大的坑"）。**任何 RNG 改造都必须保留"不调用=不消耗"语义。**

**决策与理由**：
1. **不以"消除脆弱性"为理由做**——那需要**每用途独立发生器**（每机制一条 `mt19937`），
   代价是**所有伤害断言一次性重标**（伤害浮动 `(217 + rand()%39)/255`，换发生器则每个伤害
   数字都变，约二三十个场景）。只有确实想要"新增一条随机不影响其它机制"时才值，
   且应**单独一个会话专门做**，不与新特性混做。
2. **真正值得做的目标 = 让测试钉住掷点数值，从而在边界上验证概率表**。本项目反复栽在
   "官方读数错误"上（瞬杀星级千分点表 / 坚硬修正表 5-6-8-10-9-10 / 毒 3~8 百分点），
   而现有测试手法（args=100 必定触发 / proc_forced）**只能测"触发"分支，证不了阈值是 5% 还是 6%**。
3. **形状（待做时按此实现，默认零行为变更、零重标）**：
   ```cpp
   enum class RngStream { Accuracy, Crit, ComboCount, DamageFloat, Resistance,
                          EffectChance, TraitProc, Initiative, RandomPick };
   // ctx.rng_.inject[stream] = 值 → 该流**下次**掷点直接返回它、不消耗底层序列；
   // 未注入 → 逐位走 std::rand()，与现状完全一致。
   ```
   插件侧（moves_lib / soul_lib / curse_stack / trait_state）要**多一个 CoreApi 末尾槽**
   （`rng_next(stream, bound)`）才能用上；头文件内联的（curse_stack / trait_state）可直读 ctx。
4. **时机**：下一批特性（剩 40 余种，会密集碰概率表）顺手一起做——那时边界验证需求真实且密集，
   现在做只会多一层没有消费者的间接层。

### 三条「谁在哪一层，谁负什么责」

- **掩码抑制**：`ElfPet::damage_suppress_mask`（bit = `DamageEffectCategory`）是**唯一真相源**。
  **在管线里的**效果由 `DamagePipeline::run` 机械按类别跳过（新效果声明类别即自动覆盖，零硬编码）；
  **在时点桶里的**效果（如 effect 34 弹伤）必须**自己查掩码**（`damage_guard_suppressed`）。
  沧岚蚀砚之泪≥4滴 = 写入 `BLOCK|DETECT`。
- **粉伤即时结算**：一次 `deal_pink_damage` = 一段，逐段取整/逐段扣护罩/逐段检测，
  **没有段计数状态**。
- **`BLOCK` 阶段是唯一能同时拿到「被归零前的值」和「执行归零」的位置**。
  想"免疫 N 次 + 按免疫量回馈"（816 弦月锋华 / 2360 王·龙予狂宴）就必须挂这里；
  但 **`BLOCK` 的默认回调会抢先消费免伤票据** → 计数要自己管（闭包状态），别指望票据。
  共享实现已抽成 `arm_immunity_reflect_true(ctx, self, count)`。

## 五、坑与约定（2026-09-11 段）

1. **免断 = `ImmunityType::BREAK`**（owner 级，免疫内核），**不是** `SkillArmor` 的属性。

   **同来源覆盖刷新、不同来源绝不合并**——哪怕底层效果代码完全相同。
4. **全部消费**：一次技能使用消耗**所有**响应的次数类条目（回合类响应但不消耗）；
   miss 也照常 notify。
5. **`ws` 在 `BATTLE_ROUND_START` reset，而 ROUND_START 排在 CHOOSE 之后**
   （线性序：CHOOSE → PROTECTION_1 → ENTER_STAGE → ROUND_START → 战斗链）。

   在选择期设会被清掉。
6. **`ws.reset()` 用 `memset` 清零后再恢复默认值**——新增非零默认字段（-1 / 1.0 / 200）务必
   在那个循环里显式恢复，否则默认值变 0。
7. **不要用"改写内存 + 下个时点还原"的写法**：本游戏存在**跳过时点**语义
   （星皇之怒"体力因此归 0 的对手无法触发任何效果"），还原那一步可能被跳过 → 改动变永久。
   用 ws 字段（每回合自动失效）或 epoch/版本号（O(1) 作废）。

## 附录二：效果结算顺序的三层模型与"语义显式化"守则（2026-09-27，渎神/神圣复苏 1237 事故复盘）

**事故**：渎神 38020 的 1237（消双方回合类）把同技能后继效果 43（回满血）/1814（臣服窗口）
的在途节点当"可断回合类"误断——判定面 `has_round_effects` 把一次性动作节点（left_round==0
归一化 duration=1）计入，SUCCESS 触发整容器 epoch 作废，后继全灭。神圣复苏同款 1237 从未
暴露，仅因 1237 恰好排在它效果列**末尾**——顺序只决定雷炸不炸、在谁身上炸，不是根因。

**顺序的三层模型**（效果结算只是大时点之一，内部顺序关系）：
1. **时点间**：FSM 状态固定序（先制→命中→效果结算→伤害→行动后→死亡→回合始末）。效果只选桶。
2. **效果链内**：`moves.side_effect` 数组序 = 官方书写序 = 同桶执行序（荡世 1012 吸强先于 882
   变威力、吸到的强化当场参与威力计数，即依赖此序；场景 139 T1 锁）。
3. **桶内**：执行期再注册进未来桶的条目（窗口 tick / AFTER_ACTION 检查），同桶按注册序。
4. **正交维度——生命周期语义**：回合类（计时窗口，可断可驱散）vs 一次性动作节点（在途执行）
   vs 常驻（ROSTER/ON_STAGE）。两次事故（解析器误读 2321、1237 误断后继）都是**这一维度的
   语义没有显式表达**，靠字段过载或文本匹配隐式承载。

**设计守则（讨论定稿 2026-09-27）**：
- **拒绝全局效果 ID 优先级队列**：表达不了"同 ID 在不同技能里不同序"（官方书写序本就是
  每技能一份的意图）；ID 数值与优先级无关联；本质上会退化成每技能一份的重复数据，且是
  又一张手工维护的中央表（与插件自注册设计相悖）。
- **数据层序 = 执行序是骨架**：数组序就是官方意图的载体，不另设第二真相源。
- **同桶顺序成为约束时，优先换桶，不给同桶内加优先级**（荡世流血 1679 → OLD_ROUND_END_1
  一次性节点是范本）。
- **"数据层不出问题"的防线是测试不是架构**：凡技能行为依赖效果间相对顺序，用场景断言锁死
  （荡世 T1"威力视图 140 + 伤害比值 1.4"即范例）；凡语义靠字段/文本隐式承载的，显式化
  （isActionOneShot / 生命周期标签），不要让记账层去猜。

### 死亡模型讨论 2026-09-30（进行中——三通道分类定稿，反同归内核化设计待落地）

**三通道分类（用户定稿，与引擎现状逐一对照）**：
1. **伤害通道**（红/粉/真，`deal_damage` + `run_pink_damage` 两个结算函数收尾）→
   **预死亡信号**（hp≤0 时发广播，带 actor/target/kind）→ 免死可触发。信号落点=推送式，
   反应型免死（②范围即时检测族）在信号回调里写血即自然否决；与拦截器拉层并存
   （①时点型走拦截器、②即时型走信号）。
2. **秒杀通道**（`force_hp_to_zero`）→ 发 EVENT_HP_TO_ZERO + 查免疫秒杀票 → 免死不触发
   ——瞬杀不修正红伤，"0 红伤 + 必瞬杀"打穿护盾表姐正是本通道（引擎现行为一致）。
3. **体力修正通道**（自爆 HP_CONSUME、斩杀印记）→ 不发秒杀信号、不查免疫票 → 免死不触发、

   通道不可见"两种讲法等价，后者更精确。

## 2026-10-01 人工裁定批量落档（用户口述定稿）

### 1. 表姐免死 = 触发一次拉一次（定稿）
"给一段免死票"假设作废。现实现即正确，无需改动。

### 2. 低血无相谛秒杀不死的机理（解释性定稿）
秒杀效果先结算把血打到 0 → 免死拉起 1；随后红伤结算再次触发致命伤害通道 →
免死再次拉起。不是免死漏触发，是**两个通道先后各来了一次**，与"一次致命一次锁"
的模型自洽。

### 3. effect 63「将能力下降状态反馈给对手」规格细化
两步：①解除自身能力下降；②把解除的下降**按同等级**附加给对手。
- **两者都成功效果才返回成功**：自身有解不掉的弱化，或对手免弱 → 整体不算成功
  （现实现 batch_b effect_63_reflect_drops 是"逐槽失败"口径，需收紧为整体判定）；
- 对手某槽已 -6 无法继续下降、但无免弱 → **也算成功**，但要区分返回结果/信号
  ——引擎 `StatChangeResult::AT_CAP` 就是这个信号，实现时把"附加落地"与
  "落地但 AT_CAP"分开上报，后续效果（如"反馈成功则…"链）用得上；
- 自身无任何下降 → 整体不触发（现口径保留）。

### 4. effect 795 累计 = 场上有效、下场失效；2472 是例外
- 795「每次使用…额外提升{0}%，最高{1}%」的累计计数：**下场即清零**。
  现实现（d5_D15 plugin_storage 计数）跨切换保留 → **需修**：计数绑定在场
  （下场清零，换回重计）。
- 例外 = 蔑天行·戾杀的 **2472**：「本场战斗此伤害额外乘4」官方明写"本场"→
  下场保留（2472 现无实现，落地时按 plugin_storage 常驻）。
- 通用规则：技能的这类提升默认**场上有效**；官方文本明写"本场/下场保留"才例外。

### 5. 护盾/护罩：吸收结算进管线，生命周期不进
裁定：所有伤害最终在管线中结算，**无穿透标志的红/粉都应经过护盾/护罩消耗**，
因此吸收结算应作为管线阶段存在；护盾/护罩的**生命周期**（获得/到期/清除/定量）
仍是效果层的事，不进管线。
现状差距：红伤护盾吸收在 `deal_damage` 落血处（battle_primitives.cpp:1050，
管线之后），DamagePhase 十阶段无护盾阶段 → **待办**：新增 SHIELD 阶段
（官方顺序"点数减伤—百分比减伤—护盾/护罩" = REDUCE_PCT 之后、FLOOR 之前），
把红/粉两条吸收统一挪入。
