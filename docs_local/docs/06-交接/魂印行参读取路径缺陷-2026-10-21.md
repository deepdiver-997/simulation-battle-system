## 一、一句话结论

`SoulNodeArgs::row`（类型化行参）在**真实对局**里相对 DB `effect_icon.args`
**偏移 2 位**——绝大多数情况下 `a.row` 是**空的**，导致按 `a.row_or(i, ...)`
读取行参的存量实现**全部走 fallback 硬编码值**；少数行（DB args ≥ 3 位）
则读到**错位的值**。

## 二、机制（源码证据链）

1. **真实对局装载**（`src/entities/pet_factory.cpp:502`）：
   ```cpp
   SoulMark soul_mark(display.effect_id, ..., EffectArgs(display.args));
   ```
   `display.args` = DB `effect_icon.args` **原样**（`parse_int_list` 解析，见
   `src/db/official_data_repository.cpp:47`）。故真实对局里
   `soulMark.args.owned_int_args` **就是 DB args**（通常 2~8 位）。

2. **绑定丢弃前两位**（`src/entities/soul_mark_manager.cpp:351-362`）：
   ```cpp
   EffectArgs bind_soulmark_args(const EffectArgs& args, int owner, int host_slot) {
       merged = [owner, opp, host_slot] + args.owned_int_args[2..];
   }
   ```
   注释写明"args[0..2]=owner/enemy/host_slot 注入，DB args[2:] 原样跟在后面"——
   这个约定是**按"DB args 前两位是占位"**设计的，但真实对局的 DB args **没有**
   那两位占位（DB 里 827 是 `80 1`、357 是 `2 1 1 30`、359 是 `2 2 5`）。

3. **类型化 shim 取 row**（`include/plugin/soul_node_args.h:53`）：
   ```cpp
   a.row.assign(bound.int_args + 3, bound.int_args + bound.int_count);
   ```
   即 `a.row` = 绑定后 args[3..] = `owned_int_args[2..]` = **DB args[2..]**。

## 四、为什么存量测试是绿的

存量场景按 `{0, 0, ...行参}` 构造 SoulMark 的 args（**多带两位占位**），
于是绑定后 `a.row` = 真实行参 → `row_or(i)` 读值正确。**场景口径与真实对局口径
不一致**，两边都"错"但互相抵消，于是测试全绿、线上失配。

**例**：K193（827）读 `a.row_or(0, 80)` 取冰封概率——
- 场景：args={0,0,80,1} → `a.row`=[80,1] → `row_or(0)`=80 ✓
- 真实对局（row521，DB args=[80,1]）→ `a.row`=[] → `row_or(0)`=**fallback 80** ✓（巧合正确）
- 真实对局（row536，DB args=[80,1,1]）→ `a.row`=[1] → `row_or(0)`=**1** ✗（概率变成 1%！）
  且 `row_or(2, -1)`（补子句旗）→ **-1** ✗（3212 行的"属性技命中则消除对手回合类效果"
  子句在真实对局里**永不触发**）

## 五、两种修法（待裁决）

| 方案 | 做法 | 影响 |
|---|---|---|
| **A. 改内核绑定** | `bind_soulmark_args` 改为 `merged = [owner, opp, host_slot] + owned_int_args`（不丢前两位） | 一处改动，但会**同时改变 30 处 `row_or` 的读值**（多数会从"当前值"变成"DB args[0]"——对 827 恰好相同，对 827 row536 会从 1 变 80 = 修好；但对 172/179/187 等多参行会**再偏移**）→ 需逐个复核 17 个文件 |
| **B. 存量迁移到 db_at** | 17 个文件改走 `db_at`（读 `host.soulMark.args.owned_int_args` 原序，K226-K252 已用此法） | 改动面大（17 文件），但**语义明确**（与真实对局一致）、零内核风险；新代码一律用 db_at |

**夜跑已采取的口径（2026-10-21 起，K253-K258 全部遵循）**：
- 新代码**一律走 `db_at`**（读 `owned_int_args` 原序）；
- 场景**按 DB args 原样**构造（不补 `{0,0}` 前缀）；
- 存量文件**不动**（改动面大、需白班统一裁决并逐个复核）。
