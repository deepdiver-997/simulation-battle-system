## 三、★ 子句② 的三个口径（本次最核心，别改回去）

1. **压制走 `stat_change` 原语、不查任何免疫**："无视任何免疫直接改"——不走 `stat_drop`
   （那会先查免弱 STAT_DROP、再受 STAT_CLEAR 影响），只做 ±6 钳制。这正是它霸道的地方。
2. **但必须走原语、不能直写 `ability_levels`**：直写会同时漏掉三件事——
   视图 `ws.view_levels` 不同步（**伤害公式与出手先后读视图** → 压了不生效）、
   `EVENT_STAT_CHANGED` 不发（别的"监测等级变化"效果看不见）、以及本体/视图分裂的历史坑。
   为此新增了 `write_ability_level()` 作为**所有**等级写入的唯一落点（本次把
   `stat_change`/`stat_drop`/`clear_stat_boosts`/`clear_stat_drops`/`crit_defense_break`/
   `transfer_stat_boosts`/`stat_reversal`/`stat_boost_reversal` 八条路径全部收口）。
   直写的地方只剩 1038 谱尼轮回的**快照回档**（那是"把快照写回"，本来就不算一次等级变更，
   但它同样会绕过监测——若要给它补事件，注意别让"压制窗口"把回档又压回去）。
3. **挂 `EVENT_STAT_CHANGED` 事件，而不是"回合开始时注册一次"** ← **用户 2026-09-18 指出的坑**。
   引擎同一 State 的桶按 **(owner 0 → owner 1) 定序**跑（`execute_registered_actions(-1, …)`
   展开，即官方"回合开始时看挑战方机制、房主方先判定"在引擎里的对应物）。
   若只在 `BATTLE_ROUND_START` 注册一次压制：**索伦森 = owner 0 时他的节点先跑**，
   对手（owner 1）的"回合开始时自动强化"后跑 → 这次强化当回合压不下去 →
   **速度等级差直接改写出手先后**。事件是唯一的"写后即知"通道，天然与时点定序无关。
   - 事件**只在窗口内响应**（`ev.state ∈ [BATTLE_ROUND_START, BATTLE_ROUND_END]`）；
   - `BATTLE_ROUND_START` / `BATTLE_ROUND_END` 各再加一次**直接压制**兜底
     （覆盖"窗口开启前就存在的等级差"，如对手在操作阶段/登场时强化的情形）；
   - 压制自身的 `stat_change` 会再发事件 → 下一波复查时条件已不成立（等值）→ 必然收敛；
     `write_ability_level` 里 `delta == 0` 早退是这条收敛性的保险。
   - 场景 080 的 B2 就是这条 bug 的回归守卫：对照组（索伦森无魂印）= 对手先手，
     实验组（带 1011）= 即时强化被压回 0、索伦森拿回先手。

## 四、子句①③④ 与技能组的口径

- **① 禁强走新票 `STAT_BOOST`**：`stat_change`(delta>0) / `transfer_stat_boosts` 的 to 侧 /
  `stat_reversal`（负翻正）三处查询，命中即"整次失败、等级一点不动"。
  `clear_stat_boosts` 的返回值为 0 时**后续两件一概不给**（"消除成功则…"）。
- **① 封属走 `SEAL_ATTRIBUTE`（hit_invalid=false）**：即"属性技能无效"→ 走 ②被无效、
  触发技能无效补偿。**先例不一致**：同措辞的 781（艾恩斯·秩序之助）取了
  `SEAL_ATTRIBUTE_HIT`（照常命中、效果失效、不触发补偿）。本处按更接近的 **1217/936** 取"无效"，
  见 §六 待拍板。
- **③ 两个分支是两种机制，别合并**：
  · 命中 = **次数型免伤**（`ImmunityType::DAMAGE` + counts=1 + duration=1 回合）→ 由伤害管线
    **BLOCK 阶段**消费。**必须**走这条路：只有它吃同一道"挡伤失效"抑制门
    （`ElfPet::damage_suppress_mask`，沧岚 蚀砚之泪≥4 滴）——被压制时**既不触发也不扣次数**
    （场景 031 Q4 契约，080 C2 复验）；红线场景 080 C2 就是用户点名要的那条交互。
  · 未触发 = **减伤 50%**（`ws.damage_reduce_add` 抢第一个空槽）→ MITIGATE 类别，
    **不可被"挡伤失效"无视**（官方："减伤100%、点数减伤全都是不能被无视的效果"）。
    写在 ws = 结构性"当回合"（ws 每回合 reset）。
  · 官方"下次"在回合开始时逐回合重掷 → 免疫票 `duration_rounds=1`（用户 2026-09-18 口径：
    "每次概率 roll 一个一回合的次数效果"）。
  · ★ **一次掷点、两分支互斥、事后不改判**（用户 2026-09-18 口径）：掷中挡伤之后，即使这次挡伤
    **被无效**（蚀砚之泪≥4 滴压制 / 免疫票被别的效果压掉）也**不会**退回 50% 减伤——
    本条的判定**已经消耗**，挡伤失效是**另一条机制**在作用，不该反过来改写 ③ 当初的判定。
    实现上是结构性的（减伤只写在 `else` 里），并且**加了断言钉住**：080 C2 明确检查
    "被压制那一路的 `ws.damage_reduce_add` 全 0、伤害照常落地、免疫票未被消费"。
    将来若要改成"挡伤被无效则改判减伤"，必须**同时**改 `soulmark_1011_round_start` 与 080 C2。
- **④ "等量" = 实际恢复量**（吃封回血/恢复修正后的 HP 差），与 effect 1005 同口径；
  粉伤走 `PERCENT_VALUE`（值自算但吃百分比抗性/护罩/免粉）；两个量共用 `max_hp/3` 封顶。
- **登场节点必须 `early=true`**：魂印在**中切**时由 `perform_switch` 直接 `activate_soul_mark`，
  而 `OPERATION_ENTER_EXIT_STAGE` 这个时点**每场只在第 1 回合开头跑一次**
  （其后每回合从 CHOOSE 起跑）→ 不给 early，中切上台的索伦森当回合不会消强/封锁。
  代价：战斗开始时 early 与桶各跑一次 → 幂等（消强第二次返回 0 → 后续一概不给）。
- **技能组 9 个 effect**（详见各函数注释）：

## 五、踩坑清单（本批实际踩过的）

1. **单效果链路魂印（旧）在登场时还会立即执行一次**：测试里用它做"回合开始自动强化"样本时
   当回合共 +2×2 = +4。做**受控样本**要用 `SoulMarkManager::registerSoulMarkProgram` 注册
   只挂 `BATTLE_ROUND_START` 一个节点的程序链路魂印（场景 080 的 `kTestBoostMarkId`）。
2. **rand 路径决定"同种子两局取差"能不能用**：③ 的掷点是 ROUND_START 且**只在"自身无提升"时掷**
   → 有提升那局少掷一次 → 序列错位，固伤档位差算成 -67。凡是"同种子取差"的验证，
   先确认两局的 rand 消耗序列一致（080 的 E3/E9 都因此**剥掉魂印**再比）。
3. **`has_round_effects()` 拿不到 0**：技能一旦被点选，引擎就在 `BATTLE_FIRST_MOVE_RIGHT`
   为使用方登记一条 `source_id = 技能 id / effect_id = 0` 的回合类标记（`skills.cpp` 的
   `on_selected` 落点）→ 该侧 `has_round_effects` 恒 > 0。所以"断回合未成功"的样本要用
   **免断（IMMUNE）** 而不是"对手没有回合类效果"（080 E5b）。
4. **`play_round` 的第二个参数是技能下标不是技能 id**（写 `kSkillZhuangJi` 会打印
   "Invalid skill index: 10001" 并静默跑空一轮）。
5. **中切时才发现的坑**：`early` 节点在战斗开始时"early + 桶"各跑一次是正常的，别当 bug 删掉
   （删了就变成中切漏触发）。
6. **战斗开始前的 `ability_levels` 摆位有效**：`init_battle()` 在 BattleContext 构造里跑
   （`clearAllEffects` 会清等级），所以想在"登场判定"看到预设等级，必须在构造后、
   `start()` 之前写（080 A1）。中局摆位则要在 `start()` 之后、`ROUND_START` 执行之前。

### 六'.1 下一步：事前阻断（用户 2026-09-18 提出的更彻底解法）

现在的压制是**事后压回**：变更先落地 → 挂在 `EVENT_STAT_CHANGED` 上的监听器再改回去。
它能拿到正确**最终态**（080 B2 保证出手先后正确），但有两处残余：

1. 在同一个 drain 波次内，对手的强化**真实存在过**——同波次的其它监听器
   （"对手处于能力提升状态时…"一类）原则上能看见那个瞬态；
2. 监听器必须自己处理 (owner0→owner1) 桶定序与窗口边界（本实现的窗口过滤就是这么来的）。

### 六'.0 先澄清：事件方案**不等于**"下一个时点才处理"（用户 2026-09-18 的对比提问）

`battleFsm.cpp` 的 `runInternal`：**每个 State 的 handler 跑完、推进下一个 State 之前**统一 drain
（注释原话："事件投递点：State 桶执行完后、推进下一个 State 前"）。所以与"在每个可能变等级的
时点插一条检测"相比：

| 维度 | 逐时点插检测节点 | 本实现（事件） |
|---|---|---|
| 落点 | 该时点**该 owner 的桶内** | **同一个 State**，但双方桶**都跑完之后** |
| (owner0→owner1) 定序 | ❌ 先跑的一方看不到后跑的一方的变更 | ✅ 天然消掉（这正是 B2 那个 bug 的根因） |
| 覆盖完备性 | ❌ 要人枚举"可能变等级的时点"，漏一个就漏一次压制 | ✅ 任何走原语的写入都触发 |
| 残余缝 | —（本身就没覆盖全） | ⚠️ handler **之后**才 drain：同一 handler 内"先改等级、后消费等级"会晚一拍。已知两处：`handle_BattleFirstMoveRight`（双方桶跑完 → 同 handler 内算先手权）、`BATTLE_*_ATTACK_DAMAGE`（桶跑完 → 同 handler 内跑伤害管线）。实战中没有"速度等级在 MOVE_RIGHT 才变"的魂印（自动强化都挂 ROUND_START），故 080 B2 绿；但这条缝真实存在 |

⇒ 逐时点插检测 = **枚举式补丁**（必漏）；事件 = **完备但事后**；入口拦截（§六'.1）=
**完备且事前**（连上面那条"同 handler 内先改后用"的缝也一并消除）。

**根因**（用户判断，与官方现象一致）：等级变更**没有统一入口**，谁都拦不住 →
"魂印自动强化影响先手权"这类问题会反复出现。本批已经把入口统一了
（`write_ability_level`），所以正解是**在入口上拦截**：

- 索伦森**在场时**往 RuleCenter 注册一条**绑定自身的等级上限拦截**
  （owner = 索伦森方、作用于对手侧、上限 = 索伦森同项等级；随上下场开闭）；
- 拦截点在 `write_ability_level` 内：写 `(target=对手, stat=i, new_level)` 时若
  `new_level > cap` → **钳到 cap（或拒绝本次变更）** → 那次强化从未发生，
  不依赖事件、不依赖时点定序；
- 两个方向都要管：① 对手想超过我 → 钳；② **我自己掉下去**（被弱化）→ 对手现在就超上限了，
  要在"自身等级变化"那一趟顺带复查（我自己的变更也走同一入口，天然挂得到）。

落地清单（顺序即依赖）：
1. RuleCenter 加"等级变更拦截"条目族（**不是 IMMUNE**：没有次数/时点覆盖语义，生命周期随宿主在场）；
2. `write_ability_level` 内查询 + 钳制（两方向）；
