## 一、为什么先做这条线

官方出现了一批印记，作用不是施加/免疫某个状态，而是**改另一条概率判定的实际值**：

| 印记 | 宿主 | 文本（官方 effect_icon） |
|---|---|---|
| **亮节** | 无极圣武 4800（魂印 2436）/ **帝皇侠复用同名印记** | 「精灵持有时，套装、特性、魂印、技能中不高于 50% 的附加异常效果全部降低为 0%（**直接针对控场宝石、主动毒、被动毒**）」 |
| 威怯 / 武诛 / 英雄之诫 | 无极圣武 4800 | 无极圣武魂印其余子句（未实现） |
| **永沐** | 梅赫维特 4853（魂印 2456） | 「自身位于出战背包时，若对方精灵执行概率不高于 50% 的异常状态附加效果**则为对手附加曝**」 |

共同点决定了机制形状（三条，**缺一条都会设计错**）：

1. **判据是运行时实际概率**，不是数据表字面值。语料《机制解析—无极圣武》原文：
   「**以实际概率为准**，比如 001 的战栗特性提升到 100% 就不受影响，另外对于叠加类效果
   同样也是，比如克罗的魂印，首次 40% 害怕会变成 0%，之后超过 50% 的害怕就不受影响」
   ⇒ 判的是"本次到底是多少 %"，所以**必须在掷骰之前**问。
2. **实时**，不是静态。「亮节：**下场不保留**」「永沐：**位于出战背包**」——生命周期随
   上下场变化，且亮节是 3 回合临时 buff。⇒ 只能靠**查询式票 + EffectScope**，不能做清点。
3. **与是否触发无关**。梅赫维特原文：「**不论这个控场是否触发**，只要对手打了带有不高于
   50% 的控场效果就必定给对手挂曝」⇒ 处理发生在**裁定**阶段，不是事后通知。

> ⚠️ 第 3 条是"事件方案"的死因：`EventCenter` 是**事后 emit** 设计
> （`event_center.h:15-18`「事件是'发生了什么'的声明」），而"概率没过门"这一档
> **根本没有原语调用、也就没有任何事件**——偏偏它是最需要覆盖的那一档。
> 而且事件是入队 + FSM 晚 drain，回调跑时 `currentState` 已推进，用它去改"本次概率"
> 时序上必然迟到一拍。

**先例**：引擎里已经有一模一样的形状 —— `src/primitives/battle_primitives.cpp:171-181`
的 **[2.1] 砥砺(37) 条件位**（"**对方**执行过附加异常这个动作"，置位在**入口**、
明确「不要求真落地：免疫/抗性/被弹控也算执行过」）。本线就是把这个形状一般化。
另注：砥砺的条件位**排除**主动毒/被动毒，亮节**包含**它们 —— 所以"来源"必须是可查询数据。

## 二、设计：申报 → 闸门改写 → 掷骰

```
效果侧声明"本效果的概率是多少%"（chance_pct / probability_pct）
        │
        ▼
[闸门] rewrite_anomaly_chance(被施加方, 施加方, pct, tag, source, round)
        │   票参数纯数据：threshold_pct / below_result / above_result / source_mask / tag
        │   多票按**授予顺序折叠**（前一张的输出是后一张的输入）
        ▼
[掷骰] <=0 必定不触发（不消耗 rand）/ >=100 必定触发（不消耗 rand）/ 否则 rand()%100
        │
        ▼
没过门 → ApplyAnomalyResult::ROLL_FAILED（**≠ 被免疫**：对应官方"未触发补偿"那一档）
```

### 2.1 两个"按类切分"的枚举（**刻意不通用化**）

```cpp
enum class ChanceTag    { AnomalyAttach };                       // 现在只有一类
enum class ChanceSource { Skill, SoulMark, Trait, Suit };        // 四类来源
```

- **`ChanceTag`**：亮节**只管异常附加**，概率挡伤 / 概率强化 / 概率弱化 **一概不碰**。
  将来真出现只作用于别的概率类别的印记，**再加一个值**并在它自己的查询点显式传——
  不给所有概率统一加标签（那会把语义不同的东西混成一套）。用户 2026-09-22 拍板。
- **`ChanceSource`**：官方亮节枚举的就是这四类（套装/特性/魂印/技能）→ **四类全管**；
  永沐明说「**不包含**双方的特性主动毒和被动毒」→ 只管理其余三类。**两张闸门管辖面不同**，
  所以来源必须是票上的 `source_mask`（`chance_source_bit()` 构造，`kChanceSourceAll` = 全管）。

### 2.2 票为什么复用 `RuleCenter`

新类别 `RuleCategory::CHANCE_GATE`，并登记进 `is_pure_query_category`
（`rule_center.h`）→ 白拿这些：**免 tick / 免断回合 / 免 epoch 作废 / 不计入"有无可断物"**；
窗口用 `register_round + remaining_rounds` 表达（`rewrite_anomaly_chance` 里比较，
`cleanup` 清理）；"下场不保留"用 `scope=ON_STAGE`（引擎换宠即清）。
形态与 `ATTACH_BAN`/`SKILL_BAN` 完全同族（`rule_center.h:140-152` 的注释自己写明
"**查询式保护**，不是给被保护方全队上免疫"）。

### 2.3 "未申报 = 闸门不介入"是**结构性**保证

三个施加原语的尾部参数 `chance_pct` **默认 -1 = 未申报**：
调用方自己已经掷过骰、或本来就是"必定"——闸门一概不问。
⇒ **所有旧调用点行为与改造前字节级一致**，不靠纪律；代价是"未迁移的调用点**漏管**"
（不会误伤，只是不受亮节影响）。这个默认值是整个迁移能增量的前提。

### 4.3 为什么有两档掷点位置（**改代码前必读**）

- **原语内掷骰**（route A，首选）：申报 `chance_pct`，原语在 [2.2] 先过闸门再掷。
  语义最干净——异常概率全引擎只有一个掷点。
- **闸门后本地掷骰**（`common_trait.cpp` 的两处 + `effect_unit.cpp` 的 `roll_chance`）：
  **只在掷骰前插一道 `rewrite_anomaly_chance`，掷点本身不动**。
  原因（`common_trait.cpp` 与 `trait_state.h` 都留了记录）：本仓库的伤害/命中断言
  **依赖既有 `std::rand` 序列**，无条件掷点会移位全局序列、连带伤害浮动/闪避判定整体错位
  （2026-09-16 已因此发生过 4 个场景的回归）。把掷点搬进原语会让
  `[duration rand]` 与 `[概率 rand]` **互换次序** = 整场随机序列的改动，与"给闸门加覆盖"
  这件事无关，故不搬。两条路径**共用同一道 `rewrite_anomaly_chance`**，语义不分叉。
- 对照：`resources/moves_lib/common.h` 的 `apply_ancient_hit_status` **可以搬**
  ——那条路径除这一次掷点外没有别的 rand 消费者（`random_anomaly_duration()` 是常量），
  搬移只影响"目标已死"这一条早退分支的 rand 消耗。

## 七、明确**未找到证据** / 留了口径自由度的地方

1. **亮节"回合结束时给对手 pp 为 0 的技能恢复 5 点"**：只有《机制解析—无极圣武》一句，
   且"给**对手**恢复"对持有者不利、与"亮节是防御 buff"的语境相悖（疑似"自身"之误）。
   ⚠️ **未实现**，也不在本管道的管辖面内（它是数值恢复不是概率）；宿主落地时需先实测确认
   对象到底是自己还是对手。
2. **亮节是"护持有者"还是"压制持有者自己"**：文本「精灵**持有时**，套装/特性/魂印/技能中
   不高于 50% 的附加异常效果全部降低为 0%」没说"对方"。实现取**护持有者**
   （票挂持有方、问的是"施加到持有者身上的概率"），与"亮节是防御性 buff"的语境一致
   （无极圣武是给**双方**精灵登场时发亮节）。若实测不同，改 `rewrite_anomaly_chance`
   的 `protected_side` 取值即可（一处）。
3. **永沐是"降为 0"还是"只挂曝不降概率"**：体验服文本「双方不高于 50% 的异常附加效果失效」
   vs 正式魂印 2456「若对方精灵执行概率不高于 50% 的异常状态附加效果**则为对手附加曝**」
   （**没写失效**）。《机制解析—梅赫维特》两处表述并存。落地时以正式文本为准，
   但把"降为 0"作为可开选项（`below_result=0` + 回调挂曝）。
4. **英雄之诫的"高于 50% 提升至 100%"是否含抗性/能力值那些数值子句**：
   那是数值钳制不是概率，本管道只管概率（`above_result` 只对概率生效）。
