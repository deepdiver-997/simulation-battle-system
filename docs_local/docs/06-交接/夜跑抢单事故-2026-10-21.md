## 二、三个根因（缺一不会出事）

1. **`finish.sh` 无条件 `agent_id release`**
   完工一单 ≠ 会话收摊，但状态被写成了"已收摊"。这是事故的**触发条件**：
   注册表在有人正在干活时显示 `released`。
2. **`taskctl` 的 CAS 不校验属主**
   `cmd_claim` 只断言"行状态 == 待领取"，`cmd_release` 只断言"== 进行中"。
   两者都不知道"这一行有没有活着的属主"，于是 release+claim 这条抢占路径完全合法通过。
3. **`claim.sh` 见目录存在就复用**
   `if [ -e "$wt/.git" ]; then log "worktree 已存在，复用"`——不问里面是否有人在写文件。
   设计前提本来是"一个 worktree 对应一个正在干活的会话"，但没有代码校验这个前提。

### 语义定版（这次事故最该记住的一条）

> **`status` = 是否愿意接新单；`busy` + 心跳 = 是否正在干活。判生死只认心跳。**

`released` 只表示"不接新单"，**不作废 busy**。这正是原设计最容易误读的地方，
也是事故的直接成因。

## 五、未修/待决

1. **K261 当前无 busy 记录**（a01-kprod 在我改代码之前领的）。它靠行文属主闸兜住，
   a02 现在退不了。它下一次 claim 会正常登记 busy。
2. **`cmd_done` 未加属主校验**（只做清 busy）。理由：`finish.sh` 里 `TASKCTL_WORKER`
   未必设置，worker_id 会退化成 `zhr@pidNNN`，硬校验会**误杀合法完工**——风险高于收益。
   若白班认为必要，建议先让 finish.sh 强制导出 `TASKCTL_WORKER=$SBS_AGENT_ID`，再加校验。
3. **build 信号量与 worktree 仍无硬绑定**：两个会话若绕过 claim 直接在同一目录构建，
   机制层仍拦不住。本次闸门覆盖的是 claim/release 这条主路径。
4. **taskctl 的 `mark_busy` 对非 agent worker 静默跳过**（`zhr@pidNNN` 这类未注册 ID）——
   协议要求必须领 agent ID，故可接受。
