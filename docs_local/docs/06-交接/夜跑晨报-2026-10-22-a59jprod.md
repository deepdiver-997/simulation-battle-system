## 三、勘误记档

1. **同 source_id 跨侧覆盖**（J296）：`grant_immunity` / `grant_chance_gate` 的
   `source_id` 是**刷新句柄**——两侧用同一 id 时第二张会刷新第一张（owner 不变），
   结果只有一侧真正挂上票。两侧须用 `base + side`。场景 T6290.e 首次暴露（soul1=0/soul0=1）。
2. **同状态桶会拾取新注册条目**（J302）：在 `SKILL_EFFECT` 桶执行中注册同状态窗，
   桶会当场再跑一次新条目 → NextRounds 起点失效。payload 带 start + 显式
   `roundCount >= start` 卡住（a60 终版改为 InRounds，结论一致：必须显式处理起点）。
3. **OLD_ROUND_END_1 授予回合型封属要 +1**（J297）：该锚点之后紧跟
   `tick_rounds()`，`duration={0}` 会当场扣到 0 → 用 `{0}+1` 才得到"下 {0} 回合"。
4. **effect 5 的槽码实写引擎槽**（J297）：瞪眼 20004 `[1,100,-1]` 改的是
   `ability_levels[side][1]`（特攻槽），不是文档常说的"防御"。场景观测面按
   实际写入槽取值，避免拿"等级和"或错槽做假绿。
5. **`plugin_storage` 存 float 后 `any_cast<int>` 返回空**（J305）：AMP 阶段探针
   第一次写 `ws.damage_add_pct`（float）进审计槽，`stor()` 用 int any_cast 恒得 0 →
   必须 `static_cast<int>` 后再存。
6. **KO 回合不跑 BATTLE_ROUND_END**（J305）：`CHOOSE_AFTER_DEATH` 后直接
   Round Completion，"击败也回血"变异结构性不可观测；"击败不注册"仍由审计槽守住。
7. **"未触发"两族口径**：异常施加 = 仅 `ROLL_FAILED`（J209/J210，2026-10-22 同批）；
   能力下降 = 仅 `IMMUNE`（2320 口径，`AT_FLOOR` 算触发）。J296/J303/J302 分别按此实现。
   **勘误（2026-10-25，官方实测）**：能力下降族口径翻转——灼眼焰华 2161 同族官战实测
   （补偿以状态栏图标呈现）证明**对手 -6 钳底也算未触发**，J302 已改 SUCCESS 才算
   落地；异常施加族（J296/J303）口径不变（那是 ROLL_FAILED 门，与降属无关）。
8. **author 冷却 600s**：`author_done` 后 10 分钟内同会话拿不到制定权；`author.sh`
   超时后可重试。`claim.sh` 在队列空时失败但 `taskctl claim <id>` 可正常领单。
9. **并发派发事故（a60-jprod）**：编排于 11:50 在 a59 仍活时又 spawn 了 a60（同一
   worktree/分支），a60 清掉 a59 的 busy 后接管 J302，导致同单双 claim/双 done。
   未发生文件级并发写冲突；J302 终版以 a60 的 InRounds 口径 + 40 checks 为准。
