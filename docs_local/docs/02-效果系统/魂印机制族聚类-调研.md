> 定位：为"内核更新新精灵"做 groundwork。新精灵与老精灵的技能效果大量共享家族，
> 机制差异度集中在**魂印程序**，而 soul 注册只有 47/1864——本文把 2149 条
> effect_icon 魂印按机制聚类，盘点内核原语缺口，立首批可批产族。
> 调研输入：`effect_icon` 2149 行（`scripts/data/processed/seer_unity.sqlite`）、
> `curl :8070/api/effect-index` soulEffects 1863 条、`resources/soul_lib/*.cpp`

## 〇、结论速览（三个验收问题）

**① 若只做"现有原语"魂印，第一批能覆盖多少引用？**
行级口径：**单时点短宏形态 420 行（20%）** 是"一个 handler + 参数表"就能吃掉的
（引用精灵 458 只）；再加上多子句但全部子句落在本调研"族清单"已有原语上的组合型
（42% 的行含 ≥2 时点词，其中绝大多数仍是"已知时点 × 已知动作"的组合），**第一批
做 top 引用 60 个效果宏就能覆盖 285 只精灵的 ≥1 个魂印**（引用榜 60 名内仅 3 宏
含箱二/三模式；剔除 0/247/137 三大静态宏后为 136 只）。引用分布极度长尾（1809/1864 宏只被 1 只精灵引用），批产价值 =
**族模板 × 行参数化**——一个 handler 按 effect_id 注册、吃掉同 id 多行参数实例
（见 §一"行≠宏"）。

**② 需要新内核原语的族、优先级？**
真正卡在内核的只有四件事（§六详表）：
P0 **场地/领域容器**（1780/1913/1935/1964/1649 至少 5 魂印，双 方可见、持续 N 回合、
影响双方结算查询）→ P0 **命中/闪避百分比改写钩子**（12 魂印）→ P1 **暴击倍率乘区**
（8 魂印）→ P1 **场下印记/资源定时器标准化**（1897 处决印记、1245 圣辉之羽等 12+
魂印；roster 先例在 903/2513/3550，缺的是"场下每回合触发"的标准桶与层数资源模板）。
P2：PP 上限/回合数改写（22）、回合类效果防消除豁免旗标（122）、连续同技计数（2036）。

**③ 神谕波次精灵的魂印缺多少？**
`sp_hide_moves` 有行的神谕波次精灵 **148 只**（id≤5000），全部挂有魂印，其中魂印
已注册仅 **6 只**（3516 混沌地王、3683 混沌魔尊、3711 圣光莫妮卡、3740 怒涛沧岚、
4125 洪荒列奥尼达、4186 镇世乔特鲁德——全部是精灵王线人工精做）→ **缺口 142 只、
涉及 191 个未注册效果宏**。神谕精灵集中在 id 3156~4863 段，tips 普遍是 3~6 子句的
长程序（D 桶密度高于全库均值），批产前需先落 §六 的 P0/P1 原语。

**⚠️ 行≠宏（本调研最重要的结构发现）**：同一 effect_id 的多行**各有自己的 tips 与
args**，是同一"效果宏"的不同参数化实例。实证（effect_icon，effect_id=150）：
id=19「[万魔天尊] **50%**免疫对手致命一击造成的伤害」args 空 /
id=257「[圣皇] 有**35%**概率免疫对手致命一击造成的伤害」args「350 0」/
id=2027「[保姆派派] **60%**免疫受到的致命一击伤害（boss有效）」args「600 0」。
→ 批产协议 = **handler 按 effect_id 注册一次，行的 args 驱动每宠数值**
（`bind_soulmark_args` 约定：args[0..2]=owner/enemy/host_slot 注入，DB args[2:] 透传，
见 `src/entities/soul_mark_manager.cpp:351`）；引用数排行也应以"宏被多少精灵引用"计。
另一实证：effect 693 三行 args「1 50 2 200」/「0 0 1 150」/「1 60」是三种完全不同的
参数形状——**行级切片口径的坑与 R 组在技能效果侧踩的 `side_effect.arg_count`
双表不一致同源**，魂印侧暂无 arg_count 二表，但 args 语义逐族各异，批产时逐族抄写。

**4399 交叉验证（3 例抽样）**：
- 一致：2580 斗神瑞尔斯（`reference/scrape_4399/out/pets_full.jsonl`）"豪:每次受到
  攻击都会反馈给对手1/6的伤害" = effect_icon effect_id=11（DB 有错别字"收"→"受"）；
- 一致：4731 皮神 4399 文与 effect_id=2346 大体同文（DB 版多"其他"限定词，以 DB 为准）；
- **4399 残缺例**：2458 艾尼维亚 4399 无魂印文本（kind:"none"），effect_icon 有完整
  tips——**effect_icon DB 是魂印文本的权威源**，4399 只做旁证；
- 参数化警示：2468 万魔天尊 4399 写"50%免疫"与 effect_icon id=19 一致，但同槽
  2378/2379 是 35%——同 id 不同宠数值不同是**常态**，实现必须读 args/行文，不许照抄
  任一行文本硬编码。

## 二、分桶：单效果宏 vs SOUL_PROGRAM 多节点（工单①）

行级统计（2149 行，子句按 `；/;/换行` 切分）：

| 子句数 | 行数 | 占比 | 形态判读 |
|---|---|---|---|
| 1 | 779 | 36% | 单效果宏（SOUL_MARK 单节点即可） |
| 2 | 1121 | 52% | 双子句（多为"条件 A / 否则 B"或"时点1+时点2"双节点程序） |
| 3 | 199 | 9% | 三节点程序（精灵王线密度高） |
| ≥4 | 49 | 2% | 长程序（1897 至序圣华 5 段、1724 650 字符等） |

- tips 长度分位（行级）：p25=51 / p50=97 / p75=131 / p90=182 字符。
- **含 ≥2 个不同时点词（SOUL_PROGRAM 多节点形态）：897 行（42%）**；
  单时点短宏（≤1 时点词且 ≤40 字）：420 行（20%）。
- 判读：魂印库整体比技能效果"重"——52% 双子句意味着**多节点程序是常态**，
  但节点几乎都落在同一批"时点 × 动作"模板上（§四）；真正的重程序（自定义资源系统）
  是 49 行 ≥4 子句 + 精灵王线 ≈100 行的规模，其余是模板组装问题。

### 箱二：需新内核原语（≥5 证据）

1. **场地/领域容器**——「自身登场时若对手体力值＞500则激活**机械领域**（效果持续3回合），
   若对手体力值≤500则激活**次元领域**」（effect_icon id=1408，effect 1780；1935 同构）；
   「次元之琴会将己方**场地**变为**灵籁泳馆**…持续5回合」（id=1601，effect 1964）；
   「若双方全属性能力差值≥3开启**倪克斯结界**：下2回合对手攻击技能先制效果失效…」
   （effect 1913）；「50%触发**寒霜结界**：免疫此次受到的攻击伤害」（effect 1649）。
   → 引擎无"场地"状态容器：双方可见、持续 N 回合、在伤害/先制/命中多个查询点生效。
   需要新原语：field/zone 状态槽 + 注册查询钩子（形态类似 RuleCenter 票但作用于"场地"
   而非"精灵"）。
2. **命中/闪避百分比改写钩子**——「使对手的**命中率-6%**」（effect 7，id=56）；
   「受到伤害减少15%，**增加5%的闪避率**」（effect 280）；「先出手时当回合自身
   **闪避率提升70%**」（effect 1057，id=774）。能力等级槽 5=命中是 ±6 等级制，
   表达不了百分比面板；ws 无命中/闪避百分比视图字段。12 个魂印需要。
3. **暴击倍率乘区**——「致命一击造成的伤害提升10%」（effect 283，id=38 起）；
   8 个魂印需要"暴击伤害倍率"乘区，管线现无此阶段参数。
4. **场下印记/资源定时器标准化**——「[裁决]：至序圣华登场时，对手**场下**体力最高的
   随机1只精灵受到处决：被处决者获得1层**处决印记**；3回合内，其根据处决印记的层数
   获得下列效果…1层：回合开始时，自身受到100点真实伤害」（effect 1897，id=1547）；
   「每次登场时对手每存在1层处决印记，则登场2回合内自身受到的伤害减少20%…同时为对手
   在场精灵附加1层处决印记」（effect 1972，id=1617）。roster 先例（903/2513/3550）都是
   watcher+storage 手工搭；需要"场下宠物每回合 tick 的标准桶 + 层数资源模板"，
   否则每个此类魂印都是 300 行手工程序。
5. **召唤/伴生容器批量通道**——「在圣光天马的祝福下…**召唤**持续1回合的**圣辉之羽**
   庇护自身」（effect 1245，id=956）；12 个魂印涉及。qiaotelude（金祖之龍/玄源之㡣）
   已趟出额外精灵容器首批，但每个新召唤体仍要手写容器装配——需要"召唤物注册协议"
   （能力面板来源、时点桶挂靠、消亡规则三声明）。
6. **PP 上限/回合数改写**——「2036：若连续次数≥n次则使用后额外消耗对手全部体力
   （n=自身携带技能中**PP值上限最高**技能的PP值上限）」（effect 2036，id=1654）；
   22 个魂印涉及 PP/回合数的上限侧改写，现有原语只有增减（pp_reduce/restore）。
7. **回合类效果防消除豁免**——「回合类效果无法被消除」（effect 122，id=120）。
   `break_round_effects` 需要一个豁免旗标（票或字段），否则此类"锁定"无法表达。

### 箱三：语义不明（≥5 证据，动工前需官方文本/语料/实测裁决）

1. **信息展示类**——「将三藏、蒙奇多克、天河神将、沙悟净共同放入背包则战斗中永久
   **看穿敌方精灵血量**，且我方首发精灵登场时全属性+1（仅限boss对战）」（effect 0，
   id=17 起 119 宠）。"看穿血量"是对战 UI 信息面，模拟引擎无对应语义；boss 对战
   本身不建模。→ 建议口径：此宏按"仅 UI 语义"整体跳过，或只做全属性+1 子句。
2. **现实日期彩蛋**——「每当中秋节和每个月的22日，它将爆发出惊人的力量！」
   （effect 247，id=22 起）；「每个月的25日…自身所有能力值+50！」（effect 1307，
   id=1012）；「每个月的5日，冠绝火龙之力爆发：攻击值增加200点…」（effect 1560，
   id=1225，4 段日期表）。现实时钟进对战引擎语义未定（测试无法复现、对局中途跨日）。
   → 建议口径：按"恒不触发"或"恒触发"二选一入审计口径，不改内核。
3. **同宏多行数值冲突的权威口径**——effect 150 三行 50%/35%/60%（id=19/257/2027，
   详见 §一）：tips 数值与 args「350 0」/「600 0」的换算关系（=概率×10？）无文档，
   且 id=19 行 args 为空。→ 需与 R 组切片口径一起定"魂印行 args 语义表"，未定前
   批产逐行抄 tips 数值、不信任 args。
4. **"直接攻击"术语**——「开场2回合内所有**直接攻击**都将额外附带30%概率使对手冻伤」
   （effect 265，id=14）；「首次登场3回合内所有**直接攻击**附加50点固定伤害」
   （effect 288）。"直接攻击"=攻击技能？含属性直伤？语料无统一定义。
5. **非 0-9 段异常的运行时语义**——「流血」（Bleed=16）：「所有技能有50%概率令对手
   流血」的流血每回合结算规则（掉血量/回合数）在 effect_icon 无描述，官方异常码表
   只有名字；「失明」（Blind=20，effect 1224「80%令对手失明」）、「冰封」
   （Icebound=15，effect 827）同理。枚举在表 ≠ 行为在内核——批产每个非 0-9 异常前
   需先补该异常的持续效果语义（逐个小内核任务）。
6. **kind 标签无 legend**——kind 列是 0~16 的多值数组（[11] 83 行、[] 82 行…），
   全库无字段说明文档。聚类只能从 tips 反推（本文 §四 即成果），建议随魂印批产
   顺手回填 legend 到速查表。

## 八、方法论附注（下次调研少踩的坑）

- **effect 1004 ≠ 魂印 1004**：双注册空间（SKILL_EFFECT vs SOUL_MARK），检索先定空间
  （速查表已载，本次多次命中）。
- **SQL 里对 JSON 文本列 LIKE 是陷阱**：`json_each(pet_id) LIKE '%…%'` 写法既慢又
  误配（宠物 id 子串互撞），一律取出后用 Python `json.loads` 精确解析。
- **soul_lib 注册 id 半数藏在常量里**：`SOUL_PROGRAM(kXxxMarkId, …)` 的常量可能定义在
  `resources/*_runtime.h`（如 kGaiaMarkId=736 在 gaia_runtime.h）——盘点覆盖率时
  grep 半径要含 `resources/` 根。
- **tips 文本有错别字**（"收到攻击"），且 4399 会残缺（艾尼维亚）——**effect_icon DB
  为权威**，4399/语料只做旁证；数值冲突时看 args（但 args 语义未表化，见箱三 3）。
- **统计口径三条腿**：行（2149）/宏（1864）/精灵（2006）——验收问题①③的数字
  分别落在不同腿上，引用时先说口径。
