# 魂印机制设计与精灵表现档案

> 记录目的：赛尔号的机制设计几乎总是"以某只精灵的魂印为需求来源"。做机制时先有精灵魂印，才去补引擎能力；如果不把"能力 ← 哪只精灵 ← 官方什么表现"这条链记下来，后续看到引擎里某个字段/时点时会忘了它为什么存在、以及设计意图有没有被官方文本带偏。
>
> 本文与 `效果系统内核设计.md` 分工：内核设计讲"效果系统有几个固定内核、机制如何作为数据住进去"；本文讲**反向追溯**——每条精灵效果 → 需要的引擎能力 → 落点。
>
> 建立时间：2026-09-10。机制设计随时追加，不要只写结论，写"被哪只精灵的哪个表现驱动"。

## 一、引擎假设：魂印注册每方唯一（不做 per-ID / per-owner 区分）

**决定（2026-09-10）**：魂印效果注册**按 (trigger_state, owner, effect_id) 唯一**，不做 per-pet / per-slot 区分。

**依据（游戏内规则）**：
- 赛尔号对战单边只允许携带一只同 ID 精灵 → 同方同魂印天然只有一份。
- 即使测试服可带多只同 ID（如多只瀚宇星皇），同名魂印的同源效果**也不叠加**（官方实例：瀚宇星皇魂印的 1/8 回血不因带多只而叠加）。

**引擎落点**：`soul_mark_effects[trigger_state][owner][effect_id]` 去重键足够，**无需在注册/执行层区分 pet_slot**。

**边界澄清**：
- "不做 owner"约束的是**一份注册/一次执行**；不等于"被挂实体只能有一个"。
- 例：启灵元神 1581 神印把层数放进**每个被切上的目标精灵自己的 `soulmark_storage[1581]`**——同一魂印程序可以对不同实体各挂一份私有状态（`ElfPet::soulmark_storage` 是 per-pet 的 `std::map<int,std::any>`），这不受本假设影响。
- 结论：**注册去重按魂印 id；跨实体状态放 per-pet 容器**。

## 二、机制分类（设计框架）

两类"抑制/拦截"机制分开设计，别混用：

### 2.1 全局抑制型（阻断一整类效果）

- **形态**：某个实体存活/在场时，直接让某一**类别**的效果失效。被抑制的 effect 很多、且判断条件统一。
- **实现**：**blocker 在 context 注册一个标志字段**（`ctx->xxx_suppressed[owner]` 或全局面），抑制执行时在效果函数入口查该标志。
- **代表**：薇尔诗 2513 "自身存活于出战阵容时，双方场下的精灵无法指定场上的精灵为效果对象"——一个标志让所有"场下源 → 场上目标"的效果被禁。
- **为什么用 context 字段而非 per-effect 检测**：被抑制面是"一整类"，逐个效果去查"我是不是被薇尔诗抑制"会很散；集中一个 blocker 拥有的标志，由效果函数统一查一次。

### 2.2 执行时检测型（目标侧挂条件）

- **形态**：给**特定目标**挂一个条件，只有命中该目标的效果在**执行时**才检查。
- **实现**：目标侧已挂的免疫/封（如 `HEAL_BLOCK` 封回血、`skill_seals` 封技能、异常抗性）在执行时检测目标条件。
- **代表**：1581 神印层数、封回血、封技能。
- **为什么不是 context 全局标志**：条件绑定在目标身上，非全局；不同目标可同回合有不同条件。

> 若一个效果同时命中两种：先查全局抑制（类别级），通过后再走目标侧执行时检测。层次：**全局抑制（挡类别） → 目标侧条件（挡个体） → 效果本体**。

**空元行者的三层结构（2026-09-17 用户口径澄清，实现前必读）**：
1. **空元之铭**（仐/叵/乂/卌/卪）＝ **绑技能槽**的固有效果，按"1~5号位"逐条对应。
   → 实现方式必须是**按槽位**判定（读 `roundChoice` 实际使用的槽），**不能**按"技能名/是不是第五技能"
   认；玩家调换技能位置即换绑定组合。绑定关系是**游戏开始时动态**确定的。
2. **空元之诗**（2086~2090）＝ 技能的固有词条，**不在原本行动时触发**，而是在
   **追加行动时点**（`*_EXTRA_ACTION`）触发；触发前要"抹除一篇空妄诗章"（上限 12、下场保留）。
3. **空元之录 / 之渎** ＝ 魂印级（ROSTER 常驻）子句，与前两层正交（已落地，见上表）。

## 四、场上/场下 target 识别 + 出战背包被动（roster 级）

**动机**：需要支持"某精灵位于出战背包（不一定在场）就生效"的被动，以及判定"效果源是否场下 / 目标是否场上"。

### 4.0 薇尔诗 2513 的真实判别标准（★ 关键，来自实测参考文章）

> 来源：`reference/scrape/out/all_posts_final.jsonl` idx=57《关于场下精灵不能影响在场精灵的部分细节》、idx=55《薇bug》、idx=58。

**2513 不是"阻挡所有第三方效果"，而是"户口本式的针对"**——只挡**由场下精灵提供的效果**。

| 类别 | 是否被挡 | 例 |
|---|---|---|
| **场下精灵提供**的效果（年费类） | ✅ 挡 | 星皇buff、星皇回血、启灵神印、帝君先1、梅场下挂曝、奥菲支援、圣武砥砺 |
| 亡语类 | ❌ 不挡 | 草王buff、卫岳buff（属于"在场精灵死亡后触发"，源不算场下） |
| 大部分己方类**印记**效果 | ❌ 不挡 | 蓓的星执、涂蝶的慕、马头的树海（**源是印记，不是场下精灵**） |
| └ 例外：星皇回血buff | ✅ 挡 | 虽也是 buff，但**源是星皇本身**（不是印记）→ 被挡。实测：印记图标仍在，但不回血 |
| 额外精灵 | ❌ 不挡 | 乔特鲁德的黑白龙 |
| 挂壁三兄弟 | ❌ 不挡 | 老代码不评价 |

**→ 引擎判别轴：效果的 source 是【精灵】还是【印记/其他】**。源=场下精灵 → 被挡；源=印记 → 放行。
这解释了为什么"星皇之赐印记图标还在但不回血"——图标是印记，回血是星皇提供的。

### 4.1 受影响的两个真实精灵表现

| 精灵 | 子句 | 为什么需要 roster 被动 + 源空间判定 |
|---|---|---|
| 薇尔诗 2513 | "自身存活于出战阵容时，双方场下的精灵无法指定场上的精灵为效果对象" | 她可能在背包位也持续开"场域"；需要知道源精灵的场上/场下 |
| 瀚宇星皇 903 | "自身位于出战背包时，己方精灵拥有星皇之赐，首发精灵拥有星皇之佑"（之赐=每回合行动后回 1/8；之佑=战斗开始 3 回合免异常+免弱化） | 星皇场下照样给己方精灵上 buff/回血；但 2513 场域会挡"场下星皇 → 场上首发"的星皇之佑，星皇自己首发（源场上自标）就不挡。**2026-09-21 修正（消逝敏感档）**：星皇被消逝（空元之录等）→ 之赐停止（触发前查门）+ 之佑推送注销（武心婵同款 EVENT_VANISH → revoke）；阵亡未消逝照常提供。场景 107 C/D + 083 E3/E6（断言已翻转） |

### 4.1.1 官方空间定义（★ ROSTER scope 的判定依据）

> 来源：reference idx=149《机制解析—镇世·乔特鲁德（神谕）》。这几个词在官方文本里是**有精确定义**的术语，不是口语：

| 术语 | 官方定义 |
|---|---|
| **位于背包** | 己方 6 个出战精灵（**消逝除外**） |
| **场上** | 在场精灵 |
| **场下** | 除了在场精灵之外的**其他 5 个出战精灵**（消逝除外） |
| **不在场** | 除了在场精灵之外的其他 5 个出战精灵 **+ 额外精灵**（消逝除外） |

推论（原文列举）：
- **额外精灵不属于"位于出战背包"**（如哈肯撒拿不到 20 层余恨、飞王背包内每死亡 1 只先制+1 不生效）。"每有 1 只则 xx"类效果若未写明"背包/己方场下"，**默认额外精灵可以算进去**。
- 额外精灵**不属于"在场精灵"，但属于"不在场精灵"**；**不属于"场下精灵"**（不受灵巢强化、未击败场下消逝、唐大双方场下死亡计数等检测）。
- → 引擎侧见 `docs/05-任务清单` 与 §1：`ROSTER`（位于出战背包）与 `STAGE`（场上）已建模；**额外精灵是独立概念，目前未实现**（本项目暂无额外精灵精灵）。

### 4.2 关键决策（2026-09-10 设计讨论）

1. **源空间状态必须执行时动态查，不能注册时写死**：星皇"每回合行动后回 1/8"每回合触发、星皇可每回合切换上下场 → 注册时把 slot 写进 args 会过期。
2. **新原语 `find_pet_with_soulmark(ctx, owner, effect_id)`**：执行时扫 6 槽返回携带该魂印 id 的精灵槽位；配合 §1（每方同魂印唯一）无歧义。用 `on_stage[owner] != star_slot` 判断"源此刻场下"。**预判被大量使用**（所有"场下被动 + 场域抑制"共用）。
3. **2513 场域 = context 全局 bool**（非 per-owner）：薇尔诗存活于出战阵容时置 true；死亡清。任何"场下源 → 场上目标"效果在入口统一查。
4. **统一门**（单 trigger，非两 trigger 分叉）：给"己方场上精灵上星皇之佑"只需注册一次，效果函数内查：
   ```
   if (ctx->block_offstage_to_onstage && ctx->on_stage[owner] != find_pet_with_soulmark(ctx, owner, 903))
       return kOk;  // 场域开 && 星皇场下 → 抑制；星皇上场自标 → on_stage==star_slot 天然放行
   ```
5. **不是"缺口"，是注册时机选择**（2026-09-10 修正）：先前认为"场下魂印未激活 = 引擎缺口"过重了。正解是魂印分两类注册时机：
   - **STAGE 绑定类**（无为觉者 2260 等纯自身效果）：随上下场。可保留现状（每回合重注册 + 效果函数自查"场上是不是我"），**优化项**：每个 mark 实现「登场注册 / 离场注销」钩子，省掉每回合空转触发；
   - **常驻类**（星皇 903 buff/回血、薇尔诗 2513 场域）：**战斗开始时注册一次**，跨切换存活（TEAM scope），效果函数在**触发时**才检查场上下 + 是否被抑制。它不随注册者上下场开闭。
   → 现有 `register_soul_effect` 每回合只对 on_stage 精灵跑（battleFsm.cpp:783）覆盖了 STAGE 类；常驻类需要"战斗开始对 6 槽扫描注册"这一条并行路径。

### 4.2.6 源的两轴模型（空间轴 × 生命周期轴，2026-09-19 落地；2026-09-21 修正星皇档位）

> 起因：游戏实测发现"星皇之赐**不受消逝影响**、但被薇尔诗阻断"——用单一"源"概念看是
> 自相矛盾的"不上不下"。拆成两个独立声明后它就不再是 bug 而是规格（用户 2026-09-19 拍板：
> 不要每回合轮询注销，**授一次 + 事件推送注销 + 两轴声明**）。
> ⚠️ **2026-09-21 修正**：语料 idx=402「空元之录会吃掉敌我双方的星皇之赐」+ idx=403 交互篇 +
> idx=400（2024.1.12）「一刀切」证明当初的"实测"读法是反的——星皇之赐/之佑**随源消逝失效**，
> 归入**消逝敏感**档（之赐 = 每次触发前查门；之佑 = EVENT_VANISH 推送注销，武心婵同款）。
> detach 档只剩"源=印记"类。

**轴 1｜空间轴（薇尔诗场域只看这个）**：效果**当前**的源在哪。
- 定位谓词 = `BattleContext::find_mark_in_roster`（**只剔消逝，阵亡照算**——官方
  idx=149"场下＝消逝除外"里阵亡仍占位；`find_pet_with_soulmark` 的 hp>0 门把死亡也剔了，
  那是给**更新器停刷新**用的，别混用）。
- 消逝的源 → 不在任何空间 → "场下精灵提供"的前提不成立 → **放行**（薇尔诗挡的是
  "场下精灵提供的效果"，消逝的精灵不是场下精灵）。落地：`offstage_source_suppressed`
  改为纯空间轴门（旧实现 `src_slot<0 → 恒抑制` 把存在敏感压给了所有调用方，已删）。

**轴 2｜生命周期轴（源消失后效果还在不在）**，三档，按效果各自声明：

| 档 | 语义 | 机制 | 例 |
|---|---|---|---|
| **detach** | 授予后无视源死活（"线程 detach"） | 战斗开始授一次，之后什么都不查 | 源=印记的星执/慕/树海（⚠️ 星皇之赐/之佑 2026-09-21 从本档移出——见上） |
| **消逝敏感** | 死亡保留、**消逝即死** | 授一次 + **EVENT_VANISH watcher 推送注销**（持续类）／触发前查 `find_mark_in_roster`（逐次类） | 武心婵 4500（官方"位于背包＝消逝除外"＋实测"自身死亡也还在，被消逝就没有了"）；**瀚宇星皇 903 之赐/之佑（2026-09-21 秤入）**；咤克斯体系 |
| **存在敏感** | 死亡即停 | 更新器停刷新（hp>0 门）+ 触发时惰性查 `find_pet_with_soulmark` | 普通在场类效果的自然语义 |

**推送注销为什么可靠（不用每回合轮询）**：
1. 这类票（RuleCenter）没有别的死法——TEAM 不随切换清、rounds=0 不参与 tick/断回清、
   死亡不清，唯一要防的就是消逝 → 每回合重授是冗余，且"只重授不推送"会留一回合脏窗口；
2. 消逝不可绕过：上限归零只能由 `vanish_spirit` 产生（`reduce_max_hp_*` 下限钳 1 不变量）
   → `EVENT_VANISH` 必发（071 已锁），死亡路径那种"直写绕过漏斗"的对账问题不存在；
3. 事件投递在 EventCenter drain 路径，独立于效果链——"跳过时点"类语义（星皇之怒）
   跳不掉（§4.3 的 2513 死亡监控同款独立性）。

**引擎落点（2026-09-19）**：
- `battleContext.h`：`find_mark_in_roster`（空间轴定位）+ `off_field_stats_protected(side, slot)`
  （场下体力/PP 写入门）；
- `rule_center.h`：`RuleCategory::OFF_FIELD_PROTECT` + `grant_off_field_protect`（覆盖键刷新，
  TEAM 永久）+ `has_off_field_protect`（多提供方取或）+ 既有 `revoke(source_id)`；
- `roster_field.cpp`：门拆轴（903 之赐/之佑随 detach 档修正——旧实现星皇一死回血就停，
  与游戏实测不符）；**新增效果调统一门时必须声明自己的两轴组合**；
- `wuxin_chan_4500.cpp`：武心婵保护子句（场景 083 B/C 组）；
- `zha_liumeng_curse.cpp`：连锁归零写入前查 `off_field_stats_protected`（场下写入路径的
  先例——**新增场下写路径必须先查这道门**）+ 咤消逝守卫/转化位清除（补 v1 遗留）。

### 4.3 星皇之怒的"跳过而非关闭"（★ 影响死亡语义）

> 官方文本：星皇之怒"以技能 50% 威力额外进行 1 次攻击……**体力因此归 0 的对手无法触发任何效果**"。
> 参考：idx=131「有关于'未击败，击败，被击败'相关的时点效果都会被曝失效……某种意义上来说确实是一个跳过时点」。

**实测（用户 2026-09-09~10 游戏内验证，2026-09-10 复核）**：星皇二段击杀薇尔诗 → **抑制消失，死后清除得到保证**。

**推论**：薇尔诗在游戏开始时注册了一个**监控**，在每个"可能导致死亡"的时点触发，检查自己是否已死，若已死则**清除抑制标记**。即：
- 2513 场域标记**不随魂印开闭**（不是"魂印被关闭 → 标记清"）；
- 该 monitor 走的是**独立于「魂印开闭」的路径**——正因为不依赖那条路径，它才不会被星皇之怒的"跳过"波及（星皇之怒只能跳过常规效果触发链，跳不掉这个自注册监视器）；
- 对照：如果引擎只按常规"精灵上下场/死亡 → 注册/注销魂印"来做，被星皇二段击杀时那套注销会被 skip（"体力因此归 0 的对手无法触发任何效果"），抑制就会残留。薇尔诗实测不残留 → 印证了 monitor 路径的独立性。

**引擎含义**：
1. 效果生命周期不能只依赖"开/闭"二元；需要"被跳过（skip）"这一状态。被 skip 的效果不应视为已关闭。
2. 威慑：**凡是靠"死亡时关闭"来撤销的全局状态（如 2513 标记），都要配一个战斗开始注册的死亡监控**，否则遇到星皇之怒就会残留。
3. 这是**星皇之怒的特殊性**（其他二段精灵做不到——idx=113 指出"星皇是仅有一个二段重新计算伤害的"），官方也因此在"新特性 × 星皇之怒"上积累了大量 bug。实现新特性时需专门考虑与它的交互。

### 4.4 结论与分步

落地拆三件事（可独立分步）：
